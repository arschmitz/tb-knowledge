# MailServices message routing and lazy shared services

## Choosing the message service

`MailServices.messageServiceFromURI(uri)` finds the first colon and uses the part before it as the protocol. A URI is the text that identifies a resource. If there is no colon, the function throws a `Components.Exception` with `NS_ERROR_FAILURE`. For `file`, it uses `mailbox` instead. It requests `nsIMsgMessageService` from `@mozilla.org/messenger/messageservice;1?type=${protocol}`.

The function does not fully validate the URI or normalize protocol case. Do not describe it as a general URL validator. Missing protocol components can still fail at service lookup.

`neckoURLForMessageURI(messageURI)` gets that service, calls `getUrlForUri(messageURI)`, and returns `.spec`. Necko is Gecko's network layer. A message URI and its network URL are different representations; callers should use the service conversion rather than change the text by hand.

## Matching native code

In `nsMsgUtils.cpp`, `GetMessageServiceContractIDForURI()` performs the same colon split and `file` to `mailbox` conversion. `GetMessageServiceFromURI()` obtains the matching service, propagates errors, and transfers the service reference to its output. `GetMsgDBHdrFromURI()` calls it and then asks the service for `MessageURIToMsgHdr()`.

These implementations are intentionally paired. A routing change needs a check of both paths, their errors, and the supported protocol registrations. This study did not test all protocols.

## Shared service lifetime

`MailServices` uses `XPCOMUtils.defineLazyServiceGetter()` for accounts, IMAP, POP3, news, outgoing servers, compose, address books, copy operations, folder notifications, transactions, and other mail services. The getter requests a service on first access; merely importing the module does not request every service.

On `xpcom-shutdown`, its observer deletes every current key on `MailServices` and removes itself. The source states that this releases references so they do not appear as memory leaks in test logs. Keeping a separate reference in a caller can extend that caller's lifetime responsibility; deleting this object's properties does not delete every reference in the process.
