# Preserve task terms when building knowledge queries

At the inspected revision, automatic retrieval puts up to 20 changed or recent paths before the task and the last 6,000 prompt characters. Keyword search keeps only the first 80 distinct terms. The embedding worker receives only the first 2,000 characters of each input. Large path lists or prompt boilerplate can therefore exclude task terms from one or both search methods.

## Evidence

- `commands/knowledge/service.mjs:126`: `const query = `${context.paths.slice(0, 20).join(" ")} ${task || ""} ${prompt.slice(-6000)}`;`
- `commands/knowledge/store.mjs:173`: `const words = [...new Set(String(query).match(/[\p{L}\p{N}_-]{3,}/gu) || [])].slice(0, 80);`
- `commands/knowledge/embeddings.mjs:74`: `texts: texts.map(text => text.slice(0, 2000))`

## Validation and limits

Read the owning source and checked that these knowledge files have no working-tree diff. This establishes the input limits and ordering. It does not establish how often truncation harms real Thunderbird tasks. Three read-only exact-search probes found useful specific Calendar routing evidence, but a broad Calendar accessibility query also returned attachment-list advice. These probes are exploratory, not a quality benchmark. No live coding or review comparison was run.

## Proposed follow-up

Build a compact query from the actual task, affected component, symbols and exact patch paths. Search again when the investigation discovers a new symbol or failure. Compare task outcomes with current retrieval before adopting changes. These actions are proposals, not implemented behavior.
