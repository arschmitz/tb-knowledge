# Missing Content-Disposition does not remove an attached message from the API tree

Entry 873 treats every message/rfc822 part as an attachment before the text-part disposition filter. getAttachmentName guards the optional Content-Disposition header, tries its filename and the Content-Type name, then supplies ForwardedMessage.eml. Current attachment traversal stops at an attached message unless includeNestedAttachments is requested. The new fixture checks the missing-header form, its distinct sub-message ID and its own three attachments. This augments the earlier inline-forwarded-message lesson; it is not a rule that all unnamed text bodies are attachments. Keep contentDisposition as the local parsed-header variable, following the existing naming evidence.

Scope: forwarded-message-missing-disposition.
