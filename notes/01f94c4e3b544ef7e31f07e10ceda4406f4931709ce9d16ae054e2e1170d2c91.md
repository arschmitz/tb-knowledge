# The hosted-account confirmation landing is a UI shell before redirect logic

The owned confirmation widget clones its template, but setState is a TODO returning its argument and resetState is empty. The template contains sample host/user/security strings and warning badges; these do not represent discovery, certificate validation or implemented credential consent. The controller registers the state and hides it with other steps, while actual startup remains autoConfigSubview and no owned transition targets confirmation. Accepted later source fills host/user/scheme labels, captures host, emits manual edit and routes isRedirect through a separate confirmation path. Those later local state contracts are not credited to the UI-only landing or treated as a full transport/privacy audit. The original changed test only checks the existing recommended configuration badge. Three template icon images have no alt attributes; accessible-tree, keyboard, state reset and consent flow were not exercised.

Scope: mail/account-hub/credential-confirmation.
