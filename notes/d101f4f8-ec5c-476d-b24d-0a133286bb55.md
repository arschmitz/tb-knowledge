# Cached Calendar offline replay and UID conflict response transfer

Extends [full synchronization](14b243b1-6109-4ba9-be50-d66b7b09c49c.md), with actual offline storage interface,
provider method targets, and checked assertions. Production JavaScript and public
interfaces; xpcshell fixtures/tests. Every local callback in these methods was read.

`playbackOfflineItems`, 478–609, processes created, modified, then deleted phases.
Each phase snapshots matching cached items into an array, checks offline state,
then pops items from the end and awaits one remote operation at a time.
Remote targets are mUncachedCalendar.addItem, modifyItem(item,null), deleteItem.
Null oldItem asks the provider to overwrite its current version; passing the
offline item as its own old version is not equivalent.

On success, deletion calls cache.deleteItem; other phases call
calIOfflineStorage.resetItemOfflineFlag. Those local success-cleanup promises are
not awaited at 549–565. Ordinary failed remote operations retain the offline flag
for another attempt. Offline is checked per phase, not before every queued item.
There is no explicit user cancellation handle. Reaching the end means remote
operations have settled; it does not guarantee all unawaited local cleanup settled.

Created-item UID_CONFLICT removes the created flag and retains one pending item
per ID in mPendingUidConflicts. `applyPendingUidConflicts`, 618–664, replaces the
pending array before processing. Finds the actual invited attendee and response
on the offline item, then fetches the newly synced server item from cache.
Missing server item is requeued. Missing response/attendee or already equal
response is skipped. A server attendee already answered elsewhere, or a changed
SEQUENCE without `itip.disableRevisionChecks`, wins and discards the local reply.
DTSTAMP is deliberately not compared. Otherwise clones server item and attendee,
changes only participationStatus, and awaits facade.modifyItem. Errors requeue
the offline item. This pending array is in memory, not persistent journal storage
in this file; restart lifetime is a separate unresolved scope.

Direct test links:

- `test_caldav_offline_modify_playback.js:100–163` edits another item online,
  modifies one offline, restores offline state, waits for server/cache recovery,
  and checks both items exist exactly once with the offline flag reset.
- `test_ics_offline_playback.js:340–778` directly covers replay/storage and full
  sync conflict branches. The earlier add-only notes are retained, including
  [cached CalDAV add completion](b42aabdf-857a-47d0-8962-e50581c9929b.md).
- `test_caldav_uidCollision.js:457–527` queues an ACCEPTED item offline while
  the stale cache lacks the server deposit. After refresh, checks acceptance in
  both server and cache, one UID resource, and no client email reply from this
  direct add path. Runs the case with a newer server DTSTAMP too.
- That file's `testOfflineAcceptSecondDepositResync`, 534–599, uses the actual
  iTIP action, reconnects, then cycles offline/online again. Checks accepted
  event still exists, view occurrence query returns both deposits, and acceptance
  remains intact. It directly checks replay result durability across this cycle;
  it does not simulate application restart.

The same test file 254–448 also checks online create-collision recovery across
several server responses, cached/uncached mode, newer sequence, disabled revision
checks, newer DTSTAMP, and already answered server copies. Those tests execute
the invitation recovery path as well as providers; they are not direct evidence
for every branch of applyPendingUidConflicts. The offline tasks explicitly are.
No task here directly verifies every requeue/error/cancel branch. All linked
tests are active in `calendar/test/unit/xpcshell.toml:66,75,112`.
