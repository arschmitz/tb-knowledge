# Verified preference distinction: Calendar view route versus create/edit route

`calendar-item-editing.js` declares `CREATE_EDIT_DIALOG_PREF` as `calendar.event.createEditDialog.enabled`. In `openEventDialog()`, the create/edit branch checks that constant, requires an event, and accepts mode `new` or `modify`. It calls `showCalendarEventCreateEditDialog()`.

The later branch reads `calendar.dialogs.new.enabled`, requires an event, and accepts only mode `view`. It loads `calendar-dialog.mjs` when needed and shows the view dialog. The earlier tab branch has priority over both branches.

`showCalendarEventCreateEditDialog()` dynamically imports the create/edit module, creates or reuses the named dialog, chooses a visible positioning container, sets an edit route from the item's calendar/event/recurrence IDs or clears the route for create, then awaits `dialog.show(event)`. Module loading and showing are separate operations. A name match between the two preferences would hide these conditions.

The general preference source and markup expose `calendar.dialogs.new.enabled`. The inspected browser manifest sets that preference true. This manifest setting alone does not enable or test the production create/edit preference route. The Create Save browser test loads the create/edit fixture directly.

Relationship classes: the two reads and route branches are directly observed; their effect follows from the branch conditions. The manifest-to-pref setup is registration evidence. The direct fixture test executes the create/edit dialog but does not directly assert that toggling the production route preference selects it. A dedicated production-route test link remains unresolved.

Change impact: tab routing, event versus task selection, mode selection, lazy module loading, route identity, dialog reuse, and positioning. Dynamic import rejection and cancellation while showing need their own checks; they are not inferred from an `await` site.
