# Build generated section caches in bounded resumable stages

The fingerprinted current version-change path clears generated sections/search/vectors, loads all record bodies and rebuilds inside one BEGIN IMMEDIATE transaction during store open. The managed record_id index now fixes the earlier old-row table scan; that scan must be described as historical. The remaining rebuild still concentrates generated-cache writes and commit/checkpoint work, and there is no batch cursor or progress/readiness gate in this path. The original cache observation was 1.104 million sections,39.28 GB database and36.26 GB WAL. File length establishes stored work volume, not uncheckpointed bytes or the fraction of elapsed time due to checkpointing. Remaining proposal: use bounded resumable generated-cache stages with progress, an explicit single writer and a consistent readiness/version gate. Keep the prior usable index until a complete replacement can be selected. Skip old-row lookup on known fresh inserts or cleared rebuilds; preserve immutable records, complete ingestion, section citation identity and failure recovery. Do not reduce study depth or change durability settings merely to shorten migration. The inspected evaluation wrapper retains a read transaction until close, but no reader was shown to cause the checkpoint delay. A migration/crash-resume benchmark and checkpoint-progress/transaction-lifetime evidence are still needed; this worker ran no migration or timing test.

Scope: knowledge generated-cache migration.
