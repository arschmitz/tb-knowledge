# Recent comment evidence and additions to the writing guide

This pass adds evidence to the [original guide](81596887-76aa-4804-932a-d01b73042690.md)
and [original coverage report](dcf42054-6e08-4658-b6c1-d45f17f0674a.md). It does not
replace them. Earlier notes, source records, grammar results, and user rules remain
intact. Material older than four years has zero weight in this new pass.

## Source, dates, and weights

The source is the same fixed revision, `87d0159c7149a43253964c2cb6917939557dc799`. The source
working files were unchanged. The cutoff is October 12, 2022 at midnight in
America/New_York. The as-of date is October 12, 2026. Every tracked file receives
an age decision, including exclusions inherited from the original extraction.

Use the comment lines' history, not just a file's latest edit. Read the full
reachable commit history with `--since-as-filter`, then full Git line attribution.
The ordinary history cutoff missed paths because some commit dates are out of
order. The corrected scan includes those paths. Git follows file renames.

For each nonblank comment-block line, use the earlier author and committer date.
This prevents a recent rebase from refreshing an old authored line. Exclude the
whole block if any line predates the cutoff, is a history boundary, or has unknown
attribution. Old delimiters or tags can therefore exclude a partly rewritten
block. This conservative choice prevents old wording from gaining new weight
through a nearby edit.

For eligible text, use `2 ** (-ageYears / 2)`, with age from the oldest line.
A current block has weight 1; two years old has weight 0.5; four years old has
about weight 0.25. Excluded blocks have weight 0. New-file comments gain weight
through their new lines. A recent edit elsewhere in a file does not refresh its
comments. These weights are evidence weights, not votes that automatically set
policy. Copied, migrated, or reformatted text can still have recent dates.

## What the recent evidence supports

The newer source still uses several natural sentence forms. It contains short
labels, instructions, implied-subject summaries, first-person reasons, passive
clauses, long constraints, and imperfect English. Common action verbs include
`use`, `set`, `check`, `create`, `add`, `get`, and `return`. This variety does not
replace the user's chosen present-tense function summaries or simple wording.

Tags, types, examples, tool annotations, and commented-out code affect parser
statistics. Weighted labels are not quality grades. The statistical parser cannot
resolve a pronoun's meaning or verify source behavior. Use checked source context
to choose useful additions, not a frequency threshold or a mandatory word count.

### Name the state a test recreates

The October 10, 2026
[notification-count test](https://github.com/thunderbird/thunderbird-desktop/blob/30cdf5a03b41253e744bc058a699c1947a2b8123/mailnews/base/test/unit/test_notificationCountMultiAccount.js#L49)
uses “Simulate a restart” and then names the account reload. Its code flushes the
folder cache, unloads accounts, checks the reloaded roots, and loads the notification
service afterwards. `GetAllServers` calls `LoadAccounts`, which supports the reload
step. This is a simulation inside a test, not a full application restart. Its
comment weight is about 0.999, so this very recent evidence has more weight than
older eligible examples.

Keep the fixture state and ordering clear. A possible shorter form is: “Simulate
startup counting after the accounts are reloaded.” Keep the following comments
that explain the undiscovered folders and why the service loads afterwards.
Do not collapse the whole setup into “Prepare the test.” No fresh test run is
claimed for this source example.

The related
[folder helper documentation](https://github.com/thunderbird/thunderbird-desktop/blob/30cdf5a03b41253e744bc058a699c1947a2b8123/mailnews/base/src/MailNotificationService.sys.mjs#L103)
names why loading folders matters, and why no flag filter is used. Its body calls
`getFoldersWithFlags(0)`. The checked implementation initializes children and
recurses through them. Its callers still use `confirmShouldCount`. Preserve that
reason rather than documenting only the obvious return type.

### Name the condition that makes a skipped check appropriate

The October 1, 2026
[outgoing-server documentation](https://github.com/thunderbird/thunderbird-desktop/blob/30cdf5a03b41253e744bc058a699c1947a2b8123/rust/protocol_shared/src/outgoing.rs#L415)
names the username, authentication method, and endpoint URL. It then explains why
a missing password is recoverable. The checked function tests those three values;
its initialization caller skips validation for a newly created server and performs
it for a loaded server. The block weight is about 0.990.

Keep the exception next to the check it limits. A shorter explanatory sentence
can say: “A missing password does not prevent this check from succeeding. The
password prompt can recover from that case.” Do not turn this local exception
into permission to skip password checks throughout Thunderbird.

### Name the value and its lifetime in a safety explanation

The September 1, 2026
[SAFETY comment](https://github.com/thunderbird/thunderbird-desktop/blob/30cdf5a03b41253e744bc058a699c1947a2b8123/rust/protocol_shared/src/outgoing.rs#L534)
names `pref_name`, `value`, and `GetCharPref`, and states that both values remain
alive until the call returns. The adjacent code creates the two values before
passing their pointers. Its weight is about 0.963.

Preserve those names and the end of the required lifetime. A shorter form is:
“SAFETY: `pref_name` and `value` remain allocated and alive until `GetCharPref`
returns.” This explains a concrete lifetime condition. It does not certify every
other requirement of the unsafe call or require unrelated comments to use this
label. No Rust build or complete safety proof is claimed.

### Name the result a workaround must preserve

The March 24, 2026
[password-wrapper comment](https://github.com/thunderbird/thunderbird-desktop/blob/30cdf5a03b41253e744bc058a699c1947a2b8123/rust/protocol_shared/src/outgoing.rs#L853)
explains why `xpcom_method!` is not used. The custom implementation preserves
`NS_MSG_PASSWORD_PROMPT_CANCELLED` when no password is returned. The checked macro
success branches return `NS_OK`. The comment weight is about 0.826.

Suggested wording: “Do not use `xpcom_method!` here. If the user cancels, preserve
`NS_MSG_PASSWORD_PROMPT_CANCELLED`. The macro returns `NS_OK` for successful
results and would lose the cancellation status.” Keep the exact status names.
An extra explanation of the wrapper may help a new reader; a generic claim such
as “ensures correct error handling” would lose the reason.

### Keep grammar and completion accurate even in newer text

The July 2026
[input helper](https://github.com/thunderbird/thunderbird-desktop/blob/30cdf5a03b41253e744bc058a699c1947a2b8123/mail/components/accountcreation/test/browser/browser_accountHubEmailManualConfigForm.js#L1448)
still says “Sets value of input and fires event supplied in parameter.” Its weight
is about 0.925. Recency does not make missing articles clearer. The earlier
suggestion still fits: “Sets `input.value` to `value`. Dispatches an event named
`eventName`.” The checked body registers and awaits `config-updated`. When callers
need completion documented, add: “Resolves after the `config-updated` event.”
This preserves actions, names, and async completion without invented guarantees.

The August 2026
[alarm-offset documentation](https://github.com/thunderbird/thunderbird-desktop/blob/30cdf5a03b41253e744bc058a699c1947a2b8123/calendar/base/modules/utils/calAlarmUtils.sys.mjs#L20)
uses an imperative “Get…” summary and states a negative-duration expectation.
Its weight is about 0.956. The chosen writing rule still favors “Returns…” for a
function summary. Recent source is evidence of a form, not authority to override
that deliberate rule. The adjacent fallback comment can be clearer as:
“If the alarm unit is invalid, use minutes.” The body checks the unit and applies
that fallback; it does not validate every alarm preference.

## Additions supplied to consumers

The concise instructions now add these practical checks:

- When explaining safety, name the value and how long it remains valid.
- If a check is skipped, name the condition that makes the check unnecessary.
- For a workaround, name the result that would change without it.
- For test setup, name the state the test recreates and any simulated action.

These add detail to the original reason, constraint, and caller-contract guidance.
They do not create a new comment-coverage requirement. The prior “should” rule
for assertion messages remains in effect. Newer tests with other message forms do
not override that user instruction. Normal reviews still must not report harmless
wording alternatives as defects.

date range, and weight was checked against independent metadata from 171,670

exactly on four checked source files. Fourteen source locations were checked

The instruction-delivery test passed. Shared AGENTS.md, local Codex guidance, and
the console's `COMMENT_WRITING_GUIDANCE` contain the additions. The current chat
received refreshed instructions. A running backend or another existing chat can
need a reload. No live model-adherence claim is made. Raw corpus, dates, occurrence
weights, full aggregates, and checkpoints remain private; the practical guide and
coverage are shared through the normal publication path.

The original extraction limits remain. Ownership markers need context checks.
Git dates do not prove fresh authorship, and old content copied into a recent file
can appear recent. Whole-block eligibility can omit useful new sentences in a
mixed-age block. Statistical parses include tags, labels, code, and machine text,
so a label count is not a prose-quality measure. No full manual meaning review of
every comment, Thunderbird runtime test, or new English-parser evaluation is
claimed. Those limits apply to this added layer; they do not remove the original
study or weaken explicit user instructions.
