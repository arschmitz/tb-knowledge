# Notification preference telemetry uses state instead of a repeated fetch event

The review questions repeated update events because their frequency would add timing information beyond the requested count of users with default versus modified settings. The accepted implementation sets a labeled Boolean on initialization and later URL preference changes. Its URL value is !prefHasUserValue, so it describes preference provenance rather than successful display or whether notifications are enabled. The module-level lazy getter is placed after the object following a reported temporal-dead-zone failure. This is the scoped notification metric design and historical rationale; no telemetry or module-load test ran here.

Scope: In-app notification telemetry.
