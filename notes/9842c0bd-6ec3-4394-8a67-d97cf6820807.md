# Native mail copy requests retain callbacks and serialize by destination

`MailServices.copy` resolves the message-copy component; its registration selects `nsMsgCopyService`. `CopyMessages()` validates source, destination, and each header. Equal source/destination returns failure. Empty messages synchronously call `onStartCopy()` and `onStopCopy(NS_OK)` without creating a request. This explains why an empty post-filter batch can still call the archiver's completion handler.

For real work it creates `nsCopyRequest`, copies the header array, groups headers by their actual owning folder, and adds strong references to headers and folders. The request retains the listener, window, and optional transaction manager. It requests undo support and opens a transaction batch only when multiple source groups exist. Constructor defaults, file-copy flags/keywords, and folder-copy destination leaf names are separate request state. File-message replacement retains the old header for metadata recovery; this service does not remove that old message itself.

`QueueRequest()` appends the request. An existing request for the same destination blocks immediate message/file copying; folder copying also compares destination leaf name. `DoNextCopy()` walks the queue in order while skipping destinations already active. Thus the queue is ordered by destination conflicts; requests targeting different folders may overlap when new calls trigger the driver. The broad IDL statement that each operation executes in sequence must not be read as a single global native lock.

The driver marks source groups processed and calls the actual destination folder's `CopyMessages`, `CopyFolder`, or `CopyFileMessage`. Those are dynamic protocol targets; the service body does not itself implement storage or network transfer. A cross-server folder move keeps the requested move for the actual call but changes the notification bookkeeping flag to copy. Folder completion can happen synchronously and delete the request before `CopyFolder()` returns, so failure cleanup checks queue membership before touching that request again.

The folder calls `NotifyCompletion()` with source support and actual destination. `FindRequest()` matches object identity and ignores requests already being removed. Folder copying can match the arrived child's parent. Once sources are processed or a failure arrives, `ClearRequest()` sends successful folder move/copy notifications, closes a multi-source undo batch, marks pending removal, calls `onStopCopy` before removing the request, then deletes it. That order lets a callback retrieve the arrived folder and queue another operation safely. Completion scanning tracks the original queue length so a new request from that callback is not mistaken for the completed one.

The destructor suppresses callbacks by clearing each listener before failing/removing outstanding requests. Native service shutdown therefore does not promise a final callback to every JS consumer. There is no cancel-request method in this interface. Actual folder error paths must be traced separately; the source shown here does not prove every thrown or immediate folder failure sends completion.

Direct archive tests check the resulting folders and source/destination counts. They execute this service but do not directly assert queue conflicts, shutdown callback suppression, cross-server bookkeeping, or callback-triggered reentrancy. Those are static native facts here; no native test run is claimed.
