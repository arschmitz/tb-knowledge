# CalTransactionManager history, permission checks, and failure boundaries

Scope: production JavaScript in privileged Calendar modules and application scripts.
All local function and method bodies in `CalTransactionManager.sys.mjs` were read.
This closes the earlier partial read of that file. Provider and scheduling internals
remain separate scopes.

| Function or group | Reads, action, result, and failure behavior |
| --- | --- |
| `getInstance`, lines 71–76 | A module variable owns one manager. A direct `new CalTransactionManager()` creates separate history. |
| `commit`, 97–108 | Pushes the exact transaction before starting its operation. Awaits and returns the operation result. On rejection, finds and removes that object wherever it now sits, then rethrows the same error. It does not run an inverse operation. |
| `beginBatch`, 117–121 | Pushes a new empty batch and returns it. It does not execute a child operation or wait for a group to finish. |
| `peekUndoStack`, `peekRedoStack`, 129–131 and 167–169 | Read the last entry. An empty array produces `undefined`. |
| `canUndo`, `canRedo`, 156–159 and 194–197 | Return a Boolean from the top entry's current `canWrite()` result. They do not scan lower history entries. |
| `undo`, 138–148 | An empty stack rejects with `NS_ERROR_FAILURE`. Otherwise, moves the entry to redo history before returning its inverse promise. No catch restores the old history if that inverse fails. |
| `redo`, 176–186 | The same empty-stack check; moves the entry to undo history before running its forward operation. It does not use `commit()`'s failure-removal catch. |
| `CalTransaction`, 211–223 | The base permission result is false. The two async base operations are empty and resolve with `undefined`. Concrete classes override them. |
| `CalBaseTransaction`, 313–330 | Stores live item, calendar, old item, and response objects by reference. `_dispatch()` calls `cal.itip.checkAndSend()` synchronously. `canWrite()` checks the new item, and checks the old item too for a modify transaction. |
| `itemWritable`, 437–444 | Requires an item and its calendar, calendar writability, and calendar permission to add items. It is not a per-item permission check for every kind of operation. |

`calACLUtils.sys.mjs:21–29` checks disabled/read-only state and offline access.
Cached calendars or a calendar explicitly reporting `requiresNetwork === false`
can remain writable offline. `userCanAddItemsToCalendar`, 38–43, allows absence of
an access-control entry, absence of access control, ownership, or explicit add
permission. The file also has separate delete, modify, and invitation-response
checks; transaction history does not substitute for those checks at Save.

Observed limits in the body: a new commit does not clear `redoStack`; the manager
has no busy flag, operation queue, cancellation token, history-size limit, or
shutdown release method. A transaction is retained by a stack until callers
replace/remove that stack entry or the manager becomes unreachable. These are
source facts, not evidence of a user-visible failure in all callers.

Actual consumers: `calendar-command-controller.js:633–638,671–675` calls the host
permission checks and undo/redo wrappers for `cmd_undo` and `cmd_redo`.
`calendar-item-editing.js:794–808` starts undo/redo without awaiting them and
updates the menu immediately. Its `doTransaction`, 755–788, awaits commit before
calling the completion observer and updating commands when no batch is active.
Changing the manager's completion timing affects that observer, command state,
Save completion, and provider observers.

Direct test checks: `testCalTransactionManager`, `testBatchTransaction`, and
`testSequentialBatchTransactions` check history positions, writability, and call
counts. `testFailedCommitsLeaveOtherTransactions`, 434–473, deliberately finishes
a later transaction before the earlier one rejects and verifies that only the
failed object is removed, in both manager and batch ownership. The tests read
here do not directly check failing undo/redo, new-commit redo invalidation,
history growth, or every overlap with an in-flight undo.

Correction to the provisional [failed-commit summary](bce63e86e5ab9effc23e7838a53be307147d01e7ddac020de0f6401009802637.md):
the manager removes from `undoStack`; a batch removes from its own `transactions`
array. The shared claim that neither automatically invokes `undoTransaction()`
is confirmed at this revision.
