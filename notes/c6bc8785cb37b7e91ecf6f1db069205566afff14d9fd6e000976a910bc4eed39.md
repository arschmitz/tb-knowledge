# Trace nested calls before moving an IMAP lock boundary

The historical CanHandleUrl fix moved DeathSignalReceived ahead of the nonrecursive mLock acquisition. Current CanHandleUrl retains that order but later uses a reentrant monitor, and its IsBusy call can reach IsUrlInProgress under that same monitor. Recommend checking the caller/callee lock graph and the current lock type when changing this path. Do not project the old mutex deadlock risk onto the later monitor without tracing it. This is static source and test-code inspection. Complete Bugzilla and historical review timeline/inline context remain pending. No Thunderbird runtime, build, lint or live accessibility validation ran.

Scope: mailnews/imap/src.
