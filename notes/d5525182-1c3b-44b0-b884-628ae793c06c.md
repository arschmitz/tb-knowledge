# Memory Calendar item ownership, modification checks, and deletion results

Scope: production privileged JavaScript; memory provider factory; xpcshell tests.
Every local body in `CalMemoryCalendar.sys.mjs` was read. The provider inherits
`cal.provider.BaseClass`; its actual methods are not generic Array or DOM APIs.

`components.conf` registers `@mozilla.org/calendar/calendar;1?type=memory` with
constructor `CalMemoryCalendar`. `moz.build` packages the module and component
manifest. The class declares calendar, scheduling, offline-storage, synchronous
metadata-write, and provider interfaces, lines 16–33.

The constructor and `initMemoryCalendar`, 11–14,40–45, create strong observer
storage, item and offline-flag objects, and a metadata Map. `getProperty`, 82–93,
reports no network requirement and no support for another cache, supports
priority, and allows deletion. Scheduling support returns this provider.
`relaxedMode`, 73–78, caches the first property result; later property changes
do not invalidate that field in this file.

| Operation | Storage, notifications, result, and failure |
| --- | --- |
| `addItem`, 109–112 | Clones the caller's item, then adopts the clone. |
| `adoptItem`, 115–170 | Rejects read-only calendars. Generates an ID only for a mutable item without an ID. Missing ID on an immutable item reports an operation error and rejects. The duplicate-ID guard at 140–154 is commented out. A duplicate ID can replace the stored value. For an occurrence, clones its parent and installs the exception. Sets the parent calendar to `superCalendar`, makes the parent immutable, stores by ID, notifies `onAddItem` with the supplied item, and resolves with that item. |
| `modifyItem`, 173–270 | Clones the new parent and updates its recurrence exception if needed. If oldItem is absent, uses the stored item. Relaxed mode permits a missing stored old item and avoids content/generation checks. Ordinary mode requires a stored item, equal IDs, matching normalized old content, and matching generation. If old and new generations are equal, increments the new generation. Stores the immutable parent, reports operation completion, then notifies `onModifyItem`, and resolves with that parent. |
| `deleteItem`, 273–310 | Read-only and null-ID cases report an error and reject. Ordinary mode reads stored generation and compares it with the caller's generation; it does not compare all old content. A missing stored item can throw when reading generation. Deletes the item and metadata, reports completion, then sends `onDeleteItem` with the old item. Resolves with `null`, despite the public Promise<void> comment. |
| `getItem`, 313–315 | Resolves with the stored parent reference, or null. It does not clone on read. |
| `deleteCalendar`, 59–63 | Clears item and metadata storage through `wrappedJSObject`. Does not clear the offline flags or observers here. Resolves with undefined. |

Notifications happen in these async methods before the returned promise settles.
Listeners therefore can see storage changes before an awaiting transaction
continues. Parent immutability protects item mutation; it does not release the
calendar reference or observer set. `detectCalendars`, 65–70, throws an explicit
not-implemented exception.

Actual consumer: `CalTransactionManager.sys.mjs:337–347,365–402,420–430` awaits
provider mutations before scheduling dispatch. It retains provider add/modify
results. The checked transaction storage and recovery record is
[the existing transaction analysis](94a7ba97-8135-4e4f-98d0-054f2adcbd26.md).
Changing provider completion or observer order can affect transaction history,
Save completion, and listeners that update views.

Direct test checks: active `test_providers.js:125–272` checks event/task fixtures,
getItem and query counts with selected item properties; 274–337 checks metadata
set/read/delete/enumeration. Comparison helpers omit some item properties, so
this is not a complete serialization equality assertion. Basic transaction
add/modify/delete and reversal use a real memory provider in
`test_transaction_manager.js`. Its `test_modifyMemoryItemsStartsBeforeYield`
directly checks synchronous mutation/notification before the caller yields.
No direct test of every read-only, duplicate-ID, relaxed-mode invalidation, or
missing-item delete branch was established by these test files.
