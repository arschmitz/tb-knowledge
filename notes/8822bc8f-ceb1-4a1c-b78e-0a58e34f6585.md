# Storage metadata replacement deletes first and reports some failures only through logging

## Directly observed sequence and state

The public `setMetaData` calls `deleteMetaDataById`, then `addMetaData` synchronously.
Deletion binds calendar and item ID, executes one step, and resets the statement
in the database helper. That helper rethrows execution failure. Insertion binds
calendar/item/value, executes a step, catches failures for logging, and resets the
statement. There is no outer transaction around replacement in these bodies.
If deletion succeeds and insertion fails, the old value is not restored here.

The insertion catch's comments and the actual branches differ in wording about
`NS_ERROR_ILLEGAL_VALUE`; the behavior is still that either branch logs and does
not rethrow. No acceptance of an unsupported value is inferred from a caught
error. The SQL INSERT writes `cal_id`, `item_id`, and `value`.

`getMetaData` returns the first matching value or null, catching/logging read
errors and always resetting. `getAllMetaDataIds` and `getAllMetaDataValues` each
call a separate synchronous scan of the same select statement. The scan collects
one requested column and resets; these separate calls are not a shared snapshot
or a guaranteed pair if metadata changes between them. No explicit SQL ordering
contract appears in the selected query.

## Consumers, tests and limits

`CalStorageCalendar` is the actual metadata model owner and exposes these methods
through its sync-write calendar interface. Item-model deletion can include or
preserve metadata according to `keepMeta`; therefore a mutation failure can
leave item and metadata state different. Changes affect cache/provider metadata
consumers, but every remote caller was not enumerated in this record.

Whole metadata/helper/SQL bodies were read before the pilot and reused. No direct
metadata insertion-failure test or atomic replacement test was identified in this
slice, and no such failure was run. Basic storage test execution is not promoted
to direct verification of those failures. Exact paths and paired source revisions
make these narrow claims independently checkable. This note adds body contracts;
it does not make automated structural records behavioral proof.
