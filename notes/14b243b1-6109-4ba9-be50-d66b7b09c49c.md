# Cached Calendar full synchronization, conflict decisions, and pending promise state

Production privileged JavaScript. `synchronize`, 275–279, starts `_doSynchronize`
only when mPendingSync is falsey and saves its catch(console.error) promise.
The returned promise resolves with undefined on ordinary success and after the
outer catch logs a rejection. Callers cannot use rejection alone to detect all
sync failures. No cancellation token or finally-based pending cleanup appears.

Early disabled/offline exits at 286–294 clear pending before returning. Because
the outer assignment happens after the async call returns, the saved promise can
remain set after an early exit. A controlled exact-source mock confirmed disabled
sync followed by enabled sync started no second operation. This is local control
flow evidence; application impact depends on callers clearing/changing state.

Change-log sync, 296–326, waits for replayChangesOn's actual listener to report
no operation or a non-pending operation. Reads status, clears mPendingSync,
rejects on failure, resolves on success, then awaits pending UID recovery.
Pending is cleared before that last recovery completes. The listener's operation
and status are dynamic provider values, not an assumed Promise result.

Full sync, 329–444, reads offline-created/modified/deleted items into snapshots,
awaits cache wipe/setup, and compares the exact cached calendar object with its
saved reference to stop if unregister changed it. Starts a cache batch; consumes
all server stream chunks; stores lastModifiedTime by ID; starts cache additions;
awaits every addition with Promise.allSettled; logs individual rejected additions;
then ends the batch. One refused addition does not abort other additions.

On server stream failure, ends the batch, awaits playback, sends cached onLoad,
clears pending, and rethrows; synchronize's outer catch then logs it. If another
await throws before an explicit clearPending call, this file has no finally that
guarantees clearing. This is an observed control-flow limit.

Restoration at 380–438 processes each offline snapshot with a separate catch.
Created items are cloned and adopted offline. Modified items compare local and
server lastModifiedTime: a newer server prompts; otherwise overwrite cached
item with null old version. If the server deleted an edited item, asks whether
to add it again. Deleted items still on the server prompt if server is newer,
otherwise mark deleted. Server-absent deleted items need no new action.
Then replaces snapshot dictionaries, awaits playback and pending UID recovery,
and clears pending. Failures can be logged per item; dictionary replacement is
not evidence that every saved change succeeded.

`promptOverwrite`, 458–473, calls the actual provider modal prompt, then marks
modified or deleted only when accepted. Prompt false leaves the fetched server
copy in cache. The provider UI and localization consumers have a separate record.

Direct assertions read in `test_ics_offline_playback.js`:

- 340–499: offline modify/create/delete reaches server; bystanders remain once;
  added server item survives; unnecessary prompts are absent.
- 500–626: accept/decline edit and delete conflicts against newer server copies.
- 627–690: accept re-add or decline when server deleted an offline edit.
- 691–736: one refused cache refill item does not lose other server or offline items.
- 737–778: earlier online add callback does not replay for a later offline add.

Tests replace promptOverwrite with a controlled answer and record calls. These
are direct conflict-decision/storage checks, but execute without testing the
modal window, preview markup, or Fluent rendering. Server fixtures, offline flag
restoration, onLoad waits, and settled-state checks were read. No passing run is
implied by the file or manifest entry.
