# EWS sync deduplicates message fetches while preserving change delivery order

The operation fetches each create/update ID once and indexes the latest message payload. It then walks the original change list for callback delivery. The source expects server chronological order; a HashMap or HashSet traversal is not the callback sequence. The batch token is persisted after the change callbacks. A later callback error can follow earlier local changes, and the native failure path retains accumulated new messages. This is sequencing evidence, not a transaction or recovery guarantee. No synchronization or test ran.

Scope: EWS message synchronization batch state.
