# Test rejected deletion during a CalDAV UID change at the same href

Current addTargetCalendarItem handles a new UID at an existing href by calling async deleteTargetCalendarItem inside a try without await. That async deletion awaits storage lookup and deletion, so this local catch does not observe a rejected promise and the add can proceed before deletion finishes. Proposed focused test: reject or delay the deletion and verify error reporting plus href/cache/item ordering. This is a static async-boundary concern, not an executed failure or completed fix.
