# Cached Calendar modify and delete completion, offline fallback, and error boundaries

Scope: facade modify/delete bodies and the actual provider callback bridges.
This adds missing coverage beyond the checked cached-add notes. It does not
claim all ICS/CalDAV network provider bodies have been analyzed.

`modifyItem`, 868–877, wraps doModifyItem in a promise. Failed completion status
rejects with Components.Exception; successful status resolves with detail.
`doModifyItem`, 888–970, returns no operation promise. Offline mutation updates
cache then offline journal, resolving its callback with the modified item.
Online first reads the actual cache offline flag. Created/modified journal items
stay on the offline path. Otherwise installs
`mUncachedCalendar.wrappedJSObject._cachedModifyItemCallback` and calls remote
modifyItem(newItem,oldItem).

The installed async callback awaits cached modify on successful remote status,
or awaits offline modification on unavailable-network status. It forwards other
status errors. This ordering makes cache onModifyItem occur before the provider
ends its batch. Provider hooks at `CalDavCalendar.sys.mjs:698–735` and
`CalICSCalendar.sys.mjs:181–221` read and clear that actual field and pass/await
the callback according to their bodies. Matching names were not used as proof.

Remote promise rejection also calls the same callback. Unlike the checked add
path, modify has no callbackRan guard in this body. A provider invoking an error
callback and then rejecting can invoke completion twice; an exact-source mock
observed two calls. Promise settlement itself accepts only the first result;
callback side effects can still run again. No universal UI defect is inferred.
The flag-read `.then` at 943 has no rejection callback. If flag lookup rejects,
doModifyItem has no local route that settles its wrapper promise. The error helper
also assumes non-null oldItem for calendar and ID, despite overwrite callers
passing null. Effects require the specific rejecting path and receiver.

`modifyOfflineItem`, 979–985, awaits cache.modifyItem and then
calIOfflineStorage.modifyOfflineItem, returning the modified item.
`deleteItem`, 987–1033, handles offline or created/modified journal items by
marking deleted. Otherwise awaits remote deletion, cache deletion, and attempts
synchronous metadata removal. Metadata interface/error failures are logged as
unsupported and ignored.

The enclosing delete catch only handles network-unavailable codes. Other remote
or cached-delete errors leave the catch without rethrowing. That facade promise
therefore resolves undefined in that branch. An exact-source mock with a generic
failure confirmed this. `isUnavailableCode`, 24–43, means a failed NETWORK-module
result or NS_ERROR_NOT_AVAILABLE, not every error. A transaction that awaits a
resolved facade delete can continue to scheduling dispatch; this is a supported
possible effect from the caller, not proof every failed delete triggers it.
`deleteOfflineItem`, 1035–1037, delegates to actual calIOfflineStorage.

Actual consumers: transaction bodies at
`CalTransactionManager.sys.mjs:337–347,365–414,420–430`. Their completion and move
recovery contracts depend on mutation promises. Direct tests include CalDAV
offline modify replay and ICS offline modify/delete conflict and retry tasks.
Those tests establish their scenario's server/cache assertions; they do not
directly test generic error swallowing, duplicate error callback, rejected flag
lookup, or null-oldItem failure. The controlled experiments are separate from
product test results.
