# Mail folder notifications retain listeners and route selected flags

`MailServices.mfn` is the lazy `nsIMsgFolderNotificationService`. Each registration stores a strong `nsIMsgFolderListener` and its notification flags in `nsTObserverArray`. Adding the same listener twice does not create a second entry because equality uses only listener identity; the new call does not update flags on the existing entry. Removal matches the listener object and releases that entry. `hasListeners` reports whether this array is non-empty.

All notification methods iterate registered entries and call the matching interface method only when its flag is selected. The macro ignores callback return codes and still returns `NS_OK`. It uses Firefox's `nsTObserverArray::ForwardIterator`; its mutation details were not re-read in this slice, so additions/removals during a callback are not described as a snapshot or a complete mutation contract.

`NotifyMsgsMoveCopyCompleted()` has an extra read: for a move with listeners and source headers, it checks the first source folder's actual IMAP interface and its server delete model. If the model marks messages deleted without removing their database rows, listeners receive `aMove=false`. Other notification methods forward their inputs. The listener IDL distinguishes added, classified, deleted, moved/copied, key replacement, folder changes, and compaction/reindex timing; a similarly named `nsIFolderListener` is a different interface and is not merged with it here.

The archiver registers for `folderAdded` after preparing batches and removes itself in `processNextBatch()` at finish. However, its checked prototype defines no `folderAdded` handler, and its generated `QueryInterface` names only copy-service and operation listeners. The source registration site therefore does not prove an implemented folderAdded consumer. Actual JS-to-XPCOM conversion and callback behavior for this object remain unresolved; the controlled VM probe deliberately substitutes that conversion and cannot verify it.

The native copy service sends folder move/copy notifications in successful request cleanup. Message move/copy notifications are the destination/source folder code's responsibility. Changing notification flags or semantics can affect consumers independently of a final `onStopCopy` callback.

Full service/header/interface bodies were read. The separate native-mail-test-links record now checks the full basic/local notification tests and their shared assertion helper. No passing-test evidence is claimed here.
