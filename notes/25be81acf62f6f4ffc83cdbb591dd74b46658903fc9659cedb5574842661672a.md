# Test dotted explicit tag keys at the preference observer boundary

Proposed test for messages.tags: create, update and delete a supplied key containing a dot. The current observer splits the preference name on dots and takes fixed positions for key and property, while addTagForKey lowercases and uses the supplied key to build preference names. A dotted key may therefore take a different observer path. This is a conditional static concern, not a reproduced missed event or an approved restriction on keys. Check the schema and native contract before changing accepted key syntax. Complete Bugzilla and historical Phabricator timeline/inline discussion remains pending.

Scope: mail / components.
