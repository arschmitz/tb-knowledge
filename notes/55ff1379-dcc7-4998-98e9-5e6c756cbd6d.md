# Cached Calendar construction, forwarding, observers, and refresh lifetime

Scope: the cached production calendar facade. A facade is an object that forwards
part of an interface to another object. All local bodies in
`CalCachedCalendar.sys.mjs` were read; the forwarding targets were checked.
Existing checked add records are reused rather than replaced.

Construction at 111–125 retains the uncached provider, sets its superCalendar to
the facade, and registers a new uncached observer helper that retains the facade.
The helper handle is not saved in a field. Creates a strong facade ObserverSet,
calls async `setupCachedCalendar` without await, and immediately assigns the
cached calendar as uncached offlineStorage when change-log support exists.
The first setup branch is deliberately synchronous before return.

`setupCachedCalendar`, 164–223, reads `calendar.cache.type`, default storage,
and uses the matching actual calendar component factory. Memory resets the
provider log when supported. Storage uses `cache.sqlite` under calendar-data
with the facade ID. Other types throw inside a catch that logs and resolves.
The backing calendar gets transient properties, forwarded disabled state,
relaxedMode=true, superCalendar=facade, and the saved cached observer helper.
A later setup awaits deleteCalendar and resets a supported change log.

`calCachedCalendarObserverHelper`, 46–108, forwards start/end batch from both
sources; forwards item changes only from the cache; forwards property changes
only from the uncached provider; forwards errors from both. Cached onLoad
notifies facade observers. Uncached onLoad first awaits synchronize, then notifies.
`cal.data.ListenerSet.notify`, 42–50, does not await callback promises, so an
upstream notification does not itself wait for that async onLoad body.

Forwarding at 1041–1078 targets the cache for `getItem`, `getItems`,
`getItemsAsArray`, `startBatch`, `endBatch`, and uncached provider for calendar
identity/configuration attributes. `getProperty`, 699–708, forces cache.enabled
true for an uncached provider's cache.always property, and otherwise delegates
to the uncached provider. `setProperty`, 710–717,
also forwards disabled state to backing cache. Scheduling QueryInterface checks
the actual uncached interface, and scheduling-support accessors delegate to it.
The receiver and target are established here, not by matching names.

`refresh`, 719–728, awaits offline playback first for online change-log providers,
then downstreamRefresh. `downstreamRefresh`, 730–738, calls uncached refresh
without await when allowed; otherwise awaits synchronize then invokes cached
onLoad. Offline and non-change-log refresh branches do not await downstreamRefresh.
Therefore awaiting
the facade's refresh does not establish that server sync and observer processing
are complete. Tests wait for onLoad and/or server/cache state separately.

Offline transitions reach wrappers from
`CalCalendarManager.sys.mjs:139–156,1084–1091` via the offline observer and
`onOfflineStatusChanged`. `onCalendarUnregistering`, 148–161, removes the saved
cached observer, starts deleteCalendar, clears the pointer only on successful
completion, and logs rejection. Returns before that deletion completes.
It does not remove the uncached helper here. Manager 442–448 calls it only when
clearing cache during unregister. Strong references and no local removal are
observed; a persistent leak is not established without all owners and shutdown.

Direct assertion link: `test_caldav_uidCollision.js:179–188,457–507` awaits refresh
then waits for acceptance in both server resource and cache; checks one server
event. `test_ics_offline_playback.js` helpers wait for onLoad, mPendingSync and
the ICS lock before checks. These tests explicitly rely on refresh returning
before all work completes. Setup observer removal and test cleanup are checked
in those helpers. No universal shutdown or unregister-during-sync test was
established by the cited tests.
