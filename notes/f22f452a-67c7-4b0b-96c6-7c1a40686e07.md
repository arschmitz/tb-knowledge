# Calendar storage sharing and native close completion use different lifetime layers

## Creation, ownership and release

`openConnectionTo` keys a module-level map by database file path. It opens a native
connection once and increments `useCount` for later wrappers using that path.
`CalStorageDatabase.connect` maps `moz-storage-calendar` to `local.sqlite` or uses
an explicit file URI. `closeConnection` decrements use count. At its final use,
or for forced shutdown, it calls native `asyncClose` and deletes the map entry
immediately. Its promise resolves from the native completion callback.
Evidence: [calendar/providers/storage/CalStorageDatabase.sys.mjs:17–73](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageDatabase.sys.mjs#L17-L73) and [calendar/providers/storage/CalStorageDatabase.sys.mjs:127–144](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageDatabase.sys.mjs#L127-L144).

`CalStorageDatabase.close` calls `closeConnection`, clears `db`, and returns
`undefined`. It does not return that promise. Its actual caller,
`CalStorageCalendar.shutdownDB`, awaits `close()` and then clears `mStorageDb`.
That await does not wait for native close completion. The module's
`profileBeforeChange` blocker waits only for promises for connections still in
the map when the blocker runs. Evidence: [calendar/providers/storage/CalStorageDatabase.sys.mjs:357–360](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageDatabase.sys.mjs#L357-L360),
[calendar/providers/storage/CalStorageCalendar.sys.mjs:522–531](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCalendar.sys.mjs#L522-L531), and [calendar/providers/storage/CalStorageDatabase.sys.mjs:65–73](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageDatabase.sys.mjs#L65-L73).

The Calendar observer registered after database upgrade responds to
`profile-change-teardown` by removing itself and finalizing statements. It leaves
database closing to the module's later blocker.
Evidence: [calendar/providers/storage/CalStorageCalendar.sys.mjs:157–174](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCalendar.sys.mjs#L157-L174).

## Firefox boundary and shutdown limit

Native `Connection::AsyncClose` marks closed state before dispatching an
`AsyncCloseConnection` runnable. That runnable strongly owns the connection and
completion event. It closes SQLite on the helper thread and dispatches completion
to the main thread; its final release also goes to the main thread.
Evidence: [storage/mozStorageConnection.cpp:365–407](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageConnection.cpp#L365-L407) and
[storage/mozStorageConnection.cpp:1968–2078](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageConnection.cpp#L1968-L2078).

The storage service maintains its own connection list. On
`xpcom-shutdown-threads`, it removes observers and spins an event loop until no
registered connection reports `isClosing()`. `isClosing()` is the native
shutting-down flag with the closed flag still false. This is a later native
safeguard separate from Calendar's promise. `internalClose` sets the closed flag
before calling `sqlite3_close`, so the flag wait alone does not prove that all
physical close work or completion callbacks have finished. Thread shutdown is a
separate queued action.
Evidence: [storage/mozStorageConnection.cpp:1651–1736](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageConnection.cpp#L1651-L1736).
Evidence: [storage/mozStorageService.cpp:657–687](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageService.cpp#L657-L687) and
[storage/mozStorageConnection.cpp:1634–1657](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageConnection.cpp#L1634-L1657).

The saved mocked probe directly shows the wrapper and its mocked blocker can
settle while a mocked native close remains pending. It does not show that real
Gecko finishes application shutdown before closing SQLite. The native service
wait is why that broader claim would be unsupported. Callback dispatch success,
full shutdown phase ordering, and all fallback close branches remain separate
runtime questions.

## Test relationships and observed results

and database paths for shared and separate calendars. They cover pooling, not
whether `close()` returns native completion.
Evidence: [calendar/test/unit/test_storage_connection.js:12–126](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/test/unit/test_storage_connection.js#L12-L126).
