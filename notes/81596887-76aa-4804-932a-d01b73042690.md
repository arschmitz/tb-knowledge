# Write comments in a clear human voice

This guide applies to new and changed first-party Thunderbird comments. It is a
deliberate response to the user's writing requirements. Source examples support
practical choices; they do not make every old comment a rule. The full study is
still in progress. Do not describe this guide as a completed exhaustive study.

## Rules and suggestions

The user's requirements govern: use simple English, short sentences, common
words, active voice, and concrete actions. Keep necessary details and exact code
names. Explain terms for new developers. Use ASD-STE100 as a guide, not a reason
to replace an exact identifier or to claim formal compliance.

Check the implementation and relevant callers. State what the code does. Do not
invent a purpose, workflow, effect, or guarantee. Preserve legal notices and tool
directives. Keep unrelated existing comments intact.

The sentence forms below are suggestions. Choose the form that explains the
behavior clearly. They are not lint rules. There is no mandatory word count,
required stock opening, ban on all passive sentences, or reason to remove the
writer's voice. Follow the affected component's required documentation coverage.
The source `.agents/skills/jsdoc-rules.md` requires JSDoc for specific public and
non-trivial functions, while the parent repository asks for few comments. Use
the Thunderbird rules within `comm`; skip routine code as those rules specify.

## Sentence structure and phrasing

**Begin with the action.** A function summary can use the function as its implied
subject: “Returns…”, “Sets…”, or “Removes…”. This is natural API wording, not an
instruction for the reader. An instruction uses a base verb: “Use…” or “Do
not…”. Existing comments use both forms. Keep their distinct meanings.

In `mailnews/mime/src/mimei.cpp:1168`, the summary starts:

> Returns a string describing the location of the part (like "2.5.3").

The next sentence limits that result: “This is not a full URL, just a
part-number.” The concrete example and following constraint help a reader use
the result. Do not flatten both into a vague “Handles part locations.”

**Name the subject and object.** Write who does what to which value. Include an
article when a normal English noun needs one. Keep names for objects that the
reader can find in the code.

Before, `mail/components/accountcreation/test/browser/browser_accountHubEmailManualConfigForm.js:1448`:

> Sets value of input and fires event supplied in parameter.

Suggested wording: “Sets `input.value` to `value`. Dispatches an event named
`eventName`.” This keeps the two documented actions and restores clear targets.
The body also waits for `config-updated`; document that completion condition
when callers need to know when the returned promise resolves. Do not pretend
that a grammar edit alone checks the full caller contract.

**Put the condition before the action when it selects a branch.** Use “If X,
do Y” for a condition, “When X, Y happens” for a trigger, and “After X, do Y” for
ordering. These words are not interchangeable. A condition does not prove that
an event always occurs.

`rust/protocol_shared/src/outgoing.rs:150` says:

> Retrieves the existing client, or creates it if there isn't one.

This short summary clearly states both outcomes. There is no need to force it
into a longer template. For a longer branch explanation, two sentences can be
clearer: “Returns the existing client. If there is no client, creates one.”

**Keep a reason close to the action it explains.** Use “because” for cause and
“so that” for a purpose established by the source. Explain a surprising choice
or a constraint. Do not add a benefit claim to every action.

`mail/services/sync/modules/engines/identities.sys.mjs:316` says:

> Don't use .getIdentity because it will create one if it doesn't exist.

Suggested wording: “Do not use `.getIdentity`: it creates an identity when no
identity exists.” The original is useful and human. The suggested wording names
the repeated noun, makes the referent clear, and uses present tense for behavior.
The code uses `allIdentities.find` instead of `.getIdentity`; this study has not
proved the full implementation contract of `.getIdentity`.

**Connect sentences in a useful order.** State the action, then the exception,
reason, or caller duty that explains it. Repeat the main noun when the next
sentence introduces another object. Avoid several unrelated facts in one block.

`rust/protocol_shared/src/outgoing.rs:191` explains that the preference root
needs the server key, then names `NS_ERROR_NOT_INITIALIZED` when the key is not
set. The error follows its cause. Keep the error name and link target exact.
For a new developer, explain “pref branch” as a group of preference settings
when that term is not already clear from the surrounding API.

**Use pronouns only when they have one clear referent.** “It” is safe after one
named object. Repeat the name after introducing two possible objects. “This”
must identify an action or value, not point vaguely at a paragraph or “the code
above”. Name a function or invariant rather than a position that can change.

Before, `docs/mach_commands.py:258`:

> When running sphinx with sentry, it adds significant overhead
> and makes the build generation very very very slow
> So, disable it to generate the doc faster

Suggested wording: “Sentry adds overhead during the Sphinx build. Disable Sentry
to build the documentation faster.” The following `sentry_sdk.init(None)` makes
the disabled target clear. This removes repeated emphasis without adding a
performance measurement.

**Prefer active voice, with a named actor when needed.** Passive voice can be
clear when the result matters or the actor is unknown. Do not rewrite correct
passive wording only to satisfy a count. A caller duty often benefits from an
explicit actor.

Before, `mailnews/mime/src/mimei.cpp:1216`:

> Return value must be freed by the caller.

Suggested wording: “The caller must free the returned string.” This keeps the
ownership requirement and makes the responsible party the subject. It does not
invent an allocator or a deallocation function; verify those before naming one.

**Use tense and mood to match the claim.** Present tense describes current
behavior. Past tense describes a checked historical event. “Must” states a
requirement; “can” states a capability; “may” states a possible outcome. “Should”
can mean an expectation or a suggestion, so use a precise word when that matters.
Future tense fits a planned event, but must not promise a planned implementation.

Before, `taskcluster/docker/recipes/make_venv.sh:9`:

> The script will be create the environment and install from the
> requirements file.

Suggested wording: “The script creates the environment and installs packages
from the requirements file.” This fixes the verb sequence and uses present
tense. Keep `$1`, `$2`, the default directory, and the environment-name default
when documenting the caller contract; the sentence alone is not that contract.

**Use complete sentences for explanations.** A function summary with an implied
subject is normal. Short section labels, type descriptions, and compact inline
constraints can be fragments. Do not expand a useful label into filler. A
sentence beginning “because” or “which” needs an attached main clause unless it
is deliberately part of a continued sentence.

`calendar/base/modules/utils/calAlarmUtils.sys.mjs:138` uses the brief constraint
“Up to one icon per action”. It is readable next to the duplicate-action check.
The function summary above it explains the broader operation. A new explanatory
sentence could say “Add at most one icon for each alarm action.”

**Split clause chains while keeping constraints.** Do not split a condition from
the action it controls or remove exceptions to reach a word count. Keep one
small connected topic per paragraph. Use a blank line between a behavior summary
and extra rationale or tags.

Before, `calendar/base/modules/utils/calAlarmUtils.sys.mjs:115`:

> Removes previous children and adds reminder images to a given container,
> making sure only one icon per alarm action is added.

Suggested wording: “Removes the children from `container`. Adds reminder images
to `container`, with at most one icon for each alarm action.” “At most” preserves
the skip branch for unsupported actions. “One icon for every action” would change
the meaning.

**Keep the human voice and necessary detail.** “We” can clearly explain a shared
design choice. Do not ban it or add it mechanically. In
`rust/protocol_shared/src/outgoing.rs:151`, “We use `Arc` here because…” introduces
a specific requirement from `ProtocolClient`. Keep the distinction between `Arc`,
`Rc`, and `Send`; these are exact Rust types and traits. Explain them only to the
depth needed by the reader. Do not replace that reason with “ensures robust
coordination” or “provides a seamless experience”.

## JSDoc and other comment forms

Use the local comment markers and line width. Put a short inline comment next
to the action or constraint it explains. Use a block when the reader needs a
connected explanation. Preserve tool-required capitalization, tags, and license
text. Start explanatory sentences with a capital letter and end them with a
period. Keep identifiers and paths case-sensitive. Use backticks where the local
documentation form supports them. Name a symbol or file; use an exact revision
link when a fixed source location matters.

JSDoc needs a concise behavior summary, then relevant explanation, then tags.
Match `@param` names to the signature and explain input constraints. Match types
to actual values. State meaningful return values, empty or null cases, defaults,
caller-triggered errors, and caller-visible side effects. For async code, say
what the promise resolves to and what has completed when callers need that fact.
Do not equate starting an operation with awaiting its completion. Keep examples
small and check their inputs and expected results. Use bug and specification
links for a specific constraint, not as a substitute for an explanation.

Weak source text is evidence of a problem, not a pattern to copy.
`mailnews/extensions/smime/msgReadSMIMEOverlay.js:298` still combines certificate
viewer documentation with “or subdirectory of the given special system/app
directory (aDirToCheck).” The function accepts `cert`, not `aDirToCheck`. A proposed
replacement is “Opens the certificate viewer for `cert`.” The stray directory
sentence has no support in that body. This study does not rewrite the source or
claim that every async command must return its child operation's promise.

## Writing and review checklist

- Does the comment explain a reason, constraint, caller contract, or unclear action?
- Does every behavior claim match the implementation and relevant callers?
- Can the reader identify the actor, target, condition, reason, and result?
- Do articles and pronouns make each relationship clear?
- Can a long clause chain become two sentences without losing meaning?
- Are identifiers, types, parameters, results, errors, defaults, and links exact?
- Does the text sound natural and help a new developer use or change the code?
- Does a review finding name a real misunderstanding rather than a wording preference?

## Evidence and study limits

All source examples above were read from Git blobs at
`87d0159c7149a43253964c2cb6917939557dc799`. The source working files were not changed.
The census contains 43,150 tracked entries. Raw inventory, extraction,
per-comment indicators, and checkpoints stay in the private knowledge store.
Language lexers provide a candidate corpus; lexical counts cannot prove that all
comments were extracted or that their grammar and meaning were checked.

The quoted examples were checked manually against their adjacent source. Broader
grammar indicators only flag candidates. They do not determine grammatical
correctness, pronoun referents, code behavior, or quality. Imported code, generated
code, license text, tool directives, old components, and fixtures need separate
scope checks. Patterns conflict: imperative and present-tense summaries coexist;
short labels and long explanations coexist; natural first-person reasons and
awkward pronouns coexist. Their frequency does not choose the right rule.

Existing narrow evidence `f901044845b9ae2ca4c664518258fe104f8ab31b25ab8599830f56baa4f23f5f`
reports an accepted request for complete sentence comments in Calendar provider
tests. That historical record does not establish a rule for every fragment or
every component. The current user requirements and source JSDoc instructions
support the writing rules above. Full semantic coverage of every source comment
remains unverified. Publication of this guide does not establish study completion.
