# New Calendar event Save validates a snapshot and rejects stale completion

## Inputs and early exit

`saveCalendarEventCreate()` receives a store, fixed dialog key, field helpers, and the host transaction function. Redux is the state container; the store holds plain draft and operation data. Field helpers validate values and write them into a calendar event.

The save function returns `unavailable` unless the session is in create mode, its operation is idle or error, the draft exists, and title/date-time helpers have both validate and apply methods. This prevents a second Save from starting while one is pending and prevents creating an event without its required conversion helpers.

## One request owns the result

The function makes a request UUID, retains the baseline object identity, clones the draft, and dispatches `operationStarted`. Its `isCurrent()` requires both the same baseline object and the same operation request ID. It checks this after state changes and before and after the awaited transaction.

A replaced draft or session causes `stale`, with `operationReleased` sent for the old request. The session reducer releases only a matching pending kind and request ID. It cannot reset a newer pending request by accident. A stale result after a successful transaction does not undo that transaction; the guard protects replacement interface state.

## Validation and conversion

`prepareCalendarEventSave()` returns one entry per field. A row is disabled only when its enabled flag is exactly false. For enabled fields, it copies only owned draft keys using `structuredClone`. Disabled fields receive no values, while retained draft values remain intact.

The save function validates each enabled section with a validate helper and copies its result into state. It obtains the live calendar by the snapshot's `calendarId`, then checks calendar validity against `canCreateCalendarEvent()`. That helper requires a calendar, write permission, permission to add items, and no explicit false `capabilities.events.supported`.

`isCalendarEventDraftValid()` checks stored results for enabled sections. It does not perform field validation, and missing field results do not fail by themselves. This explains why Save must run validators first.

When validation fails, Save records `event-validation-failed` and returns `invalid`. When it passes, Save creates a `CalEvent`, sets its live calendar, applies enabled fields, adapts the scheduling agent, makes the event immutable, and awaits `transact(event)`.

## Success, error, and closing

The dialog's `save()` supplies `host.doTransaction("add", ...)`. It selects invitation response mode from `X-MOZ-SEND-INVITATIONS`. The save helper does not write directly to a calendar provider or close the dialog.

A current transaction completion dispatches `operationSucceeded` and returns `success`. A current exception dispatches `event-save-failed` and returns `error`. These actions do not erase the draft. The dialog watches successful Save state and queues closing in a microtask; it checks the request and baseline again before closing.

`operationFailed()` and `operationSucceeded()` accept only the matching pending operation kind and request ID. `operationSucceeded()` retains success when a request ID exists; other operations return to idle. This is why the observer can react to Save success.

The host transaction's provider write, undo work, and invitation delivery were not fully traced. `success` here means the supplied transaction promise resolved for the current request; it is not independent proof that all remote recipients received an invitation.
