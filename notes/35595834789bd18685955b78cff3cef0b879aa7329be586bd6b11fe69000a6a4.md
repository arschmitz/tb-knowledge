# Duplicate handling distinguishes discarding a write from deleting committed data

The historical duplicate-delete branch discards its unfinished store stream and removes a header row. The fixed consumer calls HardDeleteDetachedMessage instead. The inspected helper boundary attaches the detached header without notification, requires a nonempty token and deletes committed store data. Those actions have different preconditions from aborting an in-progress write. The old one-line API migration is not evidence that it introduced the later detached/live-header design. Database-deletion/repair details beyond the named boundary remain a source-ingestion gap. No duplicate scenario ran.

Scope: Duplicate message storage state.
