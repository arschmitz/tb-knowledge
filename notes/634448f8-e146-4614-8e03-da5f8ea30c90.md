# CalDAV add and modify complete through a server reread and cache callback

The checked [request completion](7b3c6223-e72d-4ade-b71d-edcf00d38784.md) is only one stage of an item write.
CalDavCalendar.addItem/adoptItem:550–589 clone/take the item, take and clear the
injected cache callback, and create a promise resolved by operation completion.
The callback is awaited before resolving the caller. Failure wraps status/detail
as Components.Exception for add. doAdoptItem:601–689 assigns ID when needed,
checks supported type, attaches superCalendar and sends ItemRequest with
If-None-Match:* unless overwriting. Successful upload records location then calls
getUpdatedItem, rather than resolving with the sent item. Server errors map to
NS_ERROR_NOT_AVAILABLE; conflicts and other statuses have separate paths.

modifyItem:702–725 likewise takes/clears the callback and awaits it. On failure
it rejects with raw detail. doModifyItem:739–815 requires itemInfo for the ID,
clones the parent, inserts a changed recurrence exception when needed, increments
generation and sends actual cached ETag unless ignoreEtag. Successful PUT calls
getUpdatedItem; conflict invokes promptOverwrite and retry; request rejection
notifies unavailable. No promise returned by doModifyItem represents finished storage.

getUpdatedItem:1202–1227 constructs actual MultigetSyncHandler for the remote path
and starts it. addTargetCalendarItem:949–1098 parses server ICS and uses its item,
so server edits replace the originally sent content. For cached provider with
listener, wrappedJSObject.onOperationComplete calls the cache hook and waits for
its returned promise. That wait has only promise.then(resolve), without a rejection
handler. A rejected cache callback can leave this wait pending (supported source
effect; no product reproduction recorded). For uncached/no-listener path, it awaits
backing adopt/modify then notifies success/failure. Metadata/index updates precede
those operations. Missing/invalid parsed first item returns without that completion.

Direct request assertions639–700 check PUT body and If-None-Match/If-Match/no-tag
variants plus 200/201/204 acceptance. Provider testModifyItemWithNoChanges in both
cached and uncached files disables server mutation, awaits modify and compares
returned title to unchanged server item. This directly checks reread result and
promise completion for that success case. Common helper assertions are reused from
the earlier provider study, not promoted to coverage of cache rejection or parse failure.
The installed requests file failed before assertions; provider tests were read here,
not run. Older inbox cleanup at line776 passes five positional arguments to the
current four-argument doDeleteItem; see the deletion record for exact effects.
