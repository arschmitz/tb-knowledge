# The original RSVP response handler only changes widget state

This landing emits setEventResponse and copies its status back to the acceptance widget, then leaves a TODO to update the event. Its new tests assert radio selection, the status attribute and event detail; they do not save a calendar response or send an iTIP reply. Fixed accepted code later clones the occurrence and attendee and invokes a save callback or transaction then restores old status on failure and checks identity before applying a successful result. The failure rollback precedes that identity check. Keep that later persistence phase separate from the original display contract.

Scope: Calendar read-dialog response display versus persistence.
