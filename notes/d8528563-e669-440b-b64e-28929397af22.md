# Worktree choices need not wait for a full graph refresh

The worktree picker received its inventory before `requestWorktrees` awaited `refreshGraphFromServer`. A changed inventory could therefore leave the picker waiting for a full graph snapshot even though its choices were already available.

## Evidence

The local pre-change `commands/graph/client/worktrees.js` contained `if (changed) await refreshGraphFromServer(graphIndex, { force: true });`. The committed `pollGraphUpdates` in `commands/graph/client/command-sessions.js` already schedules `refreshGraphFromServer(index);` without waiting. That refresh function reports its own errors and clears its running flag in `finally`.

A local change starts the same forced graph refresh but waits only for create/delete actions. Read-only inventory returns without that wait. Existing stale-picker guards, checkout confirmation and server validation remain in place.

## Validation and limits

The browser regression holds a graph snapshot response pending and verifies that the header choices render before it is released. It then exercises real header and context-menu checkout and verifies default-source and cache preservation. The browser test, ESLint, diff checks and independent review passed. A live inventory request took 62 ms during investigation; the exact initial reported delay was not captured, so this does not establish its complete cause or a live latency improvement. The source remains uncommitted local work.
