# Calendar batch ownership, immediate execution, and caller completion

`CalBatchTransaction.commit`, lines 247–258, retains a child, starts its operation
immediately, and awaits it. It removes only that child if the promise rejects.
It is not deferred work that starts when the batch ends. `canWrite`, 260–262,
requires at least one child and permission for every child. Redo runs children
in array order with an await between them, 264–268. Undo runs a reversed array
snapshot, 270–274. A rejection stops that loop; there is no rollback of children
already executed. Redo uses the live child array; undo uses a snapshot.

The manager owns a batch as one history entry. The application script owns the
current batch pointer `gCalBatchTransaction`. `startBatchTransaction`,
`calendar-item-editing.js:814–816`, replaces that pointer with a new manager batch.
`endBatchTransaction`, 823–826, clears the pointer and updates commands. It neither
waits for children nor calls the batch's `doTransaction` again.

`doTransaction`, 755–789, selects its manager before awaiting commit, but checks
the global batch pointer after that await. Thus the post-completion observer/menu
branch depends on the batch state at completion, not solely the owner chosen at
start. If a synchronous caller ends its batch while operations are pending, the
later continuations can take the ordinary completion branch. This follows from
the checked bodies; it was not measured as a running UI failure.

Actual caller differences were read:

- Selected-task progress/calendar/priority/postpone handlers in
  `calendar-task-tree-utils.js:157–253` start several `doTransaction` promises
  without awaiting them, then end the batch.
- Clipboard paste, `calendar-clipboard.js:279–299`, does the same for new IDs.
- `CalViewDNDObserver.onDropItems`, `calendar-dnd-listener.js:664–677`, uses
  `finally` to clear the pointer, but it still does not await the add promises.
- `setContextPartstat`, `calendar-item-editing.js:883–934`, uses `try/finally`
  around synchronous setup and calls. Its catch does not await later rejections.
- `putItemsIntoCal`, `import-export.js:102–137`, opens a history batch but directly
  awaits `destCal.addItem`; it does not commit child transactions in that loop.
  The read function can therefore leave an empty batch, and a listener rejection
  before `endBatchTransaction` has no local finally path. This is a source-level
  boundary, not a claim that imported items have verified undo coverage.

Direct unit tests check child call counts, all-child writability, sequential
batch stack selection, and removal of a failed child when another child finishes
first. Call-count assertions do not themselves verify reverse undo order,
stop-on-rejection effects, these UI callers' async errors, nested batches, or
import rollback. No broad caller claim is inferred merely from the shared name
`startBatchTransaction`.
