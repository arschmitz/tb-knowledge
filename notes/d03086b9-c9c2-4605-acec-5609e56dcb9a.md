# Calendar storage promise waits for row consumers but does not reject their caught errors

## Directly observed implementation

`CalStorageDatabase.executeAsync` wraps the actual Gecko connection's `executeAsync`
in a new promise. It converts one statement into a list, then registers a callback
object. Each `handleResult` starts `handleResultInner` and retains its promise.
The inner loop awaits the supplied row consumer in row order within that result
set. A consumer rejection is caught and sent to `handleError`, which logs a warning.
It does not reject the wrapper promise or stop later rows.

`handleCompletion` awaits all retained result promises. For `REASON_FINISHED`, it
sets `finishCalled` and resolves with `undefined`. Completion therefore includes
settlement of these row-consumer loops, but does not mean every row consumer
succeeded. Different result sets can have overlapping consumer loops.
Evidence: [calendar/providers/storage/CalStorageDatabase.sys.mjs:237–294](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageDatabase.sys.mjs#L237-L294).

The native callback interface declares `handleResult`, `handleError`, and
`handleCompletion` as `void`. Gecko does not use a returned JavaScript promise as
its callback completion contract. The Calendar wrapper supplies its own wait.
Evidence: [storage/mozIStorageStatementCallback.idl:13–45](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozIStorageStatementCallback.idl#L13-L45) and
[storage/mozStorageAsyncStatementExecution.cpp:323–388](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageAsyncStatementExecution.cpp#L323-L388). Native completion is scheduled after statement reset
and transaction commit or rollback. The wrapper's row-processing wait is a
separate layer.

## Interpretation and unresolved branches

A fulfilled query is not proof that a caller's row-to-item conversion succeeded.
Changes to row consumers can affect which items reach their downstream caches and
streams even if the SQL finishes. Exceptions from `getNextRow` are outside the
consumer catch. They can reject a retained result promise; the async completion
method has no catch that rejects the outer promise in that branch. This is a
source-supported possible unresolved-promise path, not a demonstrated SQLite or
native failure. The returned native pending-statement object is discarded by the
wrapper, so this wrapper exposes no cancellation handle.

## Validation and test links

A saved controlled probe ran the exact pinned wrapper source on
2026-10-13 at 08:44:08 UTC, using Node.js 26.3.1 on macOS arm64. One mocked row
consumer rejected. The warning contained that error; the wrapper still resolved
with `undefined` after mocked native `REASON_FINISHED`. This directly reaches the
wrapper's caught-consumer branch. The connection, row set, logger, URI and shutdown
blocker were mocks. It does not test SQLite or a live Calendar query.

The native statement tests execute the callback pipeline. Their named cancellation
checks are separate from a direct check of this wrapper's row-consumer rejection.
No direct product test for that rejection was identified in this slice. No test
existence is treated as a pass. Thunderbird and Firefox revisions are the paired
commits in the metadata. The wrapper's whole body was read before this pilot;
this pilot reuses that analysis and rechecks these exact completion ranges.
