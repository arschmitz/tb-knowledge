# The initial Exchange type view adds a skeleton before protocol-choice behavior

The initial landing registers a guarded custom element, an empty form and a disabled state-map entry. Its setState and captureState methods do nothing despite summaries naming their future roles. The DOM ID and state key are distinct names; the initial settings nextStep still uses the DOM ID, while accepted later code uses exchangeTypeSubview. Later radio controls and configuration capture are separate implemented phases. This source supports the skeleton and declaration mismatch, not a working choice form, navigation failure, accessibility result or account setup.

Scope: Account Hub Exchange state and UI phases.
