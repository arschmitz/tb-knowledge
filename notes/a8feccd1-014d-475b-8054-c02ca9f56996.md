# Thunderbird application selection, build traversal, and component registration

## How the layers connect

Thunderbird has a separate source repository inside the Gecko source tree. Gecko is the shared application engine. The parent tree's `moz.build` includes the selected application's `app.mozbuild` when `MOZ_BUILD_APP` is set. Thunderbird's `mail/app.mozbuild` includes `/toolkit/toolkit.mozbuild`, then visits Mailnews, mail components, branding, Calendar, Chat, and mail packaging. Paths in this application file are relative to the parent tree.

`mail/` holds the application interface and application support. `mail/components/moz.build` visits feature components such as account creation, the address book, compose, Calendar, extensions, preferences, and the unified toolbar. `mailnews/` holds shared mail facilities. Its build file visits address books, message composition, message databases, MIME handling, local mail, IMAP, news, search, and protocol support. MIME is the format used for message bodies and attachments. These are build and component boundaries, not proof that each feature is active in each configuration.

Calendar is also split. `calendar/moz.build` visits core implementation, import/export, invitation handling, translations, and providers. A provider supplies calendar storage or server access. The provider build list includes CalDAV, composite, Graph, ICS, memory, and storage. `mail/components/calendar/moz.build` packages the new mail-hosted dialog code and lists its browser and unit test manifests. Do not look only under `calendar/` for Calendar interface work.

`chat/moz.build` visits common chat components and protocol folders. A folder's inclusion does not prove the external service still works. `rust/moz.build` includes `ews_xpcom`, `gkrust`, and `graph_xpcom`; mail traversal reaches this directory only when `MOZ_OVERRIDE_GKRUST` is set. `mailnews/moz.build` reaches Panorama only when `MOZ_PANORAMA` is set. Preserve these conditions when describing a build.

## Registration and packaging

`mail/components/moz.build` lists JavaScript modules separately from `XPCOM_MANIFESTS`. XPCOM is the shared component system used to request an implementation by its contract name. `components.conf` binds `@mozilla.org/mail/mailglue;1` to `MailGlue` in `resource:///modules/MailGlue.sys.mjs`.

`MailComponents.manifest` adds the app-startup category only for Thunderbird's application ID. Its comment explains that this restriction keeps MailGlue out of xpcshell, the test runner without an application window. Registering a constructor and subscribing it to an application lifecycle are separate steps.

The source explains the requirement to keep `/comm/mail` last in `mail/app.mozbuild`: later directories can fail to package correctly on macOS. This is a packaging reason stated by the source. It is not a new experiment in this study.
