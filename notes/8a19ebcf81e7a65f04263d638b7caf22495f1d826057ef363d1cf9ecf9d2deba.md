# Message-ID normalization copies an explicit length before backup lookup

Fresh full Message-ID patch and needed fixed selection/backup/fallback consumers read. id is selected when m_message_id.length is nonzero. Angle-bracket stripping updates the stored length/value pointer and copies exactly that length into rawMsgId. This removes the unbounded null-terminated Assign path for this ID copy, conditional on valid source length; it is not a proof ParseHeaders always supplies valid storage. Backup lookup uses a nonempty normalized ID. Fallback now depends on rawMsgId.IsEmpty, covering absent/empty-after-normalization IDs, and writes the owned string directly. Existing owned fallback-ID lesson is reused; MD5 here identifies messages, not a security guarantee. The Bug explicitly rejects equating this crash with earlier IMAP crashes just because strlen appears in both; null-termination remains an author hypothesis. Later no-beta-crash/good-stats statements are attributed. No malformed-header, hash-failure or crash test ran.

Scope: Local parser Message-ID bounds.
