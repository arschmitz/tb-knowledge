# ICS Calendar queue, lock ownership, callback ordering, and mutation result limits

Production privileged JavaScript. Every body in CalICSCalendar.sys.mjs (1266 lines)
was read, including queue, backup, transport hooks and observer methods. ICS is
the serialized calendar file format. Provider internals are recorded in several
focused notes; imported parser, serializer, channels and native files remain
separate scopes.

The component manifest maps type=ics to resource:///modules/CalICSCalendar.sys.mjs,
constructor CalICSCalendar. moz.build packages this module, the provider module
and manifest. Constructor 71–86 creates an actual memory provider, points its
superCalendar at ICS, and adds a calICSObserver that retains the ICS instance.
The source notes no removal on initial registration. Replacement memory storage,
310–321, does remove the old observer; no whole-provider shutdown release appears.
URI setter 103–118 selects HTTP, file or dummy hook object by actual URI scheme.
RequiresNetwork is false only for file; canRefresh and scheduling support are true.

Public add clones then adopts. adopt/modify, 148–214, check readOnly, take and clear
the injected cached callback before queueing, start a batch, await a resolve-only
queue promise, await the saved callback with NS_OK, then endBatch in finally.
They resolve with the item. These callback identities are the actual cache bridge
from [cached mutation analysis](136d02e0-8196-4513-b49a-d763668afe02.md), not a
matching-name assumption. Delete, 222–235, checks readOnly and queues a
resolve-only function; getItem, 241–250, queues its resolver.

getItems, 259–281, queues an async exec that consumes the memory provider stream,
enqueues each array chunk in a second bounded stream, then closes. Its start method
does not return/await task.exec. Queue processing also does not await task.exec,
so stream errors have no explicit controller.error forwarding here. There is no
queued query cancellation/removal handler. Reader-lock and bounded-close behavior
also follow the checked [Calendar stream record](7d993b50-8d13-4bfe-8370-e91b00be5ce0.md).
Refresh, 283–298, only queues an action and returns undefined.

`#processQueue`, 690–746, stops while locked. Shifts tasks in order. A mutation
locks, calls actual memory CRUD, and in its success callback records the task and
awaits #writeICS, then returns from queue processing. There is no rejection
callback for memory CRUD in this code. A rejected memory mutation can retain
the lock and leave the outer resolver pending; this is a local control-flow
limit, not a proved outcome for every caller. getItem forwards a promise to its
resolver, getItems starts exec without await, and refresh locks/starts download
then stops processing until unlock.

`#unlock`, 752–778, visits saved modification tasks, calls function listeners
with action.item, clears that array, clears the lock, and restarts queue work.
Only the alternate object-listener branch consults errCode and opCompleteArgs;
the active public CRUD queue uses function resolvers. Thus an error unlock does
not reject those public promises or carry its error status to them. A controlled
exact-source experiment with successful memory add and failing serializer creation
observed a resolved add item and cleared lock despite no file write. This is
mocked boundary evidence, not a live-file failure test.

The observer at 983–1026 forwards item/load/batch/property events to the provider
ObserverSet. onError marks readOnly=true and calls provider.notifyError. Current
memory mutation can notify before eventual disk/network completion, while the
cached callback is withheld until unlock. Completion, observer updates, server
acknowledgment and onLoad are therefore distinct signals.

Direct assertion links: providers/head.js:28–74 checks exact calendar identity,
batch counts, and add/modify notifications inside a batch. runAdd/Modify/Delete
105–150 waits on provider promises and matching notifications; these helpers
execute CRUD but do not themselves assert complete serialized server contents.
Both cached/uncached ICS files 24–48 use these helpers and wait for onLoad after
each operation. Their connection-error tasks have separate checked alert links.
The cited tests do not directly verify failed memory CRUD, failed queue callbacks,
unhandled async exec rejection, or every mutation error promise contract.
