# Recurring storage offline flags remain stale in a warm model after a flag write

## Directly observed state and callers

`CalStorageCalendar.initDB` selects the `cached-item` model for all storage
calendars in this body. The model's first recurring-cache request stores one
private `#recurringCachePromise`. Its builder loads recurring parents and their
`offline_journal` values from SQL, fills separate event/todo item and flag maps,
and reuses that promise on later requests. `getItemById` and `getItems` trigger
this cache preparation. Evidence: [calendar/providers/storage/CalStorageCalendar.sys.mjs:490–516](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCalendar.sys.mjs#L490-L516) and
[calendar/providers/storage/CalStorageCachedItemModel.sys.mjs:15–86](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCachedItemModel.sys.mjs#L15-L86), [calendar/providers/storage/CalStorageCachedItemModel.sys.mjs:95–154](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCachedItemModel.sys.mjs#L95-L154),

The offline-query refresh branch checks a different public property,
`mRecItemCachePromise`. That property is never populated by the private cache
builder in this class. A Calendar JavaScript/module search at the pinned revision
found only the four public-property uses in that branch and the private-field
uses in the same file; it found no producer elsewhere in that searched scope.
This search does not rule out an external dynamic assignment outside that scope.
Even that branch clears the public property, not the private promise.
Evidence: [calendar/providers/storage/CalStorageCachedItemModel.sys.mjs:103–121](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCachedItemModel.sys.mjs#L103-L121).

`setOfflineJournalFlag` writes the database row but does not update the cached
model's recurring flag maps. The actual Calendar `addOfflineItem` calls that
model method. Recurring query selection uses the cached flag map, while
`getItemOfflineFlag` reads the SQL row through the offline model. These consumers
can disagree. Evidence: [calendar/providers/storage/CalStorageOfflineModel.sys.mjs:19–48](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageOfflineModel.sys.mjs#L19-L48),

## New observed product probe

A private xpcshell probe in this pilot used actual Calendar models and native
SQLite, rather than a mocked query. It added a recurring event, warmed the model,
then wrote the offline-created flag. The stored SQL flag was 1. The warm model's
offline-created query returned `[]`. A second storage calendar with the same URI
and ID, created after that write, returned the series from the same query.
The probe checked setup, stored flag, and reopened result directly; it recorded
the warm/reopened difference as data. It did not change production code.

Observed at 2026-10-13 15:06 UTC on macOS arm64, Thunderbird 160.0a1,
build 20261013101249. The native source revision is unknown. Calendar source bytes
match the paired Thunderbird commit. This run establishes the described warm
versus reopened behavior in that installed environment, not every native revision,
todo branch, offline-modified/deleted state, or full network reconciliation.

## Existing direct test and gap

`testDeleteCalendarKeepsOfflineFlagsReadable` creates an offline-created recurring
item, then reopens the calendar before the query. It verifies the flag survives
wipe/re-add, when the reopened model has already loaded that flag. It does not
verify a new flag written after warming the same model. This distinction is
confirmed by its setup, not inferred from the test name.
Evidence: [calendar/test/unit/test_storage.js:194–241](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/test/unit/test_storage.js#L194-L241).

That test file passed in the saved older-build run at 2026-10-13 08:40 UTC,
Thunderbird 159.0a1/build 20261006201633, native revision unknown. Its pass does not
resolve this new warm-model branch. The cache/offline modules were fully read
before this pilot and reused; the live probe closes a previously explicit runtime
gap. No source fix or general cache policy is asserted by this record.
