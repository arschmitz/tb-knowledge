# Calendar storage mutations separate persistence, offline flags and observer notifications

## Add and modify body contracts

`addItem` clones its input then calls `adoptItem`. Adoption rejects a read-only
calendar or duplicate ID unless relaxed mode is set. It assigns a new ID when
absent. An occurrence is applied as an exception to a cloned parent. The parent
is assigned to `superCalendar`, made immutable, and persisted. The method then
notifies `onAddItem` and returns the adopted input, which can differ from the
parent object persisted. A standalone calendar surrounds that notification with
batch start/end and sends `onLoad`; a cache relies on its outer calendar for those
batch/load actions. Evidence: [calendar/providers/storage/CalStorageCalendar.sys.mjs:181–241](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCalendar.sys.mjs#L181-L241).

`modifyItem` first reads the old offline flag, checks read-only/input/ID and
stored-generation contracts, clones the new parent, and applies any occurrence
exception. Optional sequence propagation copies a truthy SEQUENCE or removes it
when falsey. Normal mode increments generation when unchanged; relaxed mode
leaves that to callers. The new parent becomes immutable before persistence.
It then restores the old offline flag, sends operation completion, sends
`onModifyItem`, and returns the persisted parent. Standalone batch/load behavior
again surrounds the observer notification.
Evidence: [calendar/providers/storage/CalStorageCalendar.sys.mjs:244–353](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCalendar.sys.mjs#L244-L353) and [calendar/providers/storage/CalStorageCalendar.sys.mjs:562–581](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCalendar.sys.mjs#L562-L581).

## Persistence and failure boundaries

The actual cached item model inherits `updateItem`, which first awaits deletion
of the old item's rows with metadata retained, then awaits an independent add
request. Add groups item and extra-table bindings into one native batch. Delete
queues all rows for the item's ID and calendar, including recurrence rows and
exceptions, optionally retaining metadata. The separate deletion and insertion
requests are not an encompassing transaction in these bodies. A native
transaction within either batch does not prove atomicity across both.
Evidence: [calendar/providers/storage/CalStorageItemModel.sys.mjs:73–79](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageItemModel.sys.mjs#L73-L79), [calendar/providers/storage/CalStorageItemModel.sys.mjs:1079–1110](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageItemModel.sys.mjs#L1079-L1110),
[calendar/providers/storage/CalStorageItemModel.sys.mjs:1368–1382](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageItemModel.sys.mjs#L1368-L1382), and [calendar/providers/storage/CalStorageStatements.sys.mjs:658–687](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageStatements.sys.mjs#L658-L687).

The offline writer catches and logs a query failure rather than propagating it.
Successful modification can therefore reach success notification after a failed
flag-restoration request. This is a directly observed catch/sequence contract;
no such native failure was injected in this pilot.
Evidence: [calendar/providers/storage/CalStorageOfflineModel.sys.mjs:36–48](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageOfflineModel.sys.mjs#L36-L48) and [calendar/providers/storage/CalStorageCalendar.sys.mjs:328–350](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCalendar.sys.mjs#L328-L350).

Deleting a parent awaits row deletion, sends operation completion and
`onDeleteItem`, then resolves null. The child-occurrence branch instead calls
`removeExceptionFor` on the parent and returns null without a persistence request
or these notifications. That mutation can throw if the supplied parent does not
allow mutation. It is not proof that occurrence deletion always persists here.
Evidence: [calendar/providers/storage/CalStorageCalendar.sys.mjs:355–389](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCalendar.sys.mjs#L355-L389).
