# Bound section metadata and output scope while retaining complete record evidence

The original fingerprinted working-tree index copied all record paths into each section, then stored them twice again in FTS. A bounded 128-row sample averaged 917 source-text bytes and 7458 JSON-path bytes; eight verified aggregate examples repeated 126.58 MB of path payload. These are cache-specific observations, not full-index accounting. Append-only outcome: current sectionMetadata selects at most eight paths mentioned in the section/context, records recordPathCount when scope is larger, and new FTS rows use those selected paths. Result metadata is recomputed with that helper. Existing section version remains 1, so legacy cached rows are not automatically rewritten. A bounded projection reduced one section metadata payload from 63083 bytes to 714 bytes; no cache rewrite ran. The result still emits full top-level record.paths, so the measured formatting lower bound remains above the 24000-character budget despite compact nested metadata. Remaining proposal: keep complete immutable scope and source text, but return bounded relevant paths plus a link/reference to complete scope; plan safe generated-cache compaction separately. Preserve record-level path lookup for paths absent from section text, exact UTF-16 citation offsets, repository isolation, explicit scope filters and claim deduplication. Embeddings already use bounded section.input. Current code is uncommitted; path-only and deep-symbol retrieval on large scope lists still need focused validation.

Scope: knowledge section indexing and retrieval.
