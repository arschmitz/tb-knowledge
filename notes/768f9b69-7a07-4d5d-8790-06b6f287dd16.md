# queueCalendarEventEdit serialization, move aliases, rejection, and release

The entire queue module's local bodies were read. The package entry is
`mail/components/calendar/moz.build:12–15`, which exports the module under
`resource:///modules/calendar/`. The Save caller resolves that actual lazy import;
this connection is not based only on the function name.

`queueCalendarEventEdit`, lines 134–189, groups pending edits by event ID, not
calendar ID or window. Independent stored copies with the same event ID share
ordering, while the `identities` map keeps their calendar identities distinct.
A request is a shallow copy of the input identity and is retained in a set.

The callback is appended to `queue.tail`. When it starts, it reads a successful
move alias for the request's calendar, if one exists, and preserves the request's
occurrence ID. Save then reloads the live event for that identity. The queue
awaits the edit callback and shallow-copies its returned identity. It retargets
existing aliases that point at the moved source and adds both old and new
calendar aliases. Separate calendar copies are not all collapsed into one item.

The returned promise follows `result`, so the caller receives rejection from a
failed edit. The tail follows `result.catch(() => currentIdentity)`, so a failed
edit does not poison later queued work. Failure does not commit the successful
alias-update block. This is a distinction between caller error reporting and
queue continuation, not silent success.

The `finally` block removes the request. Only the operation whose `next` is still
the queue's tail deletes the map entry. An older completion must not delete a
queue that already contains later requests. When all work ends, aliases are
discarded. They are not persistent move history. The queue retains requests,
identities, promise callbacks, and temporary recurrence-shift objects while work
is pending. There is no abort method or cancellation token in this module.

Observed dependency limit: the callback must return a usable identity and finish
its work. The queue does not validate that identity or ensure a provider callback
will settle. If a callback changes storage and then rejects, successful storage
is not automatically reversed. Calling back into the same queue and awaiting
work behind one's own operation is not handled by a special re-entry path.

Direct assertions in `test_calendarEventEditSave.js`:

- `test_overlappingEditsKeepNewestValues`, 382–414, checks the later title and
  the old result retained by undo after the later Save reloads it.
- `test_overlappingEditsAfterCalendarMove`, 416–498, checks destination ordering,
  storage, and each history step.
- `test_calendarMoveQueueFailureAndCleanup`, 500–545, checks continued ordering
  after rejection and removal of both idle aliases.
- `test_destinationEditWaitsForMoveCompletion`, 547–601, pauses move and older
  edit and verifies that destination work has not started at each stage.
- `test_calendarCopiesKeepTheirOwnLiveEvents`, 603–636, checks distinct source
  and destination copy titles despite a shared event ID.

These tests exercise real memory transactions for storage cases and pure
callback identities for queue-only cases. They do not prove all provider timing,
cross-process editors, restart recovery, re-entry, or indefinite-operation cleanup.
