# Bug 2073142 draft patch: restore the Details tab preference

## Scope and action

This follows note `d151acdc-b0d2-4266-ae6a-7c8bd358adf4.md`. Its source history remains valid. The existing Bug 2048214 fix avoids the null-tabmail crash by routing Details in view mode, but that mode clears `args.inTab`. Thus it does not preserve editor tabs for editable published events.

A draft patch changes only the `X-SHOWDETAILS` route in `calItipUtils.sys.mjs`: obtain the main calendar window, call `modifyEventWithDialog(item)` when `calendar.item.editInTab` is true, and otherwise retain `openEventDialogForViewing(item)`. The modify call retains the existing recurrence prompt and calendar permission checks. Invitations and read-only events use the existing summary branch. Other view callers and counterproposal handling are unchanged.

Base Git revision: `2135bbdeb7dd3feafb298c0220b412a66cc41826`. Draft patch SHA-256: `817c151bad134c86b50b9513cc6e769995f40329ef63ca0c9b872131ff7a0893`. This patch is local and uncommitted in the Thunderbird checkout. It has not been submitted, reviewed, accepted, or landed.

## Native browser tests

New `browser_imipDetails.js` clicks the actual Details action after adding the emailed PUBLISH event. It checks six editor cases: message pane, message tab, and standalone window, each with the new read dialog preference both enabled and disabled. It waits for the editor to load the matching event ID, checks its title and selected tab, and verifies that no read dialog opens. With tab editing disabled it checks both old and new read dialogs. It also checks that read-only and invitation items do not open editor tabs. The read-only case changes calendar access after the message exposes Details; read-only calendars may otherwise be excluded from the invitation lookup.

The existing `browser_attachedPublishEvent.js` now explicitly disables tab editing and closes its new read dialog. This keeps its Bug 2048214 behavior check separate from the restored tab preference.

Both files ran in native headless Thunderbird browser tests using a separate artifact build. Final result: 31 checks, all expected; 28 passed assertions, one expected TODO, two passing test files, zero unexpected results. The new test file passed ESLint together with the changed existing test. Comparing ESLint on the original and changed module found identical existing diagnostics and no new ones. `git diff --check` passed. Applying the exported patch to copies of the three base files succeeded and reproduced all four working files, including the new test.

A regression experiment temporarily restored the original module while running the new browser test. `test_details_opens_editor_tab` failed because Details did not open an editor tab from the message pane (50 wait attempts). The run was stopped after that failure because the open baseline summary dialog blocked later cases. The patched module was restored in a `finally` block, and the complete two-file suite passed again afterward. Do not interpret the interrupted baseline as a complete baseline suite result.

## Reusable lesson

For email Details, selecting the owner window and selecting view versus modify mode are separate choices. Using the owner window fixes document lookup; using view mode also changes whether editable items honor the tab preference. Check both preferences and protected items when changing this route.
