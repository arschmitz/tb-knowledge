# Gecko storage batches row callbacks and finishes transaction work before completion notification

## Directly observed execution state

`AsyncExecuteStatements::execute` creates a runnable that owns the moved statement
list, the connection, the callback, and the calling thread. It dispatches to the
connection's async target and returns that runnable as the pending-statement
handle. A missing target or failed dispatch is an immediate request failure.
Evidence: [storage/mozStorageAsyncStatementExecution.cpp:43–101](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageAsyncStatementExecution.cpp#L43-L101).

`Run` first checks cancellation. It starts an immediate transaction when the
write-action count exceeds one and no transaction is already in progress.
`StatementData::needsTransaction` supplies zero for reads and a count for writes,
including binding rows. Failure to begin a transaction does not stop this method;
`mHasTransaction` stays false and the statements are still processed. Therefore,
"multiple statements" alone is not proof that this body starts a transaction.
Evidence: [storage/mozStorageAsyncStatementExecution.cpp:460–470](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageAsyncStatementExecution.cpp#L460-L470), [storage/mozStorageAsyncStatementExecution.cpp:502–561](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageAsyncStatementExecution.cpp#L502-L561), and
[storage/mozStorageStatementData.h:95–105](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageStatementData.h#L95-L105).

Each bound row is bound to SQLite and executed in order. Binding failure records
ERROR and notifies an error; row-loop execution stops for error or cancellation.
Results are grouped after 15 rows or more than 75 milliseconds before dispatch to
the calling thread. These limits are buffering thresholds, not a promise of an
exact timer interval. Evidence: [storage/mozStorageAsyncStatementExecution.cpp:118–214](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageAsyncStatementExecution.cpp#L118-L214) and
[storage/mozStorageAsyncStatementExecution.cpp:288–320](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageAsyncStatementExecution.cpp#L288-L320).

Before completion, the executor resets every statement, clears the retained
statement list, then commits its own successful transaction or rolls it back on
error/cancellation. Commit failure changes state to ERROR and notifies an error.
It dispatches completion afterwards. Callback result/error invocations keep a
local strong callback reference to survive a nested event loop that can consume
completion and move away the executor's callback. Cancellation suppresses result
and error notifications through `shouldNotify`; completion remains distinct.
Evidence: [storage/mozStorageAsyncStatementExecution.cpp:323–454](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageAsyncStatementExecution.cpp#L323-L454).

The callback interface returns `void`; the executor discards callback return
results. It does not wait for promises a JavaScript callback might return. Calendar
waits for its own retained row-consumer promises on top of this native contract.
Evidence: [storage/mozIStorageStatementCallback.idl:13–45](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozIStorageStatementCallback.idl#L13-L45) and [calendar/providers/storage/CalStorageDatabase.sys.mjs:247–291](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageDatabase.sys.mjs#L247-L291).

## Test links and validation limits

`test_last_multiple_bindings_on_statements` directly checks mixed-type writes,
finished reason, and resulting row count. `test_multiple_results` directly checks
all expected query rows through its helper. Cancellation tests directly check
request errors/races. These execute the native queue and callbacks; they do not
independently verify every buffer threshold, begin-transaction failure, ownership
release, dispatch failure, or commit failure.
Evidence: [storage/test/unit/test_connection_executeAsync.js:95–164](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/test/unit/test_connection_executeAsync.js#L95-L164) and
