# Calendar description data and browser readiness have separate completion boundaries

The accepted description row keeps the last plain/HTML tuple when it is not ready. Full mode starts browser connection without awaiting it, then replays that tuple after the expected document loads. setDescription itself is synchronous at the fixed revision, and CalendarDialog calls it before its own load resolver. Awaiting the setter return does not prove the rich browser is connected or painted. The original commit used an async setter and allSettled, so preserve those phases. The selected compact connection branch does not replay an earlier cached tuple; this is a static state question, not a reproduced failure. No browser test ran.

Scope: Calendar dialog rich-description connection and data cache.
