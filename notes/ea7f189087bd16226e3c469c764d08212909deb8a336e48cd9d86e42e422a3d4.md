# Notification startup readiness does not make every fulfilled wait a display-ready result

The startup delay is shared across waits, while a per-wait shortcut can stop waiting for readiness. The original patch places its delay after the no-currentWindow early branch; the accepted later scheduler moves the gate before that branch and before event callback registration. In the accepted early-window-unload path, handleUnload resolves the shortcut and waitForActive returns without rejection. The UI consumer returns only on rejection and otherwise continues constructing the notification element. Thus fulfillment from that path is not proof all activity/display checks passed. This is a static completion-contract gap, not a reproduced visible notification or a complete cancellation fix. Current tests manually resolve the startup promise and do not measure the real two-minute delay. Existing listener-identity and polling-timer gaps remain separate. No runtime or accessibility test ran.

Scope: in-app notification scheduler startup and cancellation.
