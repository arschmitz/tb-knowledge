# Message opening helpers select tabs, windows, and draft composition

`displayMessage()` delegates one header to `displayMessages()`. That method reads `mail.openMessageBehavior`, with a forced tab overriding the preference. It opens new windows, tries an existing window for exactly one header and otherwise falls back, or delegates to tab opening. An unknown preference value does nothing in the switch. These calls return before message rendering; they expose no completion promise.

`openMessageInNewTab()` uses a supplied tabmail or finds the most recent main window. No tabmail falls back to separate windows. More messages than `mailnews.open_tab_warning` require confirmation. Every tab receives the folder-produced message URI and the view wrapper; all but the final tab open in the background. The final tab's background choice applies the load-in-background preference only when shift state was supplied. The method focuses a main window it found itself. Actual tab loading/view-clone ownership is downstream, not proved by the passed property.

`openMessageInExistingWindow()` returns true after asking the existing message window to display; absence returns false. `openMessageInNewWindow()` returns the opened window and passes header/view through a wrapped argument object. `openMessagesInNewWindows()` has a separate warning threshold and sequentially opens each header. A thrown opening error can stop later opens.

`displayFolderIn3Pane()` finds the recent main window, switches the first tab when needed, displays the folder, and focuses it. It has no missing-window guard. `displayMessageInFolderTab()` can use ordinary message opening when the message pane is hidden, show/select in the existing main window, or create a main window with the header argument. Platform window-integration is an additional dynamic native target.

`openEMLFile()` adds the message-display query and synchronously reads/decodes headers. Read or parser failures are ignored so the later display can handle them. The opened input stream is closed in `finally`; a close failure itself is not caught there. `X-Unsent: 1` opens Draft composition and uses the From header; otherwise it opens a tab only when the preference and current window support it, or a standalone message window.

Direct browser tests check new tab count/mode/title/message/focus, opening one separate window, and reusing a window for another header. The test itself says multiple-window opening is not directly covered; do not infer that coverage from the shared loop. The X-Unsent test directly checks a compose subject from the fixture, which contains that header and subject. It does not check every header/stream failure path. The opening helper presses Enter at FolderDisplayHelpers:276–283. The thread activation handler at about3Pane:4804–4820 routes ordinary messages to cmd_openMessage, whose body at mailCommon:113–122 calls the actual MailUtils.displayMessages receiver with selected headers, wrapper, tabmail, middle-click and shift state. The checked tests wait for UI state and window/message load signals, not the synchronous return values. No browser test run was made.

`mailCommon.cmd_copyMessage()` is a related external-message consumer: for a file URI it awaits `copyFileMessageAsync()`, logs rejection, then awaits/logs `updateFolderAsync()`. Other messages go through the view's copy command. It writes the last move/copy target preference afterward. Those final preference writes do not by themselves prove the copy succeeded when a rejection was caught.
