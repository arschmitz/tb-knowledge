# MailServices binds named helpers to actual component interfaces

The module imports Firefox `XPCOMUtils` and defines lazy service properties with explicit component contract IDs and requested interfaces. These bindings resolve `accounts`, `copy`, `filters`, `mfn`, and `folderLookup` to their actual service contracts; they do not resolve every protocol-specific method implementation. The component configuration supplies the checked native FolderLookupService, nsMsgCopyService, and nsMsgFolderNotificationService types. The base moz.build packages MailServices/FolderUtils and compiles those native files into the mail library. The mail modules build packages MailUtils and MessageArchiver.

`messageServiceFromURI()` requires a colon, extracts the exact prefix, maps `file` to `mailbox`, and asks that message-service contract for nsIMsgMessageService. Unknown prefixes fail through component lookup. `neckoURLForMessageURI()` calls that service's `getUrlForUri()` and returns the resulting `.spec`. It uses the actual receiver, so a similarly named arbitrary object method is not treated as this protocol service.

At `xpcom-shutdown`, an observer deletes every own enumerable MailServices property, including ordinary helper methods as well as lazy/resolved services, then removes itself. This releases module-held references; it is not a promise that outstanding native operations invoked all their callbacks before shutdown.

The direct unit test checks member existence and actual interfaces for its named service list. It checks file, IMAP, mailbox, and news message-service prefixes, and asserts an exception for an unknown prefix. It does not check every lazy property, malformed URI without a colon, necko URL content, or shutdown deletion. No run was performed by this agent. The [existing Firefox XPCOM utility body study](6da3bb45-4bac-4460-b78c-346e07d40ee6.md) is reused for the general lazy-service mechanism; new evidence here is the mail-side bindings, consumer identities, and narrower test limits.
