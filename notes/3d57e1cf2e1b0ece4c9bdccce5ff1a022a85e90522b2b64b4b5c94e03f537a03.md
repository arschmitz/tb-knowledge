# Current splitter window resizing locks neighbors and leaves one pane flexible

The 2024 resize-with-window implementation in 597 was later backed out at 628. The fixed current implementation is a later reland, so its old timeout logic is historical. Current code activates window resizing only after a size is assigned or established by dragging. It measures lock targets before applying their important pixel sizes, then gives the controlled pane 100% so later window growth goes there. Missing or unusable target sizes trigger a bounded animation-frame retry; disconnect and collapse release resize locks/listeners. Current horizontal and vertical tests distinguish the inactive default grid from active locking and cover growth, drag, collapse and restore. Do not infer that merely adding the attribute locks all neighboring panes immediately.

Scope: pane-layout.
