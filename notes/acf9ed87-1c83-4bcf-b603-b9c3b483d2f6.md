# Ingestion capacity calibration: current process fails the 1,000-hour launch target

The preparation tool works. The current process for reading and checking behavior does not demonstrate enough speed to promise complete Thunderbird and Firefox ingestion within 1,000 hours on four available workers. This is a no-go decision for that commitment, not proof that every future process must exceed the target.

## Measured results

- Whole ledger: 527,502 tracked paths; 524,471 included; 3,031 Thunderbird Suite paths excluded. Every pinned path/blob/mode matched the saved census. The ledger joins previous maps; it does not reinterpret every body.
- Cold preparation: all 14 packets in 1.634 seconds. Warm cache: 0.540 seconds. The packets contain 51 source/context files. This is input preparation, not behavior analysis.
- Broad preparation check: 681 representatives from repository/language/role/size groups; 663 prepared, 18 explicit binary/non-UTF8 failures in 59.667 seconds. 13,670 capped search-lead occurrences remain disclosed. All 681 inputs have an outcome.
- Reading test: 9 independently accepted whole-file obligations and 5 partial files. The sample/review span was 27.71 minutes: **19.48 accepted files per elapsed hour**, including time spent on partial results. This rate excludes earlier tool/ledger development and later publication/report work.
- 145 implementation sections, 101 relationship entries, and 25 test/coverage entries were saved. Sections include bodies, callbacks, resource rules and build sections; they are not interchangeable function counts.
- 385 current evidence anchors passed path/revision/range checks; quoted anchors also matched exact source. All final reviews match the exact producer record hash. Mechanical validation does not prove interpretation or completeness.
- New tool validation: 10 tests pass, lint passes, and 10 tests plus 14-packet preparation pass from a clean export of the published commit. Environment: Darwin arm64, Node.js v26.3.1. These are tool tests, not Firefox/Thunderbird product tests. No product test ran.

## Capacity decision

Finishing 524,471 file obligations in 1,000 elapsed hours requires **524.471 accepted files/hour**. Four continuously productive workers allow **27.456 worker-seconds per file**, before fixed costs. This sample spent **401.1 recorded analyst-seconds per accepted file**, including partial work: **14.6 times that budget**. This compares the observed process with the target; it is not a reliable whole-repository time forecast.

The 14 frozen selection cells contain 114,926 origins (21.91%); 409,545 origins (78.09%) have no calibrated cost. Each cell has only one selected file, so there is no estimate of within-cell variance or defensible confidence band. The large challenge remains partial. Initial path-based labels also misclassified an imported C file as ordinary production; the original selected file and weight were retained and its actual role corrected.

Multiplying each cell population by its selected file's recorded cost gives a conditional diagnostic of 7794.8 analyst-hours for cells whose sampled file completed, plus 240.7 analyst-hours of spent-only partial work. Dividing the complete subtotal by four gives 1948.7 ideal hours. This is not a statistical lower bound, an unbiased total estimate, or a full-scope forecast. Missing costs are unknown, not zero. It still offers no support for launching under the target.

The earlier 894-hour scenario is not a measured estimate. It assumed 3,000,000 pilot-equivalent units, 128 concurrent jobs, doubled efficiency and scaling factors. Those units and capacity were not established. Earlier rates for body descriptions and scoped behavior chains use different completion units and cannot be multiplied by this file ledger.

## Reuse, exclusions and unresolved work

The included origins contain 476,461 distinct blobs; 48,010 file copies (9.15%) have identical content. Content analysis can be reused, but each origin retains its caller, import, build and test context. This saving cannot be treated as equivalent semantic-time savings. Imported and generated code stay in scope; Suite is the exclusion.

Existing normalized evidence includes 329 body claim references across 42 files, 214 reviewed body references across 29 files, 195 older file/range readings across 182 files, three scoped chains across 78 files, and 4,189 narrow automated facts across 1,125 files. These categories overlap. Unstructured historical notes may add evidence; the ledger does not claim their absence. Their original scope and IDs remain intact.

There are 31,507 files with failed or error-containing structural parses and 20,255 binary/non-UTF8 files. Some are deliberate invalid fixtures or preprocessor-dependent source. They are extraction/disposition gaps, not confirmed source bugs. The 2,305,250 callable-like entries exclude known Rust signature-only nodes but still are not a strict count of complete function bodies. Resource extraction covered selected directories; an absent site does not prove no relationship.

Five open sampled areas require more work: debugger runtime receiver/source-map paths; compressed-stream native lifetime and caller conditions; Glean generator/template contracts; Calendar CSS theme and selector consumers; and most of the large Wasm component implementation. Complete-file decisions apply to the recorded target and checked immediate contracts, not to every transitive dependency. A test's existence or expected-result metadata is not a PASS result.

## Reusable result and publication limits

The [published tb-tools change](https://github.com/arschmitz/tb-tools/commit/20e7a5d4db5d6d188fbf351dbf445d86755372a8) adds a standalone Node.js packet preparer, deterministic grouped sampling, tests and a guide. It uses pinned blobs, checks content identity, keeps every origin and explicit failure, and labels nearby name/literal matches as unverified leads. Its regular UTF8 file limit is 4 MB. Binary files, unsupported encodings, symlinks and oversized files need other handling. It does not implement a semantic analysis worker or scheduler, and it does not add a new `tb knowledge` command route.

The initial packet configuration used a Firefox alias where an exact repository ID was required: nine explicit failures. The corrected configuration prepared the same 14 targets. One out-of-range build quote and several inaccurate contract fields were repaired and reviewed. A clean-test invocation used the wrong working directory once; rerunning from the clean export passed. These failures were retained rather than hidden.

Focused notes below preserve bodies, observed/inferred/unresolved links, exact pins, tests and open work. Review additions preserve the original audit and correction trail. Shared evidence belongs in thunderbird-knowledge; disposable ledgers, caches and indexes stay outside shared Git. Automatic ingestion does not edit deliberate instructions.
