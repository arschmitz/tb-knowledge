# SMTP progress reaches compose taskbar state and assertions

This record follows the predefined SMTP Send Now progress chain. It adds caller,
consumer, ownership and assertion links to the earlier native body records. It
does not complete all callers of every `nsMsgProgress` method. Thunderbird source
is pinned to `87d0159c7149a43253964c2cb6917939557dc799`; Firefox dependency source is
pinned to `1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b`. Production JavaScript runs in
privileged compose windows/modules; the relay and observer array are native C++.
The browser test and its head are test code. Suite is excluded.

## Trigger and actual sender

The [`button-send` markup](https://github.com/mozilla/releases-comm-central/blob/87d0159c7149a43253964c2cb6917939557dc799/mail/components/compose/content/messengercompose.xhtml#L1840-L1844)
uses `command="cmd_sendButton"`. The window loads Thunderbird's
`mail/base/content/globalOverlay.js`, whose `goDoCommand` selects an enabled
controller. `SetupCommandUpdateHandlers` registers the actual compose controller;
its online handler calls `SendMessage`. That function chooses `Now` or
`Background` using `mailnews.sendInBackground`, whose default is false.
[`GenericSendMessage`](https://github.com/mozilla/releases-comm-central/blob/87d0159c7149a43253964c2cb6917939557dc799/mail/components/compose/content/MsgComposeCommands.js#L6161-L6630)
runs preflight, then awaits `CompleteGenericSendMessage`. The latter creates
`@mozilla.org/messenger/progress;1`, registers the window-global `progressListener`,
sets the operation flag and calls `gMsgCompose.sendMsg` with that progress object.

`nsMsgCompose::SendMsg` holds `mProgress`. `SendMsgToServer` registers its native
`nsMsgComposeSendListener` with progress, then passes both objects to
`MessageSend.createAndSendMessage`, which stores `_sendProgress` and `_sendListener`.
The native `mail-set-sender` observer can replace the sender. This chain describes
the default component, rather than claiming a fixed target for arbitrary
extensions. `beforesend` and `compose-send-message` can also stop preflight.

The test helper creates a type `smtp` server and stores its key on the identity.
`OutgoingServerService.getServerByIdentity` looks up that exact key; the SMTP
component entry selects `SmtpServer`. `MessageSend._deliverAsMail` passes
`this._sendProgress` as `statusListener` to `server.sendMailMessage`.

## Producer, bytes and the Firefox boundary

The actual SMTP producer is
[`SmtpServer.sendMailMessage`](https://github.com/mozilla/releases-comm-central/blob/87d0159c7149a43253964c2cb6917939557dc799/mailnews/compose/src/SmtpServer.sys.mjs#L639-L813).
After an accepted SMTP DATA response, `SmtpClient._actionDATA` calls `onready`.
That callback reads 65,536-byte chunks from the message file. It queries
`statusListener` as `nsIWebProgressListener` and calls **`onProgressChange`
directly**. The `nsMsgProgress::OnProgress` adapter is not used in this SMTP path.

The loop increments `sentSize` by each original `chunk.length` and reports the
message file size as both maxima. `SmtpClient._sendString` adds SMTP dot escaping
before passing the data to its socket. These values therefore describe file
upload progress, not exact wire-byte counts or delivery to the recipient.

When `client.send` returns false, the loop waits for the socket drain callback.
`SmtpClient._onDrain` calls the assigned handler; that handler resolves the wait.
Firefox's [`TCPSocket` contract](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/dom/webidl/TCPSocket.webidl#L109-L158)
describes this Boolean as a buffering hint. After the file ends, the producer
closes both streams, calls `client.end()` and reports `(0,-1,0,-1)`. This changes
progress to indeterminate while the SMTP terminal response is still pending.

## Native relay and mutable listeners

This extends the earlier [registration body record](26733ffb-f98d-54f0-aad6-97067f6e0413.md),
[state relay record](906bb284-e806-51e6-afd5-7e61c719a226.md), and
[progress relay record](6d0e9762-6580-5a8c-a3ad-e8146bdbf797.md).
[`nsMsgProgress`](https://github.com/mozilla/releases-comm-central/blob/87d0159c7149a43253964c2cb6917939557dc799/mailnews/base/src/nsMsgProgress.cpp#L75-L159)
holds weak listener references. Each callback obtains a temporary strong
reference. Dead entries are removed. Progress values are forwarded unchanged;
state flags and status are also cached. Listener return codes are ignored.
Registration can immediately replay status and state. Closed or canceled progress
replays STOP with `NS_OK`, regardless of the original terminal error.

Its `nsAutoTObserverArray` is the paired Firefox implementation.
[`ForwardIterator::HasMore` and `GetNext`](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/xpcom/ds/nsTObserverArray.h#L295-L331)
use current length and advance the next index. Removal calls
[`AdjustIterators`](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/xpcom/ds/nsTObserverArray.cpp#L7-L17),
which reduces indices after the removed slot. Self-removal in a STOP callback does
not skip the next listener. A newly appended listener may be reached by the same
broadcast. This is direct implementation evidence, not a matching-name guess.

## State and result consumers

The compose [`progressListener`](https://github.com/mozilla/releases-comm-central/blob/87d0159c7149a43253964c2cb6917939557dc799/mail/components/compose/content/MsgComposeCommands.js#L925-L1017)
shows the DOM progress meter on START, removes its value, and sends taskbar
`STATE_NORMAL(0,0)`. Positive totals produce a percentage capped at 100 in the DOM.
Taskbar updates use the original current and maximum only when maximum exceeds
65,536. Nonpositive totals remove the DOM value and clear taskbar progress.

STOP clears both send/save flags, hides and resets the meter, empties `statusText`,
and sends `STATE_NO_PROGRESS(0,0)`. Only then does it notify
`mail:composeSendProgressStop`, with the compose window in the subject. This order
is the contract used by both the test helper and `waitForStop`.

[`TaskbarProgress.getTaskbarProgress`](https://github.com/mozilla/releases-comm-central/blob/87d0159c7149a43253964c2cb6917939557dc799/mail/modules/TaskbarProgress.sys.mjs#L12-L38)
selects Windows, macOS or GTK. The compose lazy getter retains the returned object
for the window lifetime. Firefox's
[`nsITaskbarProgress`](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/widget/nsITaskbarProgress.idl#L18-L56)
requires zero values for `STATE_NO_PROGRESS`. Native operating-system painting is
outside this record's declared interface boundary.

## Completion, cancellation and release

An SMTP successful terminal response calls `ondone`. The server's one-shot
`notifyStop` awaits `listener.onSendStop`. In
[`PromiseMsgOutgoingListener`](https://github.com/mozilla/releases-comm-central/blob/87d0159c7149a43253964c2cb6917939557dc799/mailnews/compose/src/MessageSend.sys.mjs#L1662-L1745),
`onSendStop` clears `_outgoingListener`, awaits delivery processing and resolves
`requestPromise` with the request on success. Failure rejects it with the status
in a `Components.Exception`. Despite its stale comment, `onSendStart` does not
resolve this promise. `_deliverAsMail` discards the request value and returns
`undefined` after its await; send completion is not socket closure.

The test has `doFcc=false`. `MimeMessageUtils.getFcc:99–120` returns the empty
default. `_deliveryExitProcessing:716–724` awaits `_doFcc:944–949`, whose empty
`_fcc` path calls `_handleSuccessfulFccCopy:539–562`. The unset message key skips
filtering and reaches `_doFcc2`. Thus final `onStopCopy` can occur even when no
sent-folder copy occurs.

`_doFcc2` schedules the final `onStopCopy` callback with `setTimeout`. Native
[`OnStopCopy`](https://github.com/mozilla/releases-comm-central/blob/87d0159c7149a43253964c2cb6917939557dc799/mailnews/compose/src/nsMsgCompose.cpp#L3119-L3169)
unregisters itself before closing progress, then clears `mMsgSend` and drops its
strong compose keepalive. `CloseProgressDialog` emits STOP; it does not directly
close a DOM window. The dialog closes itself on STOP and unregisters on unload.
The compose global listener has no explicit unregister in the searched compose
content. Progress holds it weakly; dead entries are pruned and destruction clears
the weak list. Window unload drops `gMsgCompose`; the native keepalive covers
deferred terminal callbacks. `CompleteGenericSendMessage` awaits the stop topic,
unless the flag is already clear, before it closes the compose window.

User cancellation sets `processCanceledByUser=true`, which emits
STOP/`NS_BINDING_ABORTED`. The native STOP callback unregisters before calling
`MessageSend.abort`. The outgoing listener can remember cancellation until the
request exists. The SMTP request then closes immediately, wakes a blocked drain
wait, and sends one terminal status. Callback and setter returns do not await
transport teardown. Native promise failure closes progress and releases the
in-flight guard. Compose catches the rejection and unlocks the window; user abort
does not produce the generic warning.

Two source-visible limits remain relevant to error changes. `notifyStop` sets its
terminal flag before awaiting `onSendStop` and has no rejection/finally settlement.
`PromiseMsgOutgoingListener.onSendStop` also awaits delivery processing before
reaching either resolver. If that callback rejects, the local promises are not
settled by these bodies. The async `onready` promise is discarded by `_actionDATA`,
so unexpected stream or progress-listener exceptions have no terminal routing
path there. These are conditional source findings; no runtime failure is claimed.
Temporary-file removal in `_cleanup` starts async removals with logged errors and
does not await them. Promise completion does not certify file removal.

## Exact test links

[`browser_sendMessage_progress.js`](https://github.com/mozilla/releases-comm-central/blob/87d0159c7149a43253964c2cb6917939557dc799/mail/components/compose/test/browser/browser_sendMessage_progress.js#L16-L290)
uses real account/send code with test servers and replaces the platform taskbar
component with a recorder. Its [head helper](https://github.com/mozilla/releases-comm-central/blob/87d0159c7149a43253964c2cb6917939557dc799/mail/components/compose/test/browser/head.js#L29-L52)
sets `doFcc=false`. It is not a test of real operating-system drawing.

- `testSendSmall`, lines127–163, directly checks exactly three taskbar calls:
  NORMAL, NO_PROGRESS, NO_PROGRESS. Its summary says no progress updates, but the
  assertions require start and clear calls; there are no intermediate size calls.
- `testSendLarge`, lines168–248, directly checks progress before clear,
  nondecreasing current bounded by maximum, window identity where available, and
  zero-valued clear calls. It does not require current to reach maximum or exact
  chunk counts.
- Both tests execute native registration, relay and completion cleanup. They do
  not directly assert null/duplicate registration, late replay, dead-listener
  pruning, iterator mutation, cancellation or exceptional callback rejection.
- `testSaveLarge`, lines254–290, checks first NORMAL and last NO_PROGRESS while
  compose remains open. This related assertion is mapped; its complete save
  transport chain is not counted as this SMTP chain's closure.

## Build links and change impact

`mailnews/base/src/moz.build:86` includes `nsMsgProgress.cpp`; its
`components.conf:195–200` binds the actual progress contract. Compose
`src/moz.build:12–57` includes the native sender, JavaScript modules and component
manifest. `components.conf:104–108,170–174` binds MessageSend and SMTP.
`mail/components/compose/jar.mn:6–7` packages the actual window and controller;
`mail/modules/moz.build:49` packages TaskbarProgress. Compose `moz.build:13` includes
the browser manifest, whose line31 selects this test and line2 selects head.js.

Changing chunk size or the 65,536 threshold affects small-message event counts.
Changing current/maximum values affects DOM and taskbar consumers differently.
Changing STOP timing affects taskbar clearing, test waiters, window closure and
compose keepalive release. Changing weak ownership or traversal affects late
dialog replay and removal during cancellation. Changing terminal callback awaiting
affects promise settlement and sent-copy ordering. These are concrete downstream
dependencies, not a complete change-impact map for the modules.

## Limits

This is one reviewed-chain candidate pending independent review. The underlying
body records retain their broader open caller work. No full-module completion is
claimed. Full SMTP handshake/MIME behavior, native OS drawing, alternate outgoing
protocols, arbitrary extension listeners, and complete Save/Background chains
remain outside this defined progress chain. The socket/taskbar interface contracts
and actual selected receivers were checked; those boundaries are explicit.
