# CalDAV multiget owns its fetch queue, item callbacks, timer and token ordering

CalDavMultigetSyncHandler:813–1148 retains the caller's itemsNeedFetching array
by reference, actual calendar, base URI, operation/changelog listener, new token
and page flag. doMultiGet:859–910 pops paths in reverse order while the
calendar.caldav.multigetBatchSize preference (default100) is positive. It encodes
each path then XML-escapes it and sends REPORT/Depth1 via LegacySAXRequest.
Zero/negative batch size consumes no paths; repeated empty batches are a possible
effect if the server responds successfully. No direct runtime test establishes
that configuration's eventual behavior. The request catch only handles request
rejection, not a rejected async stop handler.

onStart:916–943 notifies get failure for non207. onStop:946–998 checks207 and
pre-existing unhandledErrors, commits new sync token when this was the final
queued batch, then awaits handleResponse. Thus token persistence precedes this
batch's DOM parse/storage completion. Newly found unhandled errors are not
checked again before finalization in this body. After parsing, remaining paths
schedule a zero-delay nsITimer whose callback retains this handler; another page
starts WebDAV sync; otherwise actual calendar.finalizeUpdatedItems runs.
No explicit timer cancel/removal was established in the handler.

startDocument/endDocument bracket backing batch. endElement:1063–1140 awaits
deleteTarget for404. For href+ETag+calendar data, it compares cached ETag and
calls addTargetCalendarItem only when changed/new or an operation listener exists.
That listener condition makes an unchanged server item still complete a write
reread. It catches/logs failed item application and continues. Parse fatalError
warns; no general finally around batch end or rejection-to-changelog bridge is
present in these bodies. Cache callback rejection and malformed-item return
can prevent intended operation completion; see [write contract](634448f8-e146-4614-8e03-da5f8ea30c90.md).

Reuse [multiget event-loop yield evidence](ad4309391e1c967b0f6f6f163f52a0ce1e24a768323092d1a7827cda05119fdf.md).
The yield counter increments after awaited changed-item additions, not every
response. This extends that evidence with queue/token/listener/timer ownership.
Direct provider testModifyItemWithNoChanges compares the returned server title
and demonstrates unchanged ETag/item content still completes the ordinary caller.
test_caldav_client asserts one returned item/title. These do not directly check
token-before-parse, final error detection, invalid batch preferences or timer
cancellation. Their existence is not evidence of a product pass.
