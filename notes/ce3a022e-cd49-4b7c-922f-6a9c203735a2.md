# Native storage service retention and queued close callbacks are separate from Calendar wrapper ownership

## Directly observed creation and retention

The storage component constructs `Service` as a singleton. `Service::OpenDatabase`
creates a native Connection. Its constructor registers that Connection with the
service. The service list is an `nsTArray<RefPtr<Connection>>`, protected by its
registration mutex. `getConnections` makes a strong-reference snapshot of that
list. The service is not a raw pointer list whose entries die as soon as Calendar
clears its own wrapper.
Evidence: [storage/mozStorageService.cpp:573–593](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageService.cpp#L573-L593),
[storage/mozStorageService.h:112–121](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageService.h#L112-L121),
[storage/mozStorageService.cpp:214–261](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageService.cpp#L214-L261), and [storage/mozStorageConnection.cpp:840–865](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageConnection.cpp#L840-L865).

When a Connection reference count drops to one, `Connection::Release` treats that
reference as the service's retained entry. An atomic `mDestroying` guard starts
failsafe close and unregisters only once, even if a queued event or snapshot
raises the reference count again. On the opening target it invokes synchronous
close; on another target it queues a retaining runnable to the opening target.
A failed dispatch asserts and attempts close locally. When count reaches zero,
it stabilizes the count then deletes the object.
Evidence: [storage/mozStorageConnection.cpp:890–951](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageConnection.cpp#L890-L951).

`unregisterConnection` removes the retained entry while locked, but lets the
removed reference drop after the mutation lock is gone. It also holds a strong
Service reference across this work. This prevents nested destruction/close from
running while the service is mutating its connection list under that lock.
Evidence: [storage/mozStorageService.cpp:220–253](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageService.cpp#L220-L253).

## Close callback status and interface limit

`AsyncCloseConnection` retains Connection and its callback event until queued
cleanup. It ignores `internalClose`'s return status before dispatching the event.
The actual `CallbackEvent::Run` calls `Complete(NS_OK, nullptr)` regardless of that
internal return. A callback therefore signals this completion event ran; it is
not a detailed report of every native SQLite cleanup result.
Evidence: [storage/mozStorageConnection.cpp:365–407](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageConnection.cpp#L365-L407) and
[storage/mozStoragePrivateHelpers.cpp:255–274](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStoragePrivateHelpers.cpp#L255-L274).

The interface says an already closed/not-open connection will still dispatch a
callback despite its error, but the actual `AsyncClose` readiness guard returns
`NS_ERROR_NOT_INITIALIZED` before making a completion event. Keep this comment/
implementation conflict visible; do not use the interface prose as proof that
every rejection runs a callback. Evidence:
[storage/mozIStorageAsyncConnection.idl:103–122](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozIStorageAsyncConnection.idl#L103-L122) and
[storage/mozStorageConnection.cpp:1968–1977](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageConnection.cpp#L1968-L1977), [storage/mozStorageConnection.cpp:2023–2036](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageConnection.cpp#L2023-L2036).

## Tests and validation limits

`test_failsafe_close_of_async_connection` starts native async table creation,
drops its connection references, forces garbage collection, and awaits completion.
Its final assertion concerns clean shutdown/no crash. It executes retention and
failsafe cleanup, but does not directly check each native reference count,
mutex-release point or early callback rejection.
Evidence: [storage/test/unit/test_connection_failsafe_close.js:14–35](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/test/unit/test_connection_failsafe_close.js#L14-L35).
This file was read in full but not run in the pilot. The related async-close and
statement files passed in the separately recorded installed 160.0a1 build with
unknown native revision. These new native ownership ranges are source checked,
not native-build-matched runtime certification. Full synchronous-close internals,
all failed thread dispatches, and every application shutdown phase remain gaps.
