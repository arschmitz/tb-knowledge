# Account removal uses checked object relationships to retain shared logins

`MailUtils.findRelatedItems(account)` reads the incoming server's username, host, protocol, and authentication method. It awaits all saved logins, then returns sets of related outgoing servers, CardDAV books, CalDAV calendars, and a map from login GUID to the actual objects that use that login. It does not delete these objects.

Outgoing servers are included only when an identity on this account uses their key and no identity outside the account uses it. Password logins use protocol-specific origins and the incoming server username. OAuth items must have the same configured issuer. CardDAV and CalDAV additionally require the same stored username. With password authentication, they use effective-site equality; subdomains may share a site. With OAuth they use issuer equality instead. Address book URL parsing and effective-host lookup can reject; the helper has no broad catch.

This adds a mail caller to the [existing Gecko effective-site body study](8e1219fa-dda2-40fa-a9ce-7b1c0cdad7f7.md). That study already checked `nsEffectiveTLDService` at Firefox `1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b`. The new Thunderbird caller is `MailUtils.sys.mjs:1332–1341,1413–1416,1436–1439` at `87d0159c7149a43253964c2cb6917939557dc799`. Both revisions are retained. Native domain/IDN internals and all invalid-URL inputs are not reanalyzed in this batch.

The remove dialog awaits these relationships before revealing sections and dispatching `relatedItemsLoaded`. It reads each set to display names/counts. `updateItems()` computes the set selected for removal and enables login removal only when every object tied to a login is included. The map uses `.size`/iteration, but its initial early-return check uses `.length`; this does not correctly detect an empty Map. The rest of the method still computes an empty result and disables the checkbox. This is source evidence, not a demonstrated UI defect.

On accept, controls are disabled, the confirmation section is shown, and `removeAccount()` runs. It removes the account first, then selected outgoing servers, address books, and calendars. It deletes a saved login only after every tied object was actually added to the removed set. It searches the GUID again and awaits each login removal. A broad catch shows failure and sets the caller result false; previous removals are not rolled back. Success/failure both fulfill the local async method, allowing the outer handler to re-enable the final OK button. There is no cancel operation once removal starts.

Local message-data removal is disabled for deferred accounts or a local path outside the normalized profile. Missing local storage hides that option. This is a concrete path/ownership check, not a guarantee about every account-manager or filesystem implementation.

Direct unit assertions in `test_relatedItems.js` check exact returned sets, GUIDs, and login-to-object maps for IMAP, POP3, EWS, password, OAuth, shared SMTP ownership, and unrelated same-username services. Direct browser assertions check visible names/counts and removed/preserved objects/logins after checkbox choices. Those tests do not directly check malformed URLs, interrupted multi-stage removal, or rollback. No test was run by this agent.

The XHTML loads this script and Fluent file and declares the exact sections/control IDs. Dynamic Fluent consumers select password versus OAuth IDs and count arguments. The listed IDs exist in the checked file. No rendered dialog or full stylesheet run is claimed.
