Large text-module imports can export an empty string in the DOM module loader. This affects Thunderbird components that import larger HTML files with `type: "text"`.

At Gecko revision `bf75471716c53f2d8e94284f3d37ad6f209459d6`, `ScriptLoader::AttemptOffThreadScriptCompile` skips background JavaScript compilation for JSON and CSS modules. The guard does not include `JS::ModuleType::Text`. `CreateOffThreadTask` calls `LoadedScript::GetScriptSource`, which takes the source buffer. `ModuleLoader::CreateTextModule` then expects the original source and an unset `mWasCompiledOMT` flag. Its exact check is `MOZ_ASSERT(!aRequest->GetScriptLoadContext()->mWasCompiledOMT);`.

A local Web Platform Test imported a 57,344-byte text file through separate static and dynamic module identities. Both complete-content assertions failed with empty exports in Firefox 158.0.1 when text imports and background parsing were enabled. Both passed when `javascript.options.parallel_parsing` was disabled. A Thunderbird Daily 161.0a1 test also reproduced the failure with a 6,547-byte HTML template; its archive payload, size, and CRC were correct.

The proposed fix adds text modules to the existing JSON/CSS guard. It leaves WebAssembly compilation unchanged. The source change and regression test passed independent inspection and lint checks. The fix has not run in a rebuilt browser, so this note does not establish a verified or accepted upstream fix. Disabling background parsing was a diagnostic control, not a proposed production workaround. No general template-size limit is inferred.
