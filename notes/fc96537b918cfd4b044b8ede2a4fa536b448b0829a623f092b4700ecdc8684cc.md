# Use Map entries for arbitrary drag destination filename keys

The historical move and frozen SearchDialog declare messages = new Map(), then read and write messages[msgFileNameLowerCase] as object properties. That bypasses Map entries and permits collisions with Map’s own properties. validateFileName leaves the valid subject size unchanged. A strict ECMAScript probe confirms that assigning messages.size throws TypeError; using set/get for the size key succeeds. Scoped proposal: use Map.has/get/set, or a dictionary without a prototype, for filename counts. Add a drag test for inherited/property names as well as duplicate filenames. The language probe is actual Node validation; the Search Messages UI failure is not reproduced. Static source and test inspection only. No Thunderbird runtime, build, lint or live accessibility check ran. Full Bugzilla and Phabricator discussion remains pending-single-browser-reader.

Scope: Search Messages arbitrary filename key storage.
