# Dialog reuse does not cancel pending event loads

For revision 7b68cf9db1c67fa4736d0125914e3d799d300d0c, the AI source-review report says the singleton event dialog can receive event B through setCalendarEventRoute() while calendar.getItem() for event A is still pending. Closing clears the session and invalidates the operation but does not cancel that underlying call. Retain current-operation checks when changing event loading so a late result cannot replace the current event. This concerns asynchronous event loads; it does not establish a need for separate calendar selector generation checks. Closing an event whose initial load has already finished does not create this initial-load overlap. The report is an AI claim based on source inspection, not independent confirmation: the click sequence was not reproduced in Thunderbird, and the handled feedback was not marked accepted.

Scope: Calendar event source loading.
