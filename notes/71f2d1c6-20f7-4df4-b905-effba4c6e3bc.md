# Storage calendar wipe clears item maps and deliberately retains recurring offline flag maps

## Directly observed write and result consumers

`CalStorageCalendar.deleteCalendar` awaits its item model. The base model queues
extra-table deletes before all event/todo rows and metadata deletes, binding
`cal_id` to each statement. SQL restricts these deletes to this calendar's data.
The cached override awaits that deletion before clearing the general item map
and recurring event/todo maps. It deliberately leaves its separate recurring
offline flag maps and recurring-cache promise intact.

`#cacheItem` adds a parent to the relevant item maps but rejects occurrence objects
with a recurrence ID. `deleteItemById` removes the item and recurring parent maps
after database deletion; it does not delete a matching flag-map entry.
`getFullRecurringEventAndFlagMaps` and the todo equivalent return those maps to
recurring query selection. Item cache cleanup and flag cache lifetime are thus
different contracts. Evidence: [calendar/providers/storage/CalStorageCachedItemModel.sys.mjs:143–154](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCachedItemModel.sys.mjs#L143-L154) and
[calendar/providers/storage/CalStorageCachedItemModel.sys.mjs:196–232](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageCachedItemModel.sys.mjs#L196-L232).

## Direct test links

`testDeleteCalendarEmptiesTheCaches` populates plain and recurring event/todo
items, performs a query to build caches, wipes the calendar, then directly checks
individual reads return null and enumeration is empty.
Evidence: [calendar/test/unit/test_storage.js:136–187](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/test/unit/test_storage.js#L136-L187).

`testDeleteCalendarKeepsOfflineFlagsReadable` seeds its flag maps through a
reopened calendar, checks offline enumeration, wipes and restores the series,
and checks it remains visible through the saved offline-created flag. It directly
checks the retained-flag contract in that setup. It does not check all flag changes
on an already warm model; the separate warm-cache record captures that gap.
Evidence: [calendar/test/unit/test_storage.js:194–241](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/test/unit/test_storage.js#L194-L241).
