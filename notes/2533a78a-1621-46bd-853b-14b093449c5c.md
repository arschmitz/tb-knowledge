# Memory Calendar query filters, offline flags, and stream completion

This extends [memory item ownership](d5525182-1c3b-44b0-b884-628ae793c06c.md) with all query and offline
storage bodies. These are production privileged JavaScript and public IDL
(the interface declaration language), plus xpcshell tests.

`getItems`, `CalMemoryCalendar.sys.mjs:321–456`, returns an empty closed stream
if neither event nor task type is selected. It obtains scheduling support from
the actual `superCalendar` through QueryInterface; on interface failure it
disables the needs-action invitation filter. For that filter, calls the receiver's
`getInvitedAttendee` and checks `participationStatus == "NEEDS-ACTION"`.
Task completion filters call `calITodo` and inspect `isCompleted`.

Date bounds pass through `cal.dtz.ensureDateTime`. Offline filter precedence is
created, then modified, then deleted. Without an explicit offline filter, deleted
items are hidden; created and modified items remain visible. With a filter,
only equal flags match. `calIChangeLog.idl` defines CREATED=1, MODIFIED=2,
DELETED=4. No flag is represented by zero/null depending on the accessor.

The stream source starts `cal.iterate.forEach` over an `Object.entries` snapshot
of item storage. Recurring items requested as occurrences call
`recurrenceInfo.getOccurrences(start,end,remainingCount)`, then filter invitations
and task completion. For a task without a lower bound, uses entryDate as start.
Other items use `cal.item.checkIfInRange`. The parent-only recurring query has an
explicit unresolved range TODO at 437–438; this note does not certify recurrence
backend or range helper internals.

All matches accumulate in `itemsFound`. Only the completion callback at 446–449
enqueues the array, closes the controller, and resolves the source-start promise.
Thus count in the bounded controller is still zero during the item loop; its
`maxTotalItemsReached` check cannot itself stop that loop before final enqueue.
The final controller enforces output count. This producer does not emit one item
at a time according to consumer demand. Its source has no cancel callback.
An exception in a later dispatched iteration is outside the Promise executor's
initial call; there is no explicit catch/reject path in this source callback.

`calProviderUtils.sys.mjs:617–619` implements `getItemsAsArray` by consuming this
stream with `streamToArray`; completion means all chunks were flattened into an
array. `calICalendar.idl:355–451` declares query/range and operation contracts;
the interface declaration alone does not prove a particular provider follows
every range, return-value, or cancellation detail.

Offline methods, memory provider 461–498: addition marks CREATED; modification
retains CREATED or DELETED and otherwise marks MODIFIED. Deleting a CREATED item
removes both item and flag. Other deletion marks DELETED and notifies deletion.
`getItemOfflineFlag` resolves with the flag or null; reset deletes the flag.
Metadata methods at 502–516 directly use a Map and produce arrays of IDs/values.
These operations are separate from ordinary CRUD; callers must perform both
item mutation and journal marking when needed.

Direct test checks: active `test_providers.js:125–272` uses range and unbounded
queries against memory/storage providers and checks fixture counts and selected
properties. The apparent offline-storage task functions at 339–421 are wholly
inside a block comment. They are neither active test registration nor passing
coverage. Metadata checks at 274–337 are active. No direct test of all filter
combinations, source cancellation, dispatched callback failure, or reader release
was established in this file. Cross-repository stream internals are covered in
the separate reader ownership record.
