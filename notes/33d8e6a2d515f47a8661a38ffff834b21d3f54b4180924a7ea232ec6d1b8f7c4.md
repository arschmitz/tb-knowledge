# The biff refactor and later deadline-arithmetic fixes are separate source phases

The owned refactor sorts with int(entryA.nextBiffTime - entryB.nextBiffTime), even though its deadlines are calculated in microseconds with wide arithmetic. That narrowing does not preserve the full PRTime range, so added sorting alone is not proof of correct long-delay ordering. Accepted later source compares the deadlines explicitly and uses server keys for ties. It also changes the timer conversion from floor-only microseconds/1000 to division plus one millisecond and changes the due boundary to allow exact equality. Preserve these later fixes when studying the initial iteration refactor. The exact code establishes different arithmetic and boundary contracts; no polling starvation, sleep/resume or short-delay busy-loop scenario was freshly executed, and the later fix discussion was not fully audited.

Scope: mailnews/base/biff-scheduler.
