# The upload retry loop reuses its storage ID and created upload record

This update moves sendBlob before the metadata retry loop and retains its returned storage ID. The loop caches a returned upload record, so a later item-creation retry can reuse it. The old loop placed sendBlob inside each retry. These local source changes avoid repeating that stage on every metadata retry; they do not prove backend idempotency or exactly-once behavior after a lost response. Four workers preserve results by original part index, and the checked folder caller awaits the result array. No upload or benchmark was executed.

Scope: Thundermail generated multipart upload retries.
