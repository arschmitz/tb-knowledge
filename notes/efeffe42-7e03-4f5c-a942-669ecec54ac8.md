# Calendar storage uses REASON_CANCELLED while Gecko reports REASON_CANCELED

## Directly observed relationship

The wrapper switches on `Ci.mozIStorageStatementCallback.REASON_CANCELLED` with
two L characters. The actual Gecko interface defines `REASON_CANCELED = 1` with
one L character. It defines finished as 0 and error as 2. This is the actual
interface used by the connection callback, not a matching name in an unrelated
API. Evidence: [calendar/providers/storage/CalStorageDatabase.sys.mjs:270–290](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageDatabase.sys.mjs#L270-L290) and
[storage/mozIStorageStatementCallback.idl:33–45](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozIStorageStatementCallback.idl#L33-L45).

A native cancellation completion reason of 1 therefore falls through the
wrapper's default branch at these revisions. That branch logs and rejects with
`NS_ERROR_FAILURE` and the message `error executing async statement`. The intended
abort branch would instead reject with `NS_ERROR_ABORT` and a cancellation-specific
message. Callers that distinguish abort from a query failure can observe the
difference. This note does not claim that every query is canceled or that the
wrapper's callers request cancellation through this API.

## Native cancellation contract

The native `AsyncExecuteStatements::Cancel` sets `mCancelRequested` under a mutex.
A second cancellation fails with `NS_ERROR_UNEXPECTED`. Acceptance of cancellation
is distinct from stopping execution. The run method checks cancellation before
processing; completion can race with a late request.
Evidence: [storage/mozStorageAsyncStatementExecution.cpp:477–510](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageAsyncStatementExecution.cpp#L477-L510).

The test helper accepts either `REASON_CANCELED` or `REASON_FINISHED` when it requests
cancellation. `test_double_cancellation` directly checks the second request's
error. `test_cancellation_after_execution` directly checks that a first request
after execution does not throw. These verify native races and request semantics;
they do not directly check the Calendar spelling or resulting exception.
Evidence: [storage/test/unit/test_statement_executeAsync.js:125–174](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/test/unit/test_statement_executeAsync.js#L125-L174) and
[storage/test/unit/test_statement_executeAsync.js:433–460](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/test/unit/test_statement_executeAsync.js#L433-L460). The full 964-line test file was not reviewed;
only the helper and named ranges were read.
