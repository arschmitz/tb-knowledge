# Calendar observer snapshots, batch ownership, and OperationGroup cancellation order

Production privileged JavaScript. Every body in calDataUtils.sys.mjs was read.
ListenerSet and ObserverSet are actual Set subclasses; their add/delete methods
are not standard Set return contracts.

`ListenerSet`, 24–52, stores QueryInterface results for the configured interface.
Add/delete discard the built-in return value; has returns a Boolean. notify copies
current values before calling named methods. Removal/addition during a callback
does not change that notification snapshot. Synchronous callback exceptions are
logged and later observers still run. Returned promises are ignored; rejected
async callbacks are outside that catch. The set holds strong values until deletion,
clear, or owner release; there is no weak-listener registration here.

`ObserverSet`, 54–86, tracks distinct calendar objects currently in a batch using
a Set. This batchCount is not a nesting depth. Before adding a new observer,
replays onStartBatch for every tracked calendar, then inserts it. That replay is
outside notify's catch. The provider BaseClass, calProviderUtils.sys.mjs:580–595,
has a separate nesting counter and notifies only first start/last end. Cache
helpers forward both underlying sources. These are distinct state machines.

`OperationGroup`, 98–172, owns a UUID-plus-counter ID, pending/status fields,
cancel callback and child operation array. Only pending non-null children are
added. Remove matches ID. Empty does not mean completed; notifyCompleted must
explicitly mark it. Repeated completion logs a warning. A truthy supplied status
replaces the default; zero leaves NS_OK as initialized.

Cancel marks the group complete first, clears and calls its callback once, then
empties child storage and cancels each saved child with OPERATION_CANCELLED.
The final callback therefore runs before child cancellation. A throwing callback
or child can interrupt later cancellation because this body has no catch/finally.
No child results are aggregated here; provider/service code owns that contract.

Direct test: `test_utils.js`'s `test_OperationGroup` checks pending-child filtering,
ID/removal, group state, callback ordering and child cancel count with mocks.
It does not establish async observer rejection handling, batch replay errors,
mutation during notify, weak ownership, or cancellation after a child throws.
FreeBusy uses this group in a separate checked service relationship record.

Other local utilities read: binarySearch returns an insertion position under its
comparator; binaryInsert uses it and optional duplicate suppression; binaryInsertNode
maps children through the supplied accessor and inserts into DOM; compareObjects
creates two nsISupportsInterfacePointer holders, assigns data and the specified
interface (default nsISupports), and compares the resulting data references.
It has no local exception catch. Native interface-pointer conversion is an
external boundary that still needs a separate read.
The exact binarySearch recursive upper-bound behavior is exercised by
test_utils.js's binarySearch cases, including equal final values. These utilities
do not supply observer cleanup or async transaction ordering.
