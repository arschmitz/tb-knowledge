## Validation, failures, and next passes

Representative chains were checked by reading bodies, callers, resource/package entries, state consumers, test setup, and assertions. This also found missing or misleading links: the separate Calendar route preferences, fixture fields versus production controls, accepted HTTP open versus completed response, and add completion versus invitation delivery. No product test was run, so there is no observed passing result for these revisions or an environment to cite as passing.

JavaScript parser failures remain in the original per-file syntax maps; the new pass does not silently count them as covered. Failures can include unsupported/preprocessed syntax or invalid fixtures, but individual reasons have not all been classified. Native syntax errors and the first Tree-sitter 0.26.0 crash remain in the original coverage report; the successful native pass used 0.25.2. Native bodies are not part of the global JavaScript relationship extraction.

Next work should resolve one feature path at a time, check its actual receiver and state reads, pair registration with release, follow error/cancellation branches, and inspect the direct assertions. Priority gaps are general and native callers; interface implementations; constant/dynamic preference and event names; generated bindings; data ownership; worker and process messages; nonstandard test manifests; resources outside the listed UI scopes; and provider-specific persistence and delivery. Extend a focused record when evidence is new by appending another note. Do not rewrite an old note or promote a common pattern into a rule.
