# ICS serializer retains inputs and moves actual component ownership when building output

Production privileged serializer/wrapper JS and bundled third-party ICAL code.
Every local body in CalIcsSerializer.sys.mjs (76 lines) was read. ICAL Component
and Property classes were read in full at Ical.sys.mjs:7779–8775; the rest of
the 10030-line library is not certified by those class reads. ThirdPartyPaths.txt
explicitly lists comm/calendar/base/modules/Ical.sys.mjs; its patterns are not
promoted to Thunderbird policy.

Serializer constructor owns arrays. addItems concatenates nonempty input;
addProperty/addComponent push actual objects. No deep clone is made there.
getIcalComponent, 56–75, creates a fresh VCALENDAR, sets product/version through
actual cal.item.setStaticProps (calItemUtils.sys.mjs:461–468), then adds retained
properties/components and each item's icalComponent. cal.iterate.items at 25–34
yields each parent plus its recurrence exceptions. Thus serializer includes
exceptions, not expanded ordinary occurrence instances.

Actual receiver wrappers: CalICSService.sys.mjs:475–479 imports referenced zones
then adds the supplied underlying ICAL component; 534–547 attempts timezone
reference insertion, catches that attempt's error, then adds actual underlying
property. Bundled Component.addSubcomponent/addProperty at 8575–8589,8625–8643
removes an existing parent reference before adding to the new parent and sets
parent to the new component. It does not clone. This proves ownership transfer,
beyond the serializer's TODO comment. Removal updates jCal/cache and clears parent.

Controlled exact-source experiment: retained event already in one VCALENDAR was
given to serializer.addComponent/getIcalComponent. Old parent child count became
0, new parent count1, and event's actual parent changed. This tests the low-level
ownership path; higher-level item.icalComponent getters may construct other
objects and require their own caller analysis. Repeated serialization can move
these retained extra components between newly built outputs.

serializeToString,32–35, returns wrapper serialized ICS; serializeToInputStream,
37–40, returns a UTF-8 string input stream from wrapper. serializeToStream,
42–54, uses native converter output stream, writes text and closes that converter;
the supplied stream's close contract must be checked in its native implementation.
No async promise or local error catch occurs in these methods.

Actual ICS writer at CalICSCalendar.sys.mjs:544–579 feeds unmapped extras and
memory items, then file writer uses serializeToString and network writer uses
serializeToInputStream. Ownership/state changes can affect later output from the
same objects. Direct test_ics_parser.js:145–221 checks sorted line equality and
string/input/output stream round trips. It checks content, not old-parent
preservation or all repeated-output ownership side effects.
