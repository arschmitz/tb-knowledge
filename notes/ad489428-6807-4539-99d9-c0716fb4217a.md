# ICS download and parse completion, memory replacement, and error preservation

Extends [ICS queue ownership](ce4bf3f0-4a84-48aa-b5b0-db7cc711eb56.md) with the download completion path.
Production JS, an HTTP server test helper, and xpcshell tests. Every local callback
in the stated implementation ranges was read.

`#prepareChannel`, 301–308, bypasses cache, sets notificationCallbacks to this
provider and lets the chosen hook add conditional headers. #doRefresh, 323–349,
constructs a system-principal channel, creates a stream loader, locks, initializes
its observer as this provider, then calls asyncOpen. A synchronous open exception
logs and unlocks. Channel construction/prepare happen before that try. Redirect
352–355 prepares the new channel with forced refresh and verifies NS_OK.
Full native channel redirect/security behavior is outside this note.

`onStreamComplete`, 360–457, receives actual request, network status and byte array.
Success changes currentStatus to NS_OK when needed, clears the connection alert,
and asks the transport hook whether parsing is needed. Network failure preserves
old memory data, optionally shows a connection alert, reports READ_FAILED and
checks bad certificate status. If hook says reuse old data, still sends onLoad
for offline synchronization and unlocks. This load signal does not prove the
server download was successful or data changed.

Zero-length accepted content replaces the memory calendar with empty storage,
registers the observer, sends onLoad and unlocks. Other accepted content decodes
Uint8Array as UTF-8 with TextDecoder; a thrown conversion reports decoding plus
read failure and unlocks. It does not enable TextDecoder's fatal mode here;
not all malformed byte sequences necessarily throw.

Parsing replaces old memory first, starts observer batch and registers the
observer before parser.parseString. onParsingComplete loops parser items and calls
memory.adoptItem without awaiting its promise; retains unmapped components and
properties; catches synchronous exceptions; ends batch, sends onLoad, unlocks.
The callback parameter rc is not checked here. The old comment at 449–452 says
observer registration should follow adoption, but actual registration occurs at
424. Recorded behavior follows the body rather than that comment. Parser/backend
completion and rejected adoption still need their own source scopes.

Direct missing test links: cached ICS
testServerDeletionDropsItemsFromTheCache, providers/test_icsCalendar_cached.js:146–172,
starts with single/recurring events, removes two server events, waits for load,
then checks exact cache IDs and deleted single getItem=null. It directly covers
cache removal, beyond mere execution of sync. testRefillWaitsForTheWipe,
179–227, delays actual storage deleteCalendar and wraps addItem; checks first two
order entries are wipe start/end and preserved IDs. Overrides and calendar are
released in finally. This directly verifies ordering; it is not just an end-state
test. Adds these links to the earlier
[full-sync record](14b243b1-6109-4ba9-be50-d66b7b09c49c.md).

`ICSServer.sys.mjs:15–46,111–161` creates/stops local HTTP server, serves GET/HEAD,
accepts PUT, and hashes serialized contents to an ETag. It does not implement
conditional-header rejection or PROPFIND. Thus its green fixture scenarios do
not prove all real HTTP conflict/ETag fallback branches. The offline tests directly
check their server text, cache items, conflict decisions and journal playback.
