# Keep add-on startup completion distinct from successful installation

Current _installDirect enables the installed add-on, awaits startupPromise when present and then retains a one-second wait. The source comment links this ordering to NOT_AVAILABLE during account-server creation. This is evidence of a historical startup dependency, not proof that a one-second delay guarantees readiness. When changing this path, check the provider startup contract and subsequent server creation rather than deleting the wait as formatting cleanup. This is source and test inspection only. Full Bugzilla and historical review discussion remain pending. No Thunderbird runtime, build, lint or live accessibility check ran.
