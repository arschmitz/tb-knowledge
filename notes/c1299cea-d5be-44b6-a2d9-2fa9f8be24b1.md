# Gecko lazy preference values, callbacks, weak ownership, and cleanup

`XPCOMUtils.defineLazyPreferenceGetter`, lines 176–277, installs a preference
getter but does not register its observer until first access. In debug builds,
a non-null fallback is checked against an already-defined preference type.
The fallback is used for an invalid/missing preference; it is not a persisted
preference default.

First access registers the exact observer with `Services.prefs.addObserver(pref,
observer, true)`, replaces the initial accessor with `lazyGetter`, then reads it.
`lazyGetter` reads a string, integer, Boolean, or fallback according to the current
type and caches the transformed value. The sentinel is `undefined`, so a transform
that returns `undefined` is recomputed on later access. False, zero, and empty
string remain valid cached values. Read/transform exceptions are not swallowed.

The observer accepts only notification data equal to the full preference name.
With no callback, it invalidates the cache for the next read. With a callback,
it takes the previous cached value, invalidates, immediately reads/transforms the
new value, then calls `aOnUpdate(name, previous, latest)`. It does not compare old
and new transformed values before calling. The callback is synchronous in this
body; a returned promise is not awaited. A callback/transform exception is not
handled locally. The body does not itself prove how each native caller reports
that exception.

Ownership is checked across the actual native receiver. The getter closures
retain the observer; the preference branch holds it weakly. A weak reference lets
the observer be collected when no owner retains it.
`Preferences.cpp:2671–2780` stores weak versus strong identity separately and
resolves a weak observer for each notification. `AddObserverImpl:3472–3545`
requires weak-reference support, handles duplicate or weak/strong upgrade cases,
and registers a prefix callback. The JavaScript exact-data check filters any
longer names matching that prefix. `NotifyObserver:3632–3654` sends the branch as
subject, `NS_PREFBRANCH_PREFCHANGE_TOPIC_ID` as topic, and a root-relative name.

`RemoveObserverImpl:3548–3596` tries strong then weak identity and retains the
callback entry if unregistering fails. `NotifyObserver` skips a dead weak referent
and schedules cleanup. `MaybeScheduleCallbackSweep:3613–3629` avoids shutdown and
duplicate runners. `ReapAndCompactCallbacks:3730–3753` removes expired entries
and compacts dead callback nodes. `FreeObserverList:3670–3691` unregisters a
branch's callbacks in bulk at shutdown and guards re-entrant removal.
The JS helper has no explicit dispose API; dropping/replacing the owning getter
can allow collection but does not prove immediate native callback removal.

Direct test links:

- `test_defineLazyPreferenceGetter`, `test_xpcomutils.js:62–119`, checks fallback,
  initial existing value, repeated updates, user-value reset, transformed values,
  and debug fallback-type rejection. It does not directly assert `aOnUpdate`
  argument order or JavaScript observer collection.
- `PrefsBasics.WeakObserverIdleSweep`, `Basics.cpp:121–162`, releases a native
  weak observer, verifies the callback initially remains, changes the preference,
  then waits for callback count to fall. Its repeating timer is test setup for
  idle scheduling and is cancelled afterward.
- `PrefsBasics.WeakObserverRegistrationSweep`, 164–217, checks cleanup after the
  registration threshold and release of its observer array. `gtest/moz.build`
  includes this source in `xul-gtest`.

These native tests check native observer cleanup; they do not prove the complete
JavaScript garbage-collection path for each Thunderbird owner. Preference write
storage, callback-trie ordering, all process forwarding, and every branch-root
configuration are not fully audited by this record.
