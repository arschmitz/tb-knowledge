# Notification preference metric initialization does not establish the later update path

The initial telemetry values are set by initGlean reading the lazy getters. The shown historical and fixed four-argument getter registration does not pass the _updatePreference method as a callback. That method exists and sets a metric, but the inspected inappnotifications source search found no call to it; other URL telemetry writes are separate. Requested granular preference-update metric tests are not added in this assigned diff. This is a bounded update-path/test gap, not a reproduced telemetry failure or a claim all metric collection is broken. A proposed focused test should change each mapped preference after initialization and check its own label alongside the actual display filter. The review applies a blank line between methods, comment punctuation/indent cleanup, scalar Boolean assertion choice and manifest alphabetization while that ordering linter was disabled. Map-generated getters and split limit were optional suggestions; final source application is recorded without creating global rules. The complete Bug data reviewer specifically says these Boolean prefs fall under an earlier collection review; its attachment/linked review was not independently opened and no blanket data-review exemption is inferred.

Scope: In-app notification preference telemetry coverage gap.
