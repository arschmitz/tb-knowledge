# Suggest inline comments for complex or non-obvious code

This is a deliberate user-directed clarification for Thunderbird code writing,
review, and verification. Automatic learning must not change it.

## Guidance

When code is complex or its purpose or behavior is not obvious, suggest a short
inline comment beside the relevant code. State what needs explaining and why.
Read the implementation and relevant callers before proposing the explanation.
Explain the reason, constraint, ordering, or non-obvious action. Do not invent
intent or repeat what clear code already says.

Use the existing comment-writing rules for clear actors, conditions, reasons,
results, exact identifiers, caller contracts, and local format. Place an
explanation beside the action it explains. A complex block may need one comment
for the block rather than a comment on each statement. Do not infer intent from
a name alone. If the reason is uncertain, identify the missing explanation rather
than propose an unsupported claim.
