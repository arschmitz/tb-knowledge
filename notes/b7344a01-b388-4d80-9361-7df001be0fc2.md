# ICS backup names, retention, preference reads, and async failure ownership

Production privileged JavaScript. Every body and nested callback in #makeBackup,
CalICSCalendar.sys.mjs:803–977, was read. Backup completion is separate from
the later upload; backup promises resolve undefined and may reject.

Reads calendar.backup.days (fallback 1) and calendar.backup.filenum (fallback 3)
for each backup. Gets Calendar data directory through checked helper 446–455,
creates backup subdirectory with 0755. A directory or manager/property lookup
failure logs and resolves so upload may continue. Persistent uniquenum2 is created
from current time if absent and forms calBackupData_<id>_<type>.ics names.

An absent initial file triggers a one-time initial copy. backup-time2 controls
whether enough days passed for a daily copy; the property is updated before the
download succeeds. Daily and edit backup filenames are reserved with
nsIFile.createUnique using 0600. Retention enumerates files, selects names
containing this ID and type, sorts by lastModifiedTime, and removes the oldest
excess files. Removal errors are ignored for a later attempt. In a daily pass
purges daily type; otherwise purges edit type. This is not a global guarantee of
exactly three total files or exactly one successful copy every day.

Creates a bypass-cache system-principal channel with provider callbacks and an
nsIDownloader targeted at the edit file. The async download listener treats
FILE_NOT_FOUND as success with no backup, rejects other failed request statuses,
then awaits initial/daily IOUtils.copy when selected and resolves. Those awaited
copy failures have no catch wired to the outer reject here. A later callback
rejection can leave the outer backup promise pending. The callback/channel retain
provider URI/directory/names and promise closures until completion/owner release.
No explicit cancellation handle or finally-based reserved-file deletion appears.
An asyncOpen synchronous exception logs and resolves, allowing upload.

Observed reason: save first attempts a copy of existing source so earlier data
can be restored after corruption or later edits. The stored backup-time update
and best-effort paths limit this assurance. No direct backup-retention, reserved
file cleanup, async-copy rejection, shutdown, or cross-platform permission test
was established by the checked Calendar tests. Generic IOUtils tests are not
proof of this whole backup routine's success.
