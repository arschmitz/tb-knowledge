# Calendar provider properties, identities, scheduling filters, and registry lifetime

Scope: production privileged provider helpers. Every local body in
calProviderUtils.sys.mjs was read, including class methods and lazy callbacks.
The module build exports this file under the Calendar utilities resource path.
Imported account manager, provider classes, storage manager and iTIP internals
are external boundaries, not fully analyzed by this record.

BaseClass initializes per-instance properties, observers, batch count and
wrappedJSObject. Calendar ID assignment persists previously set non-transient
properties. Derived type-specific constructor static transient-property entries
and instance transientProperties decide whether reads/writes persist.
Name/readOnly/URI/superCalendar accessors and observer methods act on those
fields and property helpers, not on a separate Redux state store.

`getProperty`, 697–757, always resolves transport dynamically and reads the
global notify-replies preference on each request. Other values are cached in
mProperties; undefined triggers derived identity/account/organizer resolution,
then stored preferences if permitted. Missing results are cached as null.
Unsupported popup alarms force suppressAlarms. `setProperty`, 760–778,
uses the existing loose inequality guard, changes cache, invalidates derived
identity/account/organizer fields only for imip.identity.key, persists when allowed,
then notifies old/new values. deleteProperty, 780–785, notifies before deleting
local and persisted values. It does not mirror every setter invalidation here.

`getEmailIdentityOfCalendar`, 356–404, uses identity key: null selects default
account or first account with an identity; empty key disables identity; a specific
key searches account identities and optionally returns the owning account.
Missing configured identity is logged. `getImipTransport` returns null without
identity, otherwise the lazy email transport singleton. Directory helper,
446–455, creates profile calendar-data with mode 0700 if missing, caches its
file object, and returns clones to callers.

Scheduling `isInvitation`, 803–857, requires an organizer (or parent organizer),
indexes first attendee per lowercase ID, excludes a calendar-user organizer,
then accepts a matching calendar-user attendee. Without access control, checks
X-MOZ-INVITED-ATTENDEE or organizerId. With access control, checks owner identities
and excludes organizer ownership. Calendar-user addresses are used as provided;
their normalization belongs to their producers. `getInvitedAttendee`, 860–895,
prefers organizerId lookup, then owner identities, then calendar-user addresses.
`canNotify` returns false, selecting outbound iTIP at this base level.

Provider registry at 902–976 uses a lazily initialized Map of ICS and CalDAV
provider objects. Graph provider is included if calendar.graph.enabled is true
at first initialization. The getter does not install a live preference observer.
Register replaces by type; unregister deletes; byType returns the object or undefined;
ics/caldav convenience getters call byType. Registry ownership lasts with the
module Map. A later preference toggle is not proof a provider was added/removed.

Direct test: `test_calProviderUtils.js:1–86` uses an actual memory scheduling
receiver and event to check invitation and invited-attendee outcomes for matching,
empty, differing calendarUserAddresses and organizer cases. It does not directly
check every identity cache invalidation, registry preference toggle, persistence
error, or access-control owner combination. Other provider network and completion
helpers are captured in separate focused records.
