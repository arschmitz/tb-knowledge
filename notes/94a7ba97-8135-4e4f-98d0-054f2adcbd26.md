# Calendar transaction storage results and safe failed-move recovery

Scope: production Calendar transactions; memory and storage provider tests.
This extends the earlier Save and scheduling records with all add, modify, and
delete transaction bodies and the recovery helper.

`CalAddTransaction.doTransaction`, lines 337–341, awaits `calendar.addItem`,
dispatches the ADD operation, then retains the returned item. Its inverse,
343–347, awaits deletion, dispatches DELETE, and saves the item as `oldItem`.
`CalDeleteTransaction`, 420–430, awaits deletion then dispatches DELETE; undo
awaits addition then dispatches ADD. Delete undo does not replace `this.item`
with the provider's returned object. These operations have no explicit return
value; their successful promises resolve with `undefined`.

`CalModifyTransaction.doTransaction`, 365–402, first forms a recovery key from
the old calendar ID and item ID. Before any new edit or move, it awaits cleanup
of earlier failed moves for that source. Same-calendar edits prepare the sequence,
await `modifyItem`, dispatch MODIFY, and retain the returned item.

A move has these exact stages:

1. Save the old calendar and await destination addition.
2. Clone the destination result and make the clone immutable. The snapshot is
   the value against which later cleanup compares storage.
3. Await source deletion.
4. If source deletion succeeds, call scheduling dispatch with ADD then DELETE.
   Finally retain the destination result.
5. If source deletion fails, add the snapshot to the module's recovery map and
   attempt cleanup. If cleanup also fails, log that error and keep the recovery
   entry. Rethrow the original source-deletion error. Do not dispatch scheduling
   messages for this incomplete move.

`removePendingMoveCopies`, 26–39, processes copies in sequence. It fetches the
current destination item and deletes it only if its normalized iCalendar content
still equals the snapshot. Missing or changed copies are forgotten. A read/delete
failure occurs before removal from the set, so that copy remains retryable.
Successful earlier copies have already been removed from the set. The outer key
is deleted after the whole set completes.

The equality helper is checked in `calItemUtils.sys.mjs:279–339`. The caller
passes `[]` and `{}`. Both are truthy, so the usual ignored revision properties
and attendee/organizer name parameters are not excluded. The helper sorts the
normalized properties, parameters, and nested components. A generation-only
edit can therefore protect a destination copy just as a title edit can.
The comparison concerns serialized iCalendar content; it does not compare every
provider property or make the read/compare/delete sequence an atomic operation.

Ownership: the recovery map is module-local and retains immutable live item
snapshots and their calendar references. It is separate from Redux and undo
history. No persistence or shutdown-drain mechanism appears in this file.
The next modify attempt for that source triggers retry. There is no explicit
cancellation API. Provider mutations and provider observer callbacks can already
have occurred before a later failure; scheduling `_dispatch` is a different step.

The inverse move in `undoTransaction`, 404–414, deletes the destination,
dispatches DELETE, adds to the saved old calendar, then dispatches ADD. It has no
equivalent recovery catch if restoring the source fails. Same-calendar undo
uses `prepareSequence` and `modifyItem`, then dispatches the old item. Do not infer
that every multi-step transaction is atomic from the class comment.

Direct checks read:

- `testCalAddTransaction`, `testCalModifyTransaction`, `testCalDeleteTransaction`
  check basic memory-calendar storage and reversal.
- `test_modifyMemoryItemsStartsBeforeYield` checks that memory provider modify
  and redo notify before the caller yields. `_dispatch` is replaced in this test.
- `testMoveRollbackFailureKeepsSourceError` verifies the original error object,
  zero scheduling dispatches, unchanged source, and empty failed undo entry.
- `test_failedMoveRollsBackStorageAndNotifications` checks destination removal,
  retained draft, unchanged history, retry, ADD/DELETE dispatch order, undo, redo.
- `test_failedMoveCleanupCanRetryWithStorage` uses a real storage destination.
  It checks blocked retry while cleanup fails, retry back to source, preservation
  of content-changed and revision-changed copies, and unrelated copies.
- `test_moveRollbackPreservesPendingDestinationEdits` pauses source deletion,
  changes the stored destination while paused, then verifies that rollback and
  later source edits preserve the changed destination.

Those tests replace selected provider methods or scheduling dispatch. They do
not establish remote CalDAV server behavior, invitation delivery, cleanup across
restart, a writer between comparison and deletion, or all inverse-move failures.

Correction to [the operation-constant note](dbac5bb06b70d5f09adb9e9cdf3ea3b13445d08eb000372e7598891d66c7a4cf.md):
at this revision a forward move awaits both destination add and source delete
before either scheduling dispatch. Its older statement that ADD dispatch happens
before source deletion must not be applied here. The old record remains evidence
for its original context. This also verifies and narrows the provisional
[failed-move account](f9f8ded6aede8c3928e1979ff0753f5e9392c66860ea7db956d705d7406ba3e6.md).
