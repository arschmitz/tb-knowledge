# Commands console and shared Thunderbird memory system

Knowledge maintenance runs every 30 seconds and includes history, semantic indexing, query-gap work, learning, and publication. Large synchronous `store.get()`/`store.all()` reads can starve dashboard HTTP even while the backend remains alive. Yield before every full-record read; use the bounded worker `missingSections` operation (existing model filter and 32-row limit), a covering classification-metadata index, and cooperative publication-scan yields. Twenty live API checks during maintenance stayed HTTP 200 in about 27–63 ms with 15 D332899 assessments ready. [Task 10]
