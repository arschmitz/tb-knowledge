# Places transaction history records successful bodies and groups undo work

## Observed behavior

`TransactionsHistoryArray` stores proxy transaction objects in reverse commit order. It owns a `WeakMap` from each frozen proxy to its raw implementation. Each proxy exposes `transact()` and `toString()`; the manager records raw implementations in a `WeakSet` before execution. Reusing an object throws synchronously even if its first execution later rejects. Clearing history does not clear that set.

`TransactionsManager.transact()` obtains the raw object, awaits `execute()`, adds history only after fulfillment, updates the active window's `undo` command group, and returns the exact execute result. New item transactions return a GUID; `Move` returns the input GUID array. The module overview's statement that other transactions have no value does not describe `Move` at this revision.

History entries put the latest successful transaction first. A new independent entry clears redo entries. An undo awaits each entry member in stored order. Redo visits the same entry from its last member to its first member and uses `redo()` when present, otherwise `execute()`. Undo failure logs and clears undo entries; redo failure logs and clears redo entries. Neither branch rolls back already completed members, and each returns before the command update performed on the success path.

`entry(index)` validates an integer in range and returns the live stored entry array. The comment says it returns a clone, but the body does not clone it. This is a directly observed source/comment mismatch; caller mutation effects have not been reproduced in Firefox.
