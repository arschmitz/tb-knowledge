# Select publication candidates before decoding and stream large record sets

Current working-tree store.all() selects every record body when no repository is passed and immediately JSON.parse maps the whole result. publishProjectLessons and exportLessonNotes call it before selecting lesson candidates or linked-note markers. Repository and transport synchronization likewise decode all records before filtering shared rows. A read-only aggregate observation counted63616 records, of which5839 were lessons; it did not measure decoded bytes or heap use. Proposed optimization: select required kind, visibility and repository rows in SQLite before decoding; retrieve needed linked-note markers or evidence by ID; process unavoidable large shared-record sets through bounded cursors/batches rather than one parsed array. Keep full candidate coverage, claim deduplication, existing publication keys, portable-text/credential checks, repository-matched evidence and exact citations, linked-note fallback behavior and immutable-file collision checks. Use a consistent snapshot or explicit single-writer boundary so batching cannot omit new records or change retry behavior. store.all(repository) already filters repository in SQL; the finding concerns the no-argument publication/sync callers and missing kind/visibility selection. No code change, memory benchmark or failure reproduction ran in this worker. Bounded operational error excerpts remain separate private evidence. This proposal concerns local publication and sync. No benchmark establishes that the proposed selection or streaming change resolves a runtime failure.
