# Choose code style for the affected context

This guide extends the existing style instructions. It is a deliberate
user-directed change. Automatic learning must not edit it. The loop default below
is a practical preference for new code, not a claim that all old code follows it.
Current configuration and the affected contract remain decisive.

Read the [coverage report](c3a69f18-1758-4b7e-9d63-5e51cbbcfb54.md) for the exact source, scan, and limits.
Read [the existing style reference](../skills/thunderbird-review/references/style-and-formatting.md)
for naming families, source retrieval, and review reporting. Keep the
[comment-writing guide](81596887-76aa-4804-932a-d01b73042690.md) and its existing
assertion-message rule. This guide adds code choices; it does not replace prose rules.

## Establish the scope before choosing a form

For each changed section, identify its language, component, runtime, file role,
receiver, and caller. A receiver is the object whose method the code calls. A
caller is code that uses a function. A contract describes the inputs, results,
errors, and effects that callers rely on.

Check the resolved lint and formatter settings for the exact path. Read inline
exceptions and ignored-path lists. Then compare accepted siblings in the same
component, language, runtime, and test harness. A harness is the code that runs
tests and supplies their helper functions. Test helpers, fixture data, production
code, embedded scripts, generated files, imported code, and Suite are separate
contexts. A folder name alone cannot classify every section correctly.

Label each choice as one of these:

- **Required:** current configuration, a caller contract, or a direct user instruction.
- **Local practice:** repeated accepted code or checked review decisions in this scope.
- **Suggested default:** a useful choice when the affected section has no stronger reason.
- **Unresolved:** conflicting or missing evidence; preserve the uncertainty.

Do not turn frequency into policy. Do not use one old review to define all files.
Do not copy an exception from test code into production code. Do not treat lint
success as proof of behavior, good naming, or a complete manual style pass.

## JavaScript loops and collection operations

For new code that visits iterable values and performs actions, **prefer
`for...of` over `Array.prototype.forEach` when behavior remains the same**. Use
this default in the affected section, not as a reason to rewrite unrelated code.
An iterable supplies values to a loop; arrays, maps, and many platform collections
do this. A stronger local contract can require another form.

| Need | Form and constraint |
| --- | --- |
| Visit values and perform actions | Prefer `for (const item of items)`. It makes `break`, `continue`, and ordered `await` visible. |
| Use index, reverse order, stride, or explicit index-controlled mutation | Use an indexed `for` loop. State the index's role in its name. |
| Repeat while a condition holds | Use `while`. Use `do...while` when the body must run at least once. |
| Produce transformed values | Keep `map`; use the returned array. Do not use it only for actions. |
| Select values | Keep `filter`; use the returned array. |
| Ask whether any or every value matches | Keep `some` or `every`. An empty array makes `every` true; check that this fits the caller. |
| Return the first matching value | Keep `find`; account for an absent result. |
| Accumulate one result | Use `reduce` only when the result and callback stay clear. A loop is often clearer for several state changes. |
| Enumerate object property names | `for...in` includes inherited enumerable names. Use it only when that contract fits. `Object.keys` and `Object.entries` select own enumerable string properties. |
| Visit iterator values | Iterate directly when no array operation or stable snapshot is needed. |
| Preserve a snapshot or use an array method | Materialize an array when the caller needs it. Do not remove a spread merely to shorten the expression. |

For an ordinary dense array whose contents stay fixed, this is a useful change:

```js
// Before: perform one action for each value.
items.forEach(item => {
  updateItem(item);
});

// After: the action and control flow stay in the current function.
for (const item of items) {
  updateItem(item);
}
```

Keep the value-producing form when it describes the result:

```js
const names = items.map(item => item.name);
const hasUnread = items.some(item => !item.isRead);
```

These are checked illustrative examples, not claimed source excerpts.

### Check meaning before changing a loop

`Array.prototype.forEach` and `for...of` are not interchangeable in every case.
`forEach` skips missing array slots and fixes its visit range before iteration.
The normal array value iterator can yield `undefined` for missing slots and can
visit appended entries. Deleting or replacing entries can affect both forms.
A collection's custom iterator can have a different contract.

A callback's `return` leaves that callback. A `return` in a loop body leaves the
surrounding function. Check the callback's index and array arguments, its `thisArg`,
receiver binding, and any helper signature. Do not pass a callback directly to
another API without checking every supplied argument. For example, `map(parseInt)`
passes an index as the radix; it does not mean the same thing as
`map(value => parseInt(value, 10))`.

For ordered async work, use a loop with `await` when the caller must wait for each
operation. `Array.prototype.forEach` ignores the promises returned by its callback;
awaiting the `forEach` call does not wait for those operations.

```js
for (const item of items) {
  await saveItem(item);
}
```

Use `Promise.all(items.map(...))` only if the operations may overlap. It rejects
when an input rejects and does not cancel work already started. Check ordering,
shared state, load, cancellation, and cleanup. Use `for await...of` when the input
and completion contract need async iteration. Do not change a sequential test
scenario into overlapping work as a style cleanup.

These distinctions follow the [ECMAScript collection specification](https://tc39.es/ecma262/multipage/indexed-collections.html#sec-array.prototype.foreach).
The study also ran small examples for sparse slots, appends, callback returns,
callback arguments, and async completion. They confirm language meaning in Node;
they do not test Thunderbird behavior or prove a platform collection's contract.

## Variables, expressions, and control flow

Use `const` for a binding that is not reassigned. A binding is the name's reference
to a value; `const` does not freeze an object or array. Use `let` for reassignment.
The comm rule uses `prefer-const` with `destructuring: "all"`. Do not mechanically
replace `var` in shared scripts: top-level visibility and redeclaration can matter.
The checked configurations do not enforce `no-var` or `eqeqeq`.

Follow local equality practice and the real value types. **This guide does not
add a blanket `===` rule.** Check type conversion before changing `==` or `!=`.
An intentional `value == null` covers both `null` and `undefined`; a strict check
for `null` alone does not. Existing Calendar and Mail source contains both forms.
Neither a count nor a lint pass proves which form fits a particular comparison.

Use `??` when only `null` and `undefined` mean missing. Use `||` when all falsy
values should use the fallback. Check valid `0`, `false`, and empty strings.
Use an explicit Boolean conversion when the API requires a Boolean result rather
than another falsy value. Do not demand `!items.length` over `items.length == 0`
from Mozilla defaults: comm explicitly disables `mozilla/prefer-boolean-length-check`.

Use optional chaining when absence is allowed. If initialization requires an
object, keep a clear check or failure rather than silently dropping the action.
Check the effect of optional calls and required results. Keep destructuring small
and meaningful. Destructuring a method can lose its receiver. Defaults apply to
`undefined`, not every missing-like value.

Keep guard clauses and state updates easy to follow. The resolved lint includes
`no-else-return`, `no-nested-ternary`, and object method/property shorthand. It
allows `else if` under the checked `no-else-return` options. Do not invent a ban on
all `else` blocks. Preserve intentional switch fall-through and its accepted
comment form. Avoid expressions that combine unrelated assignments and actions.

Use a method, function, or arrow according to its receiver, identity, and caller.
Arrows capture surrounding `this`; normal functions can receive another `this`.
Listener removal needs the same registered function. Object method shorthand is
required by the checked lint; converting every function to an arrow is not.
The `func-names` setting differs between production code and test paths.

Keep static and lazy imports in the established runtime family. Ordinary modules,
privileged system modules, workers, content scripts, WebExtension scripts, and
Storybook do not share every global or import rule. A shorter eager import can
change startup work. Use existing public helpers when their contracts fit; do not
create a near-duplicate API as a style change. Trace relevant callers before
changing inputs, return values, rejected promises, cancellation, or ownership.

## Names and layout

Use concrete role names and name units when needed. A value loop should name a
value; an index loop should name an index. Follow the affected family's case and
prefix choices. There is no new blanket rule for `_`, `g`, private fields, file
case, or Boolean prefixes. Check public names, persisted keys, selectors, imports,
resource manifests, and accessibility references before renaming.

Keep useful blank-line groups and local method organization. Do not impose a
fixed method order or extract a helper only to hit a line-count target. Let the
applicable formatter choose indentation, wrapping, semicolons, quotes, arrow
parentheses, and trailing commas. Nested settings can override parent settings.
Calendar's nested Prettier width is 100. The checked Gecko parent uses 80 and a
CSS width of 160. A width setting guides formatting; it is not by itself proof
that every longer line is a defect.

## Tests, helpers, fixtures, and setup sections

| Context | Checked rule or scoped choice |
| --- | --- |
| General test paths | Mozilla test rules enable event/state waits and disable production `no-console` and unsanitized HTML checks. This permits intentional test construction; it does not establish a production exception. |
| Browser test paths | The browser override restricts direct preference writes and clears in favor of `SpecialPowers.pushPrefEnv`. Check the resolved configuration and cleanup behavior. |
| Calendar test paths | A later override restricts local date getters/setters and multi-argument `Date` construction in favor of UTC forms. UTC means Coordinated Universal Time. |
| Overlapping browser and Calendar paths | The Calendar `no-restricted-syntax` array replaces the earlier browser array. Do not claim both arrays are enforced merely because both blocks match. This study does not repair that configuration. |
| Shared `head*.js` | Lint permits shared top-level helpers that appear unused in one file. Read the harness and consumers before deleting them or changing their scope. |
| `.sys.mjs` and module helpers | Module unused-variable checks cover all variables; shared script globals have different handling. A test directory does not erase module rules. |
| Named test tasks | The test override turns off the production `func-names: "never"` restriction. Keep descriptive task names where the harness family uses them. |
| Storybook `.stories.mjs` | Unassigned imports and unresolved imports have explicit exceptions, including imports that register custom elements. |
| Fixture data and negative cases | Preserve deliberate invalid input and exact protocol data. Do not “correct” it into a passing input. |

Use assertion APIs supplied by the actual harness. Use scalar comparisons for
scalar results and deep comparisons for structures when those APIs support them.
Do not collapse several steps into a clever expression that makes a failed
scenario hard to locate. Reuse a helper when it keeps the test action and expected
result clear; avoid abstractions that hide the scenario.

Register cleanup with the established harness. Prefer waiting for actual events
or states to arbitrary delays. Test setup, scenario actions, assertions, and
cleanup can use different helper forms within one file. A synchronous fixture
builder and an async scenario do not have the same completion contract.

Keep the existing instruction for authored or self-reviewed assertion messages:
each message must contain `should` and state the expected behavior. Do not report
a missing `should` alone as a defect in someone else's patch. A message with the
wrong expected behavior still needs correction.

## CSS, markup, localization, and other languages

Use the [comm CSS configuration](https://github.com/thunderbird/thunderbird-desktop/blob/30cdf5a03b41253e744bc058a699c1947a2b8123/.stylelintrc.js) and the actual component's
shared styles. It requires logical properties and double-colon pseudo-elements,
with explicit platform exceptions. Logical properties follow writing direction,
such as `margin-inline-start`. Check direction, selector scope, cascade, state,
light/dark themes, and forced colors. Reuse established semantic tokens. Dynamic
geometry can need inline style; do not add a blanket ban from one example.

Choose semantic markup and existing widgets in the affected component. Keep
labels, roles, IDs, selectors, and keyboard behavior consistent. Use Fluent
localization IDs from the affected family. Keep IDs stable for unchanged meaning
and check the current migration rules when meaning changes. DOM, CSS, and Fluent
names belong to separate namespaces; their case and prefix rules can differ.

C++, Rust, Python, IDL, shell, build files, and configuration need their own
formatter, lint, accepted siblings, and caller contracts. Do not translate
JavaScript loop or casing rules into them. Native pointer ownership, Rust borrowing,
Python generators, macro expansion, and generated build inputs can constrain
forms that look interchangeable. Read those constraints before suggesting a change.
This study did not do an exhaustive syntax or meaning analysis of those languages.

The [comm EditorConfig](https://github.com/thunderbird/thunderbird-desktop/blob/30cdf5a03b41253e744bc058a699c1947a2b8123/.editorconfig) and
[Python configuration](https://github.com/thunderbird/thunderbird-desktop/blob/30cdf5a03b41253e744bc058a699c1947a2b8123/pyproject.toml) even contain different Python width
values: 88 versus Ruff's 99. Identify the actual selected formatting tool and its
configuration rather than inventing a resolution. Imported crates can bring their
own `rustfmt.toml`; that is not first-party Rust policy. Generated and third-party
exclusion lists must be read as well as the extension.

## Review checklist

- Exact language, component, runtime, file role, and section identified.
- Resolved configuration and inline exceptions checked.
- Local examples are accepted, relevant code; imported and generated code separated.
- Loop form matches values, indexes, mutation, callback binding, and completion.
- Expression changes preserve types, defaults, errors, and valid falsy values.
- Tests use their actual harness, cleanup, assertion messages, and fixture intent.
- Names and imports preserve public, stored, DOM, and resource contracts.
- Formatter and focused lint ran on selected changed files; ignored files reported.
- Each style finding gives a concrete change, its scope, source, and useful reason.
- Harmless alternatives and unrelated cleanup are not presented as defects.
