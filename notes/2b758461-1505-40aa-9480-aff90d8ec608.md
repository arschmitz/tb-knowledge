# Gecko storage locks binding rows and arrays while checking their actual owners

## Directly observed ownership and mutation

`BindingParamsArray` initially retains the creating `StorageBaseStatementInternal`
through `mOwningStatement`. `NewBindingParams` asks that same statement to create
its binding row and refuses once the array is locked. `AddParams` checks that the
row was created by this array, stores a strong row reference, then locks the row.
Locking the row drops the row's array and statement owner references, avoiding an
ownership cycle. Locking the array drops its statement reference because the
statement has now retained the array.
Evidence: [storage/mozStorageBindingParamsArray.cpp:15–69](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageBindingParamsArray.cpp#L15-L69), [storage/mozStorageBindingParamsArray.h:91–96](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageBindingParamsArray.h#L91-L96), and
[storage/mozStorageBindingParams.cpp:91–129](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageBindingParams.cpp#L91-L129).

`AsyncStatement::BindParameters` checks the array's actual owner against `this`,
rejects an empty array, retains it, then locks it. A second array from a statement
with identical SQL is not accepted merely because the SQL or parameter names
match. Explicit `BindByName` and `BindByIndex` methods reject a locked row.
Evidence: [storage/mozStorageAsyncStatement.cpp:303–314](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageAsyncStatement.cpp#L303-L314),
[storage/mozStorageBindingParams.cpp:199–217](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageBindingParams.cpp#L199-L217), and [storage/mozStorageBindingParams.cpp:367–397](https://github.com/mozilla-firefox/firefox/blob/1a097ed8d31f6b307a5d0ebc34a82ceaf7f3727b/storage/mozStorageBindingParams.cpp#L367-L397).
The hidden row used by the `params` helper has a separate internal unlock path;
this note's prohibition concerns exposed binding rows after `addParams`.

## Calendar caller and effect

The actual Calendar item writer creates one array per statement in a `Map`,
creates rows containing `cal_id`, fills item properties, adds the rows, then binds
each array before passing the Map's statement keys to native execution.
Evidence: [calendar/providers/storage/CalStorageDatabase.sys.mjs:218–229](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageDatabase.sys.mjs#L218-L229) and [calendar/providers/storage/CalStorageItemModel.sys.mjs:1079–1130](https://github.com/thunderbird/thunderbird-desktop/blob/87d0159c7149a43253964c2cb6917939557dc799/calendar/providers/storage/CalStorageItemModel.sys.mjs#L1079-L1130).
A change to row/array mutation timing can affect this item-and-extras write batch.
The builder must finish values before adding and binding those rows. This describes
the source contract; it does not create a new project style rule.

`addParams`. `test_bind_params_array_already_locked` checks that adding another row

new row creation fails. `test_not_right_owning_array`,
