# Scalable section-vector retrieval with measured source preservation

This provisional tb-tools change adds a persistent local USearch 2.26.4 index for
section vectors. It speeds up evidence lookup while retaining original vectors
for scoring. It records implementation evidence, not a new shared instruction.
The base Git commit alone does not contain this uncommitted implementation.

## Implementation and evidence

Each repository, embedding model, and vector dimension has separate graph
segments of at most 4,096 vectors. The graph uses inner product, float32 storage,
`connectivity=32`, `expansion_add=200`, and `expansion_search=400`. Search takes up to 240
candidates from each segment, merges them to 240, and adds the newest 128 indexed
vectors in that partition. It scores at most 368 original vectors with the prior
JavaScript arithmetic, then loads only the final section bodies. Final scoring keeps the strict
similarity threshold above 0.35, limit 60, and source order for equal scores.
Approximate search can omit a neighbor. Original-vector rescoring does not make
candidate selection exhaustive.

A durable source change journal tracks inserts, replacements, deletions, and
source identity changes. Graph files are immutable and checksum checked. A batch
saves and flushes changed files before committing mappings, filenames, source
generation, and cursor in SQLite. Cleanup checks the committed manifest under
the writer lock. A failed write preserves prior published files. Cleanup removes unpublished
files when possible and retries later. A reused source row ID or replacement starts a
rebuild. Query and rescoring share a pinned source snapshot; the derived index
must match its source generation. Missing or damaged files, stale or incomplete
indexes, explicit filters, unsupported vectors, small partitions, and near-tied
candidate cutoffs use exact streaming source scoring. Read-only evaluations
always use that exact path.

Startup, embedding maintenance, and normal service activity schedule index work.
No separate indexing command is required. Each scheduled batch has at most 16 rows and a
20 ms target checked between rows. Native operations, file saves, flushes, and
lock waits can exceed that target. Search remains available through the exact
fallback during rebuilding. The query cache reuses at most 16 native view objects;
file-verification metadata has a separate bounded cache. The package pins the
optional native dependency. Unsupported targets retain exact search.

The pinned [JavaScript API](https://github.com/unum-cloud/USearch/blob/v2.26.4/javascript/usearch.ts) supports path-based save/load/view.
The pinned [native view implementation](https://github.com/unum-cloud/USearch/blob/v2.26.4/include/usearch/index_dense.hpp) resets prior storage before mapping.

Exact implementation quote from `commands/knowledge/vector-search.mjs`:

> Score source vectors before loading any section text. Retain only the best 60 rows.

## Measured results

The stable-code benchmark uses fresh worker processes, a fixed ranking clock,
original-vector scoring as its oracle, source/code fingerprints, and the real
searchKnowledge pipeline. The real input is a pinned shared snapshot. Its
Thunderbird partition has 971 existing 384-dimensional MiniLM vectors. It uses 46
mixed-vector and question/section-vector-proxy queries. The synthetic scale cases
use independent queries against clustered 384-dimensional vectors. Each scale
case has 20 queries. No new model calls generate question embeddings or answers.

Every scenario below retained all expected top 60 results, identical selected
source order, and identical complete returned context. The streaming exact path
also matched the prior full-scan section results. Every measured auto query used
the index; these speeds do not include fallback queries.

| Corpus | Queries | Exact section median ms | Indexed section median ms | Exact full query median ms | Indexed full query median ms |
| --- | ---: | ---: | ---: | ---: | ---: |
| real (971 vectors) | 46 | 18.6 | 7.6 | 28.2 | 17.8 |
| stress-1000 (1000 vectors) | 20 | 18.5 | 7.6 | 22.9 | 12.3 |
| stress-10000 (10000 vectors) | 20 | 188.5 | 10.5 | 210.7 | 51.0 |
| stress-50000 (50000 vectors) | 20 | 914.9 | 19.1 | 1098.3 | 298.7 |

The 50k build took 60.6 seconds in the harness, with a
largest measured batch of 177.3 ms. The harness
yields with setImmediate; the production scheduler also waits 25 ms between
pending batches. Production backfill therefore takes longer. OS file caches
were not reset. These are measurements on one Darwin arm64 host, not general
latency guarantees. The small real corpus and synthetic stress data do not
establish recall for every future corpus or query, or generated-answer quality.

A separate production candidate test used 70,000 vectors in 18 segments and 200
calls using 20 query vectors repeated 10 times, without forced garbage collection. Candidate coverage stayed 1.0. The
first call took 137.3 ms and verified all graph files.
Later calls used cached verification metadata and performed no more whole-file
verification reads. Repeated candidate lookup median and 95th percentile were
15.7/21.0 ms. Peak resident process memory (RSS) was
312.4 MB. This checks the 16-view cache beyond its capacity;
it does not establish a universal memory or cold-start bound. The 70k build came
from a provisional run, so only its source-checked, stable-code query repetition
is used as final evidence. OS caches were warm; native mapped-page reads still
occur even when no JavaScript whole-file verification read occurs.

## Rejected approaches and checks

A libSQL 0.5.29 DiskANN trial passed the small corpus but failed the 10k clustered
stress case. A denser `max_neighbors=64` / `search_l=1200` / `insert_l=400` trial still had mean top 60
recall 0.4158 and lost selected sources on 13 of 20 queries, while adding about 977 MiB
of index storage. Separate mutation probes also lost an aged inserted winner
after an update/delete sequence. Those configurations and the dependency were
rejected. The replacement passed original-score recall checks before integration.

The related knowledge and packaging suite passed 221 tests. After the last
recovery changes, 31 focused tests passed with no skips. They cover generation
invalidation, filters, stable ties, unsupported dimensions, missing native code,
pinned readers, cache loss, changed identities, a source write between selection
and rescoring, row-ID reuse, missing/corrupt immutable files, directory loss,
reopen, and a native save that writes then fails. The copied-runtime packaging
smoke passed 384-dimensional add/search/save/view with Node 26.3.1 and copied
USearch dependencies on Darwin arm64. Other platform prebuild paths were checked;
full cross-platform app packaging and runtime execution were not performed.
ESLint and scoped whitespace checks passed. Independent source and failure-path
review found no unresolved implementation issue; this remains model review.

The running console backend was not restarted while other tasks were active.
The new scheduling and retrieval code takes effect when that backend next loads
these source files. No Thunderbird build, UI/runtime validation, Try job, or
new generated-answer evaluation was run for this backend change.
