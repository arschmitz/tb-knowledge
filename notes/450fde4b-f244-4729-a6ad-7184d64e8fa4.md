# Calendar stream iteration crosses Gecko reader locks, completion, and release

Cross-repository chain. Thunderbird production JavaScript
`calendar/base/modules/utils/calIteratorUtils.sys.mjs:243–278` constructs
CalReadableStreamIterator, retains the stream, obtains getReader in
Symbol.asyncIterator, and returns reader.read from next. cancel delegates to
reader.cancel. It has no return, throw, finally, or releaseLock method.
The checked factory/consumer record is [Calendar bounded streams](7d993b50-8d13-4bfe-8370-e91b00be5ce0.md).
Thunderbird `calendar/test/unit/test_calIteratorUtils.js:17–38` executes the loop.

Gecko production C++: every body in ReadableStreamDefaultReader.cpp was read.
`ReadableStreamReaderGenericInitialize`, 62–106, connects reader and stream and
initializes the closed promise according to stream state. Constructor/setup
reject an already locked stream. `ReadableStream::Locked`,
`ReadableStream.cpp:476–478`, tests whether its reader pointer exists.

`ReadableStreamDefaultReaderRead`, 206–241, marks disturbed, dispatches closed
read to CloseSteps, rejects stored error, or asks controller to pull. Read request
ChunkSteps/CloseSteps/ErrorSteps, 131–197, settle read with value/done or rejection.
Closed read resolves with undefined value and done=true. It does not release the
reader. `Read`, 248–269, rejects when reader no longer has a stream and otherwise
creates a promise/read request.

`ReadableStreamReaderGenericRelease`, 277–313, changes the closed promise and
clears stream-reader references. DefaultReaderRelease, 337–351, also rejects
pending read requests. `ReleaseLock`, 356–371, is the explicit entry point.
Reader cancel, 394–417, delegates to ReadableStreamCancel; a released reader
rejects cancellation. Cancel closes stream and runs controller cancel algorithms,
`ReadableStream.cpp:581–666`, but does not itself perform reader release.
Cycle collection declarations/destructor, 36–53, cover native ownership and
pending requests. Retained lock does not alone prove an uncollectable leak.

Thus normal exhaustion of the Calendar custom iterator keeps a reader lock
while the stream remains reachable. Early for-await exit cannot invoke a missing
iterator return cleanup method. Directly calling cancel is not releaseLock.
A controlled exact-source Node stream experiment confirmed locked=true after
normal exhaustion; no Gecko runtime result was recorded for that experiment.
Repeated iteration of the same custom iterator calls getReader again and may
meet the existing lock. All callers' lifetimes remain a broader study scope.

Controller boundary: ReadableStreamDefaultController.cpp:103–154 permits close
or enqueue only while readable and not close-requested. The public Close at
234–243 uses the throwing check. Calendar wrapper double-close therefore meets
a native TypeError path at this revision. Whole controller implementation is not
claimed fully reviewed by this note.

Direct generic WPT assertions: default-reader.any.js:96–188 checks lock and
release/reacquisition; 485–540 checks cancellation does not release the reader
and subsequent release permits new reader access. These target Gecko's public
stream API, not Calendar's wrapper. They were read in those ranges, not run.
Thunderbird test_calIteratorUtils executes its custom iterator, but its assertion
at 35 assigns `dest[idx] = val` and checks truthiness. It does not compare equality
or destination length. Classify it as execution evidence for reading, not direct
proof of returned order, completeness, lock cleanup, or value equality.
