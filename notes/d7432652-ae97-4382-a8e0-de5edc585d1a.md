# Parser timezone warnings connect item state, Fluent arguments, console and alert output

Extends [parser completion](fe892857-0c6f-4f10-b364-179c6dc937ae.md). Production privileged JavaScript and
Fluent localization, plus an explicitly missing direct test.

parserState.checkTimezone, CalIcsParser.sys.mjs:230–255, treats a zone as phantom
when it has no icalComponent and is neither UTC nor floating. For a date with
that zone, keys warning by item.hashId plus zone ID, so one conversion state logs
the same item/zone once. Supplies timezone/title/formatted datetime to
unknown-timezone-in-item, logs text plus item.icalString and stores the key.
This method reports; it does not itself assign a replacement timezone. The
Fluent text's claim about floating fallback needs the actual date backend for
complete behavior proof.

After conversion, processIcalComponent join at 106–119 checks whether any warning
was stored. If alert component exists, gets service, formats
timezone-errors-alert-title and timezone-errors-see-console, creates alert with
name/title/text, and catches showAlert failure. The service lookup and earlier
formatting are outside that showAlert catch. Alerts are separate from parser
status: successful completion still reports NS_OK at 125–127.

Exact Fluent consumers are calendar/calendar.ftl:155–157. Code passes the named
arguments used by the message. Warning state is parserState-local; there is no
repository-wide preference or automatic rule derived from these observed strings.
Direct test link is absent: test_ics_parser.js:test_timezone,141–143, has no body
beyond TODO. Do not count its name or run_test invocation as a checked warning
