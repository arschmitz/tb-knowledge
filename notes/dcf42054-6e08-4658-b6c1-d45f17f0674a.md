# Comment study coverage, results, and source-link correction

The automated file census and full-candidate grammar pass are complete. The
[practical guide](81596887-76aa-4804-932a-d01b73042690.md) and concise instructions
are available to both consumers. This report updates the guide's initial progress
statement. It does not certify perfect extraction or the meaning of every comment.

## Exact source and coverage

The study read Git blobs at `87d0159c7149a43253964c2cb6917939557dc799`, a local
Calendar patch revision. It did not change the source working files. All 43,150
tracked files are accounted for: 31,445 have lexical results and 11,705 have stated
exclusion reasons. There are 5,745 files with no detected comment spans. “No
detected comments” is an extraction result, not proof for every possible syntax.

The retained prose corpus has 523,826 occurrences and 347,640 distinct texts.
Every distinct text passed through a local English sentence parser. Every
occurrence retains its file and comment index. Duplicate text shares one parse.
The parser records subjects, verbs, tense, mood, clauses, articles, pronouns,
condition markers, word counts, and punctuation. This study is not based only on
regex counts or samples. Manual checks support the guide's cited examples.

Exclusions cover binary or non-UTF-8 data, legal documents, prose documents,
structured metadata, encoded keys and certificates, protocol fixtures, expected
output, archives, and imported test data. Each file has its reason in the private
manifest. Generated code, imported libraries, Suite, tests, and non-JavaScript
source remain separately marked. Their wording does not define first-party rules.
Ownership and generated-file markers still need context checks before reuse.

## Findings and their scope

The first-party candidate group contains 92,655 prose occurrences. It includes
normal explanations, short labels, type tags, examples, and commented-out code.
Common parsed verbs include `use`, `set`, `get`, `check`, `add`, `create`, `return`,
and `remove`. Natural first-person reasons, conditional actions, and implied-subject
function summaries recur. Pronouns also recur; their frequency does not prove
clear references. Tag text and code examples can distort sentence counts.

Component practices conflict. Calendar summaries use both “Get…” and “Removes…”.
Mail tests use short instructions such as “Check…” and “Make sure…”. Rust explains
constraints with “We…” and names exact types. Native-code comments often name
caller duties and memory ownership. Suite and old native code include terse
labels and long explanations. None of these forms is a mandatory global template.

The user's rules govern new prose: short, direct sentences, common words, active
voice, concrete actions, exact names, and enough detail to preserve meaning.
Suggested sentence forms help apply those rules. Use an action summary, put a
controlling condition near its action, keep a reason close to the choice it
explains, and name an object again when a pronoun is unclear. Keep passive voice
when the actor is unimportant. Keep concise labels and clear combined outcomes.
Do not turn harmless wording choices into review defects.

For new readers: a caller is code that uses a function. Its contract describes
the inputs, results, errors, and effects that code can rely on. JSDoc is
JavaScript documentation in comments. An API is an interface another component
uses. A promise represents a result that may arrive later.

The guide covers when a comment adds value, sentence structure, articles,
pronouns, tense, mood, clause order, paragraph connections, punctuation, exact
identifiers, links, inline and block forms, JSDoc summaries, tags, parameters,
returns, types, examples, async completion, errors, and defaults. The strongest
rules come from the user and current instructions. Source patterns support scoped
suggestions and counterexamples, not authority through frequency.

## Validation and extraction corrections

- Every saved source span and line number matched its fixed Git blob: zero failures.
- String/comment tests passed for 14 language families. Representative source
  excerpts and parser checks are retained separately.
- All 3,690 `.js`, `.mjs`, and `.sjs` files received an independent JavaScript
  check. The parser accepted 3,668. Tokenization handled 22 legacy or preprocessed
  files. One invalid Suite source line needed a recorded mask; no source was edited.
  Three lexer text mismatches were corrected with parser results.
- Embedded markup checks covered 1,514 XML files and 742 CDATA regions. They added
  342 script comments and 1,080 further CDATA candidates. These checks include
  XBL bodies as well as script elements.
- Event-handler checks covered 5,305 attributes in 2,087 markup files. Of 53 values
  with comment-like delimiters, JavaScript tokenization found four real comments
  and no tokenization failures. Their raw Git spans were checked.
- Compiler include-file fragments and legal notices were separated from prose.
- The grammar model handled checked active/passive and conditional examples, but
  misread some commands and malformed sentences. Labels remain observations.
- All 26 focused instruction-delivery tests passed. Targeted lint and diff checks
  passed. Tests confirm complete guidance on new turns and follow-ups, including
  unavailable knowledge retrieval. No live model-obedience claim is made.

## Remaining limits

Language dispatch, mixed-language templates, macro quoting, generated markers,
ownership, and entity expansion can limit extraction or classification. There are
867 files with lexer error tokens, recorded in the manifest. Errors do not prove
that comments were missed, but the study does not certify perfect extraction.
The sentence parser is statistical. It does not resolve pronoun meaning, check
code behavior, or decide whether every comment is good. A full manual meaning
review of every comment was not done. These limits are part of the result, not
evidence that existing comments should be copied as rules.
