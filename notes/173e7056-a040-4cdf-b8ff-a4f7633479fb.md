# CalDAV server discovery derives capabilities, scheduling endpoints and error state

CalDavCalendar.checkDavResourceType:1577–1774 requests resource type, owner,
principal, privileges, supported reports/components and ctag. Redirect consent
can replace URI; rejected redirect/client errors disable calendar and terminate
discovery. It records auth scheme/realm, WebDAV sync support, principal/home URI,
ctag and supported VEVENT/VTODO intersection. Privileges determine read-only for
shares that cannot write content/bind; a404/null privilege property does not
establish read-only. Capability flags must be checked for explicit resetting
when server changes; presence-setting alone is not a complete transition contract.

checkServerCaps/findPrincipalNS/checkPrincipalsNameSpace:1775–2012 continue through
OPTIONS and principal properties to scheduling inbox/outbox and mailto addresses.
OPTIONS404 can retry calendar URI. Automatic scheduling is preferred; explicit
scheduling setter:402–409 is gated by calendar.caldav.sched.enabled. Discovery
registers actual provider with free-busy service when supported. Missing property
data can try another principal namespace or disable explicit scheduling. That
does not itself clear the separate automatic-scheduling flag. Endpoint/address
updates control later request destinations, organizer properties and inbox polling.

completeCheckServerInfo:2030–2046 saves calendar properties and successful status,
marks checked, then calls safeRefresh. Failure reports mapped error and fails
cached changelog. reportDavError/buildDetailedMessage:2058–2117 map DAV statuses
to Fluent IDs and details, mark disabled-by-DAV-error and notify error observers.
Unknown error IDs return rather than inventing localization. Network alerts are
conditional on a provided network result and calendar enabled state. Alert text,
disabled state, cache refresh completion and onError delivery are separate consumers.

fillACLProperties:1289–1319 selects configured email identity first, then calendar
user address, then ACL owner fallback. An access-controlled ACL owner can override
those choices. setProperty('imip.identity.key'):508–516 invalidates organizer and
identity properties then recalculates. getProperty:478–506 serves actual ACL
properties/capabilities and selects this transport for scheduling support.
The ACL manager's full implementation is reused from the earlier body study;
no new blanket identity policy is learned from this provider behavior.

Direct provider testCalendarWithNoPrivSupport and testReadOnlyFromPrivilegeSet
in cached/uncached files assert no read-only for null privileges and three explicit
privilege sets. They use separate new calendars per case, so they do not directly
check true→false readOnly on the same object after rediscovery. Identity unit
file directly checks configured identity, user address fallback, case retention,
ACL mailto prefix and default identity. Its installed run passed with build limits.
Discovery redirect interaction and endpoint release/unregister were not verified
by those assertions. CalDavProvider autodetection remains a separate body pass.
