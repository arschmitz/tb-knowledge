# Verified test relationship: CalDAV cached add, observer batch, and helper limits

The earlier cached-add note traces provider completion through the injected cache callback. This note adds its relevant test and helper relationships without repeating that full map.

`providers/xpcshell.toml` loads `head.js`, lists `test_caldavCalendar_cached.js`, and fixes the calendar timezone preferences to UTC. The test setup opens a fake CalDAV server and creates a cached CalDAV calendar. The first task waits for initial item/load notifications, verifies the pre-existing item, calls `runAddItem()`, then calls the modify and delete helpers.

`head.js` registers `calendarObserver` through `cal.manager.addCalendarObserver()`. Its `onAddItem()` and `onModifyItem()` directly assert a batch count of one. These callbacks resolve their pending helper promises. `runAddItem()` awaits `calendar.addItem(event)`, then waits for either add or modify notification with `Promise.any`.

Direct test coverage: the batch-count assertions run in the actual observer callback. The first test directly checks that the pre-existing server item can be read. Executed coverage: `runAddItem()` traverses the cached add path and waits for a notification. It does not itself assert every returned field or separately prove cache-write-before-promise resolution. `Promise.any` intentionally accepts an add or modify callback; do not describe it as requiring only an add callback.

Possible/unresolved: a test that directly isolates the injected callback's exact completion order, duplicate failure guard, or all offline-replay branches. Reading this helper does not establish that coverage. The fake server is test infrastructure, not evidence that a real server accepted the operation.

The test unregisters the calendar and its registered cleanup closes the fake server. A full manager-observer removal and harness lifetime audit remains a gap. No passing result is claimed.
