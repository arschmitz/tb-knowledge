# Calendar discovery filters actual providers and returns successful provider-object result groups

Production privileged JavaScript. calProviderUtils:957–975 lazily creates the
actual provider Map with ICS and CalDAV, adding Graph only when
calendar.graph.enabled is true at first access. detection:993 maps to this module.
Detection.providers:44–51 copies providers whose detectCalendars property exists.
It does not create memory/storage providers from matching method names elsewhere.

detection.detect:142–199 checks available providers, applies caller filters to
their type keys, then starts every remaining provider's detectCalendars call.
Each provider promise is converted to {provider,status,detail}; Promise.allSettled
waits for all. A successful nonempty array becomes a Map entry keyed by the
provider object, not its type string. Empty arrays and failures are counted as
failed results. If all fail it throws the last DetectionError found, otherwise
NoneFoundError. A partial successful result does not include failure groups.
DetectionErrorClass:23–31 creates named subclasses for auth, cert, none found and
canceled. These classes give actual instanceof dispatch for UI handling.

No AbortSignal is accepted or passed to provider calls. Waiting for all provider
promises is distinct from cancelling them when one fails or UI closes. A provider
that throws synchronously during the array map can exit before allSettled is
constructed; the documented promise-returning provider contract matters. Filtered
zero-provider behavior goes through the final all-failed test, not the earlier
initial provider-size check.

Actual consumers: calendar-creation.onDetectionSuccess:697–732 prepares cache,
marks already-subscribed URIs disabled, and creates a new Map keyed by provider.type
for list rendering. Account Hub #getCalendars:2231–2279 flattens provider arrays,
turns existing URI results into {name,existing:true}, and returns an array for
selection. These different output shapes are not interchangeable.

Direct test_detection.js:77–96 checks one ICS result and its URI for ordinary/302
discovery. It executes aggregate selection but does not directly assert mixed
provider failures, sync throws, empty filter results or overlapping request order.
Browser discovery tests check UI output from the actual caller. No new aggregate
product run occurred in this pass. This extends existing maps with body behavior.
